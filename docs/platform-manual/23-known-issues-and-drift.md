### 7-note. `config.device_profile_categories` — no reference seed; targeted migrations only (update 2026-08-29)

**Finding**: `config.device_profile_categories` (the profile ↔ device-category compatibility table that `admin.create_device` checks in application code, and that `admin.v_active_device_profiles` / the onboarding wizard's `filterProfiles()` read to decide which telemetry profiles are offered for a chosen category) is populated by **no repository reference seed at all** — `postgres/ddl/80_device_profile_categories.sql` only defines its structure. On staging it held exactly one row (`ENERGY_METER_ENISCOPE_V1` ↔ `Energy Meter`, added out of band 2026-08-24). Consequence: a telemetry profile with no row here is returned by `admin.v_active_device_profiles` with `device_category_ids = {}` and is hidden by the wizard for **every** category, and `admin.create_device` raises *"Device profile is not compatible with the selected category."* The same shape applies to `metadata.device_models` (starts empty; feeds the "Device model" selector and a second `admin.create_device` gate).

- **Severity**: Medium (blocks onboarding of any device whose profile/model has no compatibility/catalogue row; silent — the selector is just empty).
- **What changed 2026-08-29**: Migration `219_airsense_environmental_sensor_compatibility.sql` adds, idempotently and by natural key, the two rows the **Best Energy "Air Sense"** environmental sensor needs: `config.device_profile_categories` (`ENVIRONMENT_SENSOR_AIRSENSE_V1` ↔ `Environmental Sensor`) and `metadata.device_models` (`Best Energy / Air Sense`, `Environmental Sensor`). The pre-existing `ENVIRONMENT_SENSOR_AIRSENSE_V1` profile and its 12 field mappings are **not** modified. See [25-change-history.md](25-change-history.md) 2026-08-29.
- **Still open**: (a) the architectural gap — compatibility is enforced only in `admin.create_device` app code, with **no DB trigger** (a raw `INSERT INTO metadata.devices` bypasses the check); (b) there is still no general reference seed, so every new device model / profile-category pair needs its own targeted forward migration.
- **Recommended action**: Decide whether `config.device_profile_categories` and a base `metadata.device_models` catalogue should become first-class reference seeds (re-applied on every deploy) rather than accreting one migration per model; and whether the compatibility check warrants a DB trigger to close the raw-INSERT bypass.

### 1. Undocumented columns on `metadata.assets` (`building_id`, `floor_id`)

**Finding**: Live staging's `metadata.assets` table has `building_id UUID` and `floor_id UUID` columns. No `ALTER TABLE metadata.assets ADD COLUMN building_id/floor_id` exists anywhere in `postgres/ddl/*` or `postgres/migrations/*` (confirmed by repository-wide search). Yet a live trigger, `metadata.validate_asset_physical_location()`, actively enforces a rule using them: if `space_id` is set on an asset, `floor_id` and `building_id` must *also* be set explicitly on that row — not merely derivable by joining `space → floor → building`.

- **Severity**: Medium
- **Current impact**: Anyone writing a raw `INSERT INTO metadata.assets` that sets `space_id` without also setting `building_id`/`floor_id` will get rejected with `"Asset space requires its floor and building."` — this happened during the Meenaxy Pharma migration this session and was worked around by resolving all three explicitly.
- **Workaround**: Always populate `building_id`, `floor_id`, and `space_id` together when creating an asset with a physical location. See [19-operations-and-diagnostics.md](19-operations-and-diagnostics.md) and [08-device-onboarding.md](08-device-onboarding.md) for the working pattern.
- **Safe to ignore?**: Yes, as long as the workaround is followed. Not safe to ignore if writing new raw seed/migration SQL against this table without checking live schema first.
- **Recommended action**: Locate and add the missing migration to the repository (`postgres/ddl` or `postgres/migrations`) so this column/trigger pair is documented and reproducible on a fresh deployment, not just present on staging by unknown means.

### 2. `ems_readonly` cannot see staging triggers via `information_schema.triggers`; `ems_admin` can

**Finding**: A query against `information_schema.triggers` filtered to schema `metadata`, run as `ems_readonly` (with confirmed `SELECT` access to the underlying tables), returned 0 rows. The identical query run as `ems_admin` returned 12 active triggers across `assets`, `devices`, and `asset_devices`. Root cause not identified this session.

- **Severity**: Medium — this is a **methodology trap**, not just a curiosity: any read-only investigation that trusts `ems_readonly`'s view of `information_schema.triggers` will falsely conclude staging has no validation triggers, when it in fact has many.
- **Current impact**: An earlier verification pass in this session's own history reported "staging has zero triggers on the metadata schema" based on an `ems_readonly` query — that report was **wrong** and was corrected once `ems_admin` access became available.
- **Workaround**: Use `ems_admin` (or query `pg_trigger`/`pg_proc` directly, which are not subject to the same restriction) for any investigation that needs to enumerate triggers, not `information_schema.triggers` as `ems_readonly`.
- **Safe to ignore?**: No — treat as a standing caveat for all future read-only investigations.
- **Recommended action**: Determine why `information_schema.triggers` is empty for `ems_readonly` (likely a privilege nuance in how that view is defined) and document it, or file it as a genuine Postgres/role-configuration question.

### 4. Staging-only duplicate location row (`DISTRIBUTIONPANEL` under both `GROUND` and `MEZZANINE`) — **RESOLVED, re-verified live**

**Historical finding**: Staging's `metadata.spaces` had a space coded `DISTRIBUTIONPANEL` under *both* the `GROUND` and `MEZZANINE` floors of the `PRODUCTION` building (org `MEENAXY_PHARMA`, site `UNIT_2`). Production has `DISTRIBUTIONPANEL` only under `MEZZANINE`. This ambiguity caused a real migration failure this session: a business-key space lookup resolved 25 rows instead of the expected 22 (3 extra matches, from the 3 devices whose asset placement referenced `DISTRIBUTIONPANEL`), because the lookup matched both floors.

**Resolution reported**: the user's later instructions stated this duplicate was subsequently removed from staging.

**Current state — re-verified live, 2026-08-24**:

```sql
SELECT b.code building, f.code floor, sp.code space
FROM metadata.spaces sp JOIN metadata.floors f ON f.id = sp.floor_id
JOIN metadata.buildings b ON b.id = f.building_id
JOIN metadata.organizations o ON o.id = b.organization_id
WHERE o.code = 'MEENAXY_PHARMA' ORDER BY 1, 2, 3;
```
returns exactly 3 rows: `PRODUCTIONLINE_1`/`GROUND`, `PRODUCTIONLINE_2`/`GROUND`, `DISTRIBUTIONPANEL`/`MEZZANINE` — matching production exactly. **Confirmed removed. STATUS: Resolved, current as of this check.**

- **Severity**: N/A (resolved)
- **Recommended action**: None — closed. Retained here as a worked example of business-key ambiguity risk; see [15-mqtt-and-telegraf.md](15-mqtt-and-telegraf.md)/[08-device-onboarding.md](08-device-onboarding.md) for the "business key vs. UUID" principle this illustrates.

### 7. Staging Grafana investigation (2026-08-24) — connection ceiling and one failing recovery job

**Context**: User reported staging Grafana showing errors across multiple UI elements (dashboard tiles, live/status tiles, charts). Investigated read-only, as `grafana_reader` (the real DB role Grafana uses), via `SET ROLE`. Full report in [25-change-history.md](25-change-history.md).

**Finding A — `max_connections=25`**: Staging Postgres allows only 25 concurrent connections total, shared across `ems_app`, `telegraf_writer`, `grafana_reader`, ~13 TimescaleDB background jobs, and any ad hoc `ems_admin` access. At the moment checked, 0 connections were attributed to `grafana_reader` (inconclusive — could mean idle-between-refreshes, not exhaustion).
- **Severity**: Medium — plausible contributing factor for intermittent connection errors under concurrent panel load, not proven.
- **Safe to ignore?**: No — should be sampled during an actual failure (not after) before ruling in or out.
- **Recommended action**: If the Grafana failure recurs, capture `pg_stat_activity` grouped by `usename` *during* the failure window, and check Grafana's own datasource connection-pool settings (max open/idle connections) against this ceiling.

**UPDATE — confirmed active cause and fixed in repo (2026-08-28).** Root cause is **insufficient connection-slot headroom (slot exhaustion)** — not a Grafana query, dashboard SQL, or datasource defect. Observed from `pg_stat_activity`: `max_connections=25`, `superuser_reserved_connections=3` (22 slots for normal roles); concurrent holders `grafana_reader=10`, `ems_app=7`, `telegraf=1`; total `pg_stat_activity` entries reached **31**. Normal-role demand exceeded the 22-slot ceiling, so new sessions failed with `remaining connection slots are reserved for roles with the SUPERUSER attribute` — surfacing on Grafana's PostgreSQL-backed panels while live-datasource tiles were unaffected; datasource `/health` and a lone `psql` also succeed (they only fail once the pool is already saturated). *(The original Finding A above lists "~13 TimescaleDB background jobs" as a contributor — that was an estimate; the connection holders actually observed in `pg_stat_activity` are the three roles listed here.)* **Fix**: `compose.yaml`'s `timescaledb` service now declares `command: [postgres, -c, max_connections=50, -c, superuser_reserved_connections=3]` — command-line settings have the highest PostgreSQL precedence and override the initdb-time `postgresql.conf` (`source = configuration file` → becomes `command line`); **PGDATA and its `postgresql.conf` are never touched**. `max_connections` is a `postmaster` setting, so it takes effect only on a **one-time, separately authorized** `docker compose -f compose.yaml up -d --no-deps timescaledb` (clean restart, PGDATA bind volume reattached unchanged), run **after** the release is on staging — never bundled into the commit/PR; `deploy_release.sh` never recreates `timescaledb` by design. `scripts/verify/verify_database.sh` now asserts the effective `max_connections >= 50` and non-superuser usable slots `>= 45`, and is run by `scripts/release/post_deploy_verify.sh` (the `deploy-staging.yml` post-deploy gate) and `verify_all.sh` — so the check **fails until the recreate is done**, then passes. Grafana datasource pool settings (`maxOpenConns`/`maxIdleConns`) are intentionally **not** changed at this stage. No Grafana dashboard SQL / datasource / tenant-mapping / application change. See `docs/operations/CICD_PIPELINE.md` "PostgreSQL runtime configuration".

**Finding B — `run_failed_message_recovery_job` failing — SUPERSEDED, see §8**: This job's most recent run (21:45, 2026-08-24) failed; no successful run since 20:18. The root cause and full resolution (migrations 203/204/206, plus the unrelated job-1000 stall that produced most of the backlog) are documented in §8 below, not here.

**What this investigation ruled out**: permissions, missing database objects, broken semantic-layer functions/views, broken aggregation, and stale telemetry — all tested directly as `grafana_reader` with real Meenaxy data and found healthy. The root cause, if the failure is still occurring, most likely sits in Grafana's own process/container/connection layer, which this session has no access to inspect (no SSH/`docker exec`/Grafana API).

### 8. Job 1077 recovery-pipeline failure chain: root-caused, fixed, and its downstream blast radius repaired (2026-08-26/27)

**Context**: The `run_failed_message_recovery_job` failure flagged in §7 Finding B (2026-08-24) was investigated to completion two days later, uncovering three distinct, unrelated problems that had to be fixed independently. Full detail (EXPLAIN evidence, exact staging timings, empirical validation) is in [25-change-history.md](25-change-history.md).

**Problem 1 — job 1077 (`telemetry.recover_failed_raw_messages`) supersession search was effectively unbounded**. The per-candidate "is this raw message already superseded?" check joined through `telemetry.v_rtdata` via ordinary hash-joinable `INNER JOIN`s before any time-window filter could apply, letting the planner build an unbounded Hash Anti Join over the full historical `raw_messages` hypertable — one real candidate measured ~467K rows / ~46.7M JSON-expanded elements / ~701M hash-side rows, explaining the job's consistent 10-minute timeout. **Fixed** across three migrations, kept deliberately separate:
- Migration 201: bounded the supersession window to the candidate's own `[bucket_start, deadline]`.
- Migration 202: replaced a general-purpose `telemetry.v_normalized_points` lookup (forcing a chunk-wide `DISTINCT ON` sort) with a narrowly-scoped `telemetry.normalized_points_for_recovery_candidate()`.
- Migration 203: gave the procedure a per-candidate `COMMIT`, so a `max_runtime` cancellation only loses the one in-flight candidate, not the whole batch's progress.
- Migration 204: replaced the remaining `NOT EXISTS` subquery with a targeted read directly against `telemetry.raw_messages` (same window, plus an `rtdata`-is-array guard before JSON expansion, plus a corrected `device_identifiers`-membership identity test — an earlier direct-`device_uid`-comparison draft was caught by a semantic-equivalence audit as unsafe for devices with more than one registered MQTT UID). Result: the same real candidate above dropped from an EXPLAIN-estimated multi-minute scan to 1562.5ms, with TimescaleDB chunk exclusion working correctly.
- Operational sizing: `p_limit` raised from 100 to 1000 (`alter_job`, no code change) once the per-candidate cost was empirically measured (~4.5ms cheap path, ~100-260ms supersession path).

**Problem 2 — job 1000 (`telemetry.run_normalization_job`) stalled for ~15 hours, unrelated to job 1077**. `telemetry.load_normalized_points_incremental()` always computed its forward boundary as `max(telemetry.raw_messages.received_at)` — "catch up to right now" — in one uncommitted transaction. Once the gap between checkpoint and now exceeded the job's 5-minute `max_runtime`, every retry faced an equal-or-wider window with zero possible durable progress; job 1000 was found disabled, stuck at a `2026-08-26 08:16:37` checkpoint. **Fixed**: migration 205 added an optional `p_max_window INTERVAL` parameter (`NULL` preserves prior behavior exactly), enabling a manual, bounded catch-up. Staging recovery: 32 sequential 30-minute bounded calls fully drained the ~15-hour backlog (all `SUCCESS`, 2-44s each), after which job 1000 was re-enabled with its original config unchanged and confirmed running normally.

**Problem 3 — job 1077's own recoverable-candidate population was inflated by a slow-to-notice existence probe**. The "is this raw row already gone?" check probed `telemetry.raw_messages` for physical row existence, but the retention-drop job only runs once/day — so a candidate already provably past the 48-hour retention window could still "physically exist" for up to ~24h, during which job 1077 kept re-running its expensive supersession logic against it (up to 5 attempts each). This inflated the working backlog from ~904 genuinely-recoverable candidates to ~1,964. **Fixed**: migration 206 replaced the existence probe with an age comparison against the retention cutoff, read dynamically from `timescaledb_information.jobs` (`proc_name='policy_retention'`) — never hard-coded. A one-time cleanup additionally marked 1,060 already-provably-expired candidates `PERMANENT_FAILURE` directly (same predicate, both age **and** confirmed non-existence required, to avoid misclassifying rows the daily sweep hadn't reached yet).

- **Severity (all three)**: Was Medium — a secondary recovery path, not primary ingestion (job 1000, primary normalization, was the more serious of the three, since it fed all downstream analytics).
- **Current impact**: None — all three fixed and live-verified on staging as of 2026-08-27. Job 1077 scheduled, `limit=1000`; job 1000 scheduled, re-enabled, watermark advancing normally on its normal 1-minute cadence.
- **Safe to ignore?**: Yes, resolved.
- **Related code**: `postgres/migrations/201-206_*.sql`, `scripts/test/assert_recovery_*`, `scripts/test/assert_normalization_bounded_catchup_window.sql`.

**Downstream blast radius — a separate, still-partially-open finding**: job 1000's ~15-hour stall cascaded into two further downstream aggregation layers that do not automatically self-heal:
- `analytics.demand_intervals` (job 1078) finalizes each 15-minute bucket **once, permanently** (`INSERT ... ON CONFLICT DO NOTHING`) — buckets finalized as `NO_DATA` while job 1000 was down stayed `NO_DATA` forever, even after the backfill later provided real data. **Repaired** (not redesigned): 1,320 stale `ASSET`-scope rows for `2026-08-26 08:15:00→23:00:00` were corrected via a targeted `UPDATE`, reusing the exact same `analytics.calculate_demand_window()` helper job 1078 itself calls — no new business logic, no schema/job change.
- `analytics.energy_consumption_1min` (job 1079) uses a **fixed 30-minute lookback anchored to wall-clock time**, which can never look back far enough to backfill a gap once it falls outside that window. **Repaired**: 19,455 rows for the same window backfilled via the existing `analytics.refresh_energy_consumption_1min(p_from, p_to)` function (the same one job 1079 calls), with explicit bounds — no schedule/config change.
- `analytics.energy_consumption_5min` (job 1080) was investigated and found to be **structurally, permanently empty for this fleet by design** (its refresh function only processes devices with `capture_interval_seconds=300`; every device here is configured at `60`) — not a gap, not touched.
- **Severity**: Low now (data repaired, both Grafana panels — "Demand Profile", "Energy Consumption Trend" — confirmed continuous via direct panel-query re-execution against staging) but the **architectural gap itself remains open**: neither job 1078 nor job 1079 can recover from a future multi-hour outage without another manual, evidence-based repair like this one.
- **Safe to ignore?**: The current data problem, yes (repaired and verified 2026-08-27). The architectural gap, no — it will recur after any sufficiently long future upstream stall.
- **Recommended action (NOT implemented — requires explicit approval before any work)**: either (a) give job 1078/1079/1080 an optional bounded manual-backfill parameter analogous to migration 205's `p_max_window`, or (b) change `demand_intervals`'s finalization `INSERT` to `ON CONFLICT DO UPDATE` with a bounded reprocessing lookback so a small number of recently-finalized buckets are automatically reconsidered every run.

**Update 2026-08-27 — EMS Analytics Platform Phase 2 Foundation, Phase 0 (migration 207) shipped.** A full design (`Audit/EMS Analytics Platform — Phase 2 Foundation Implementation-Planning Design (STAGING, design only).txt`) was produced for a self-healing analytical pipeline (child watermark + bounded catch-up + bounded reconciliation). Its first phase, **Phase 0 — telemetry routing hardening**, is now implemented: migration 207 extends migration 205's `p_max_window` bounded catch-up to `telemetry.load_energy_measurements_incremental()` (job `run_energy_routing_job`, 1001) and `telemetry.load_environment_measurements_incremental()` (job `run_environment_routing_job`, 1012), which had retained the same unbounded `max(platform_received_at)` forward boundary in one uncommitted transaction that stalled job 1000 pre-205 — a latent repeat of this incident one hop downstream. Their scheduled wrappers now pass a bounded `2 hours` by default (`config.max_window`-overridable), so an unattended multi-hour `normalized_points` backlog **self-drains** over successive 1-minute runs; a direct manual `CALL` still performs unrestricted catch-up. See [07-telemetry-pipeline.md](07-telemetry-pipeline.md) "Watermarks and bounded catch-up" and [25-change-history.md](25-change-history.md). **The analytics-tier gap in this item (jobs 1078/1079/1080/1099/1102/1105/1107, `demand_intervals` finalize-once) is NOT addressed by Phase 0 and remains open** — it is Phase 1+ of the same design and requires separate approval per phase.

**Update 2026-08-27 — Phase 0b (migration 208) shipped: analytical-tier jobs hardened (not yet self-healing).** The seven analytical wrappers — `analytics.run_energy_consumption_{1min,5min,15min,hourly,daily}_job`, `analytics.run_demand_calculation_job`, `telemetry.run_environment_daily_job` — now each take a `pg_try_advisory_xact_lock` on their own identity (a second concurrent invocation of the same job records `SKIPPED_LOCKED` and returns without touching the processing path, closing design finding P-C1: demand's provisional `analytics.demand_state` accumulator can no longer be double-applied), record `RUNNING`/`SUCCESS`/`NO_SOURCE_DATA`/`SKIPPED_LOCKED`/`FAILED` in a new `telemetry.pipeline_state` row each (existing columns only; `last_received_at` left NULL — **no watermark yet**), and are registered with a **finite** `max_runtime` (5 min for the 1min/5min/15min tiers, 10 min for hourly/daily/demand/environment_daily), `max_retries = 3`, `retry_period = 5 minutes`, plus a `check_config` validator (`config.assert_analytical_lookback_job_config`) that rejects a malformed `lookback`/`max_catchup_window` at `alter_job` time. **Their processing window is unchanged — still a fixed wall-clock lookback** — so this item's core defect (no self-heal after a multi-hour outage; `demand_intervals` finalize-once via `ON CONFLICT DO NOTHING`) is still fully open; that is Phase 1+ (child watermarks) and Phase 4 (demand `DO UPDATE`), each requiring separate approval. Job cadence is unchanged. `scripts/test/assert_job_schedule_canonical.sql` was extended to assert all seven jobs' schedule/runtime/retry/config/`check_config` (drift detection — partially addressing item 9; the physical move of the `add_job` calls out of migrations 013/028/031/179/181/183/184 into `postgres/jobs/` is deliberately deferred, as several of those migrations use a bare unguarded `add_job` and are checksum-locked, so a canonical-layer registration running before them would double-register).
