## Datasource: provisioned per-tenant at runtime, not statically

`grafana/provisioning/datasources/ems-timescaledb.yaml` is **intentionally empty** (`datasources: []`), with an explicit comment in the file itself: "Datasource provisioning is tenant-managed by the EMS admin portal... Do not add fixed orgId values here. Fixed organization IDs become orphaned when tenants are removed or when the platform is installed elsewhere." The admin portal (`app/src/onboarding/grafana_provisioning_service.py`, `grafana_reconciliation_service.py`) provisions the `ems-timescaledb` datasource separately inside each Grafana organization that has a row in `metadata.grafana_organization_map`. Every dashboard query in the repo hardcodes `datasource.uid = "ems-timescaledb"` and filters by `${__org.id}` — Grafana's built-in "currently logged-in organization" variable — meaning tenant isolation for dashboards depends entirely on (a) the user being logged into the correct Grafana org and (b) that org having a working provisioned datasource pointed at the right tenant filter.

**CURRENT IMPLEMENTATION (verified live, 2026-08-24)**: Meenaxy Pharma has an active mapping row (`grafana_org_id=2`, `is_active=true`, `updated_at` within the same session window as its device commissioning). This was checked specifically because it's a real single point of failure — a migration that populates `metadata`/`config` device data but never touches `metadata.grafana_organization_map` produces devices with zero Grafana visibility regardless of telemetry health.

## Datasource lifecycle: create vs. reconcile (original defect fixed 2026-08-24; self-verification added 2026-08-25)

**Original historical finding**: `GrafanaClient.provision_organization()` (`app/src/grafana_client.py`) called `get_datasource_by_uid()`, and only ever acted on a `None` result (create). An *existing* datasource — found by UID — was left completely untouched. Consequence: if `EMS_GRAFANA_DB_PASSWORD` changed after a tenant's datasource was first created, the app had no code path that would ever push the corrected password into Grafana. **First fix (2026-08-24)**: `provision_organization()` was changed to call a new `update_datasource()` (`PUT /api/datasources/uid/ems-timescaledb`) when the datasource already exists, sharing one canonical payload builder with `create_datasource()`.

**Second historical finding — the first fix was insufficient on its own (2026-08-25)**: deployed to staging (commit `e89146f`), then live-tested against the actual Meenaxy Pharma tenant (Grafana org 2). The reconciliation route returned `HTTP 200` (proving `GrafanaClient`'s `PUT` did not raise `GrafanaApiError`), yet the datasource's `version` field stayed at `1` and its health check kept reporting `password authentication failed for user "grafana_reader"`, unchanged. **Root cause**: a `PUT` that Grafana accepts (any HTTP status `< 400`) only proves the request was well-formed — it is not proof the write was actually persisted. The original `update_datasource()` trusted "no HTTP error" as its only success signal. Grafana's own `version` field is the actual proof: it increments by exactly 1 on every write Grafana genuinely persists, unconditionally of whether the embedded credential later turns out to be valid (password validity is checked separately, at query/health-check time, never at write time). A live `version` that never moved off `1` across two separate reconciliation attempts is direct proof the PUT never took effect, despite the app reporting success both times.

**Investigation that ruled out org-scoping** (checked live before concluding this): Grafana's `X-Grafana-Org-Id` header — the mechanism `_request()` uses for every org-scoped call — was directly verified correct: `GET /api/orgs` showed exactly two orgs (`1: "Main Org."`, `2: "Meenaxy Pharma"`); `GET /api/datasources` under org 1 returned `[]` (no stray datasource landed there); the authenticated admin account's own default `orgId` (via `GET /api/user`) was already `2`; and the single `ems-timescaledb` datasource was confirmed to exist only in org 2. This eliminated "wrote to the wrong organization" as the explanation. The DB-side audit trail (`admin.onboarding_audit`) that would have shown the exact recorded outcome of the earlier reconciliation attempt could not be checked in the same session due to intermittent tunnel connectivity — the fix below does not depend on that evidence; it closes the gap regardless of the exact mechanism, because it no longer trusts an unverified success signal at all.

**Current implementation (corrected 2026-08-25, see resolution below)**: `update_datasource(org_id, existing_datasource_id)` and `create_datasource(org_id)` now **re-read the datasource via `get_datasource_by_uid()` immediately after every write** and verify the result before returning:
- `update_datasource`: raises `GrafanaApiError` if the datasource is missing after the `PUT`, or if the datasource's own `GET /api/datasources/uid/:uid/health` does not report `status: "OK"` immediately afterward. (Earlier versions of this method compared `version` before/after instead — removed; see the resolution entry below for why that was itself a bug.)
- `create_datasource`: raises `GrafanaApiError` if the datasource is missing after the `POST`.

`provision_organization()` now returns a structured `dict` (`grafana_org_id`, `datasource_action` — `"created"`/`"updated"`, `datasource_uid`, `datasource_name`, `datasource_version`) instead of a bare integer, so callers and the admin UI can observe *what actually happened*, not just "no exception was raised." All 4 call sites (`grafana_provisioning_service.py`, and 3 branches of `grafana_reconciliation_service.py::reconcile_grafana_tenant`) were updated accordingly; `reconcile_grafana_tenant`'s returned dict now includes `datasource_action`/`datasource_uid`/`datasource_name` directly, and its `repair_reason` audit text now records the verified action and version.

**Observability fix (the second gap discovered)**: the reconciliation route (`app/src/main.py::reconcile_organization_grafana_tenant`) always computed `result["grafana_reconciliation"]` and passed it into `render_organization_administration()` — but `app/src/templates/organizations.html` had **no markup referencing it at all**. An `HTTP 200` therefore communicated nothing to an administrator; a genuine failure returned by `reconcile_grafana_tenant()` (as opposed to a raised exception) was equally invisible. Fixed by adding a result block to `organizations.html` (using the template's existing `alert`/`alert-success`/`alert-error` convention, matching `device_detail.html`'s established pattern — no new UI framework introduced) that renders: organization id, datasource uid/name, `datasource_action`, success/failure, `reconciliation_status`, and `failure_reason` when present. It renders **only** these non-secret fields — `secureJsonData`/`password` are never part of the result dict in the first place, and dedicated tests pin both facts (the block exists, and it never references a secret field name).

**Repair path for an already-affected tenant**: use the existing reconciliation route, `POST /administration/organizations/{organization_id}/grafana/reconcile` — unchanged, still the sole supported repair mechanism. **Do not** manually edit Grafana's internal datasource record or rotate `grafana_reader`'s Postgres password as a substitute.

**Regression coverage** (`app/tests/test_grafana_client.py`, `test_grafana_reconciliation_service.py`, `test_grafana_reconciliation_routes.py`, `test_grafana_provisioning_service.py`): create/update payload parity (now comparing common fields only, since the update payload legitimately carries extra `id`/`orgId`); `id`/`orgId` present in the update payload; org-id threading through `_request()` (pins the org-scoping investigation's conclusion); `update_datasource` raising when the post-write health check does not report `status: "OK"` (**the corrected regression test for the failure mode discovered live** — simulates Grafana returning `200` for the `PUT` while the health check still reports a password-authentication failure); `update_datasource` **succeeding** when `version` stays unchanged but health reports `OK` (pins the false-negative fix); `update_datasource` raising when the datasource disappears after write; a failing write's `GrafanaApiError` message never containing the password; `reconcile_grafana_tenant` propagating a `GrafanaApiError` uncaught (so the route's existing exception handler renders it, rather than a false success); the reconciliation result being rendered in the template plus never referencing a secret field name.

**Verification status** (read this distinction carefully before relying on it):
- **Verified from repository/code**: all of the above, confirmed by direct inspection.
- **Verified by automated tests**: full suite green (1048 passed) against a local disposable test database, using the same Dockerfile.test/CI mechanism as the pipeline.
- **Verified live against staging Grafana (2026-08-25, resolved)**: the `id`/`orgId` fix and the version-check bug it exposed were both found via live testing on staging (Meenaxy Pharma / Grafana org 2). The health-check-based fix was deployed (commit `859493a`) and the Meenaxy reconciliation re-run live: it succeeded (`reconciliation_status: "REPAIRED"`), and the datasource's own health check independently confirmed `status: "OK"` afterward, corroborated by a fresh, successfully-authenticated PostgreSQL session opened by Grafana. This is the first point in this investigation where the *live* datasource is confirmed healthy end-to-end, not just the code's own logic.

## Credential drift: found, fixed, and ruled out as the sole cause (2026-08-25)

Root-caused via a checksum-only comparison (never exposing either value): the staging `ems-admin-portal` container's actual live `EMS_GRAFANA_DB_PASSWORD` was tested directly against PostgreSQL using the app's own `psycopg` driver, from inside the running container, and **failed to authenticate as `grafana_reader`**. Investigating the repository's credential-provisioning model found the actual cause of the drift: **neither `grafana_reader`'s PostgreSQL password nor `EMS_GRAFANA_DB_PASSWORD` has an authoritative source anywhere in this repository.** `postgres/ddl/02_roles.sql` creates the role with a literal placeholder (`PASSWORD 'CHANGE_ME_GRAFANA'`); no migration, bootstrap script, or CI/CD step ever calls `ALTER ROLE` on it; `scripts/bootstrap/02_validate_env.sh` validates that several other credentials exist (`POSTGRES_PASSWORD`, MQTT vars, Grafana's own admin login) but never validates or provisions `EMS_GRAFANA_DB_PASSWORD` or keeps it in sync with the database role. Both sides were set manually, independently, at different times, with nothing to prevent or even detect them drifting apart — which is exactly what happened.

**Repaired** (staging only, explicitly approved per-step before execution): generated a new random credential on the staging host itself (never transiting to any other system); set `grafana_reader`'s PostgreSQL password to it (`ALTER ROLE`, via the same `docker compose exec ... psql -U ems_admin` mechanism `scripts/apply_migrations.sh` already uses); set `EMS_GRAFANA_DB_PASSWORD` in staging's `app/.env` to the identical value; recreated `admin-portal`/`live-telemetry` (service-scoped, matching `deploy_release.sh`'s pattern — `timescaledb`/`telegraf`/`grafana` never touched). Verified via SHA-256 hash comparison and a live connection attempt from inside the container: the new value authenticates successfully. This remains a real, necessary fix — the old value was genuinely wrong — but:

**Ruled out as the (sole) root cause of the reconciliation failure**: with the new, independently-verified-correct password deployed and confirmed, the Meenaxy reconciliation was re-run and **failed identically** — `version remained 1`, the exact same `HTTP 200` write-response body, the same target identity echoed back. This is direct, live proof that an incorrect password was never the reason the datasource `PUT` fails to persist. The true cause remains open. **Recommended next step** (not yet attempted): include the datasource's numeric `id` field (available from the pre-write `GET`) in the `PUT` payload alongside `uid` — some Grafana API versions' UID-addressed datasource endpoints have been observed to echo the correct target identity in their response while internally still keying persistence off `id`, which the current canonical payload never supplies. This is a hypothesis, not a confirmed defect — it should not be implemented without first finding a safe way to test it.

**Missing `id`/`orgId` fields fix (2026-08-25)**: Grafana 11.6's documented request body for the UID-addressed datasource update endpoint (`PUT /api/datasources/uid/:uid`) includes the datasource's numeric `id` and `orgId` alongside the common configuration fields. The prior `update_datasource()` implementation omitted both — it built its `PUT` payload from `_datasource_payload()` alone, which intentionally contains no `id`/`orgId` (those fields don't exist yet for a not-yet-created datasource, and `_datasource_payload()` is shared with `create_datasource()`). `update_datasource()` now takes the existing datasource's numeric `id` (from the `get_datasource_by_uid()` record `provision_organization()` already fetches before branching to create/update) and adds `id`/`orgId` to the update payload only, on top of the unchanged canonical fields; `create_datasource()` is untouched, since a newly created datasource has no prior numeric `id` to send. This was deployed and is confirmed necessary (correct per Grafana's documented contract) but, live-tested alone, **not sufficient** — see the resolution below.

**Resolution (2026-08-25, live-verified on staging, Meenaxy Pharma / Grafana org 2)**: with the `id`/`orgId` fix deployed (commit `4e2a5e3`), the Meenaxy reconciliation was re-run live via `reconcile_grafana_tenant()` directly (portal_user_id 1, the sole active staging portal account) and **still raised `GrafanaApiError`**: `version remained 1`, even though the PUT's own response body already carried `"message": "Datasource updated"`. This exposed a second, deeper bug: **the `version`-must-increase check itself was wrong**, not the write. Direct evidence: immediately after the PUT, a fresh PostgreSQL backend (`pg_stat_activity`, ~44s old, confirmed via `ems_admin`) opened by Grafana authenticated successfully as `grafana_reader` — and PostgreSQL accepts only the one currently-set password for a role, so a fresh successful auth is conclusive proof the just-written secure password was in fact applied, `version` notwithstanding. Grafana's own HTTP API documentation example for this endpoint independently corroborates this: its sample *response* to an update shows `"version": 1`, i.e. Grafana's own docs don't depict this endpoint as reliably incrementing `version` either. **Fix**: `update_datasource()` no longer compares `version`; it instead calls the datasource's own `GET /api/datasources/uid/:uid/health` immediately after the `PUT` and requires `status: "OK"` — a functional check of the exact credential Grafana just stored, rather than an assumption about an internal counter. Deployed as commit `859493a`; running-image digest confirmed matching CI's pushed digest via `docker inspect` on staging. Re-run against Meenaxy live: `reconcile_grafana_tenant()` returned `{"success": true, "reconciliation_status": "REPAIRED", "datasource_action": "updated", ...}` — no `GrafanaApiError`. Independently verified afterward: `GET /api/datasources/uid/ems-timescaledb/health` (org 2) returns `{"status": "OK", "message": "Database Connection OK"}`; the datasource still targets `uid: ems-timescaledb`, `database: ems`, `user: grafana_reader`, `url: timescaledb:5432`; `version` remained `1` throughout (confirming it is not a meaningful signal for this endpoint/Grafana version, as hypothesized); and a fresh PostgreSQL session opened by Grafana (`pg_stat_activity`, ~36s old at check time) authenticated successfully as `grafana_reader`. **The Meenaxy Grafana datasource is now confirmed healthy end-to-end, live.**

**Operational note**: an intermediate deploy step during this repair briefly ran `admin-portal`/`live-telemetry` on the wrong (stale default) image, because a manual `docker compose up --no-build` omitted an explicit `APP_IMAGE` pin. Caught via `docker inspect` before any further action, and corrected by dispatching the repository's existing `rollback.yml` (`workflow_dispatch`, previously undocumented in this manual as a non-code-change redeployment path) targeting the exact previously-verified commit SHA — this reuses the same `deploy_release.sh`/`post_deploy_verify.sh` path and the same `REGISTRY_USERNAME`/`REGISTRY_PASSWORD` repo secrets as a normal deploy, without rebuilding or requiring a new commit.

## Live-telemetry datasource: never provisioned, plugin never deployed (found and fixed 2026-08-25)

**Symptom**: after the `ems-timescaledb` datasource was confirmed healthy, `ems-asset-overview`'s live/canvas panels (frequency, voltage, current, power factor, THD, active power, last-seen status — 8 panels) still failed with `Datasource ffuz5sq2fe9s0a was not found` in the browser.

**Root cause (read-only investigation, confirmed independently via three live signals that all agreed)**: the `wisewatts-live-datasource` Grafana plugin (`grafana/plugin-src/wisewatts-live-datasource`) had never been built and deployed to staging's Grafana plugin directory (`/opt/ems-platform/grafana/plugins/`, bind-mounted, `.gitignore`d since it holds a built artifact, not source) — confirmed both via the filesystem (only two Grafana-bundled apps present, no `wisewatts-live-datasource`) and via Grafana's own `/api/plugins` (0 matches out of 51 installed plugins). Consequently, no Grafana datasource *instance* of that type existed in any organization either (`/api/datasources` for both org 1 and org 2 returned only `ems-timescaledb`). `ffuz5sq2fe9s0a` is the UID already hardcoded into every live-panel `datasource.uid` in `grafana/dashboards/core/asset-overview.json` (the dashboard shared across every tenant org via `import_dashboards()`) — nothing in `app/src` ever provisioned a matching instance, unlike `ems-timescaledb`, which has had automated create/reconcile logic in `GrafanaClient` since 2026-08-24. This was a deployment/provisioning gap for an entire feature, not a regression of previously-working configuration, and a different root cause from the `ems-timescaledb` version-check bug documented above.

**UID determinism, considered before implementing**: `ffuz5sq2fe9s0a` looks like a Grafana-auto-generated instance ID (unlike `DATASOURCE_UID = "ems-timescaledb"`, a deliberately human-readable constant), most likely captured from wherever `asset-overview.json` was originally authored/exported. It was **not** treated as a design choice here — but since the dashboard JSON is shared identically across every tenant organization and was explicitly out of scope to edit without proof the UID itself is wrong (it is not; the value works fine, it was simply never provisioned anywhere), the dashboard is the contract: every org's live-datasource instance must use this exact UID for the dashboard to resolve it in any organization. `LIVE_DATASOURCE_UID = "ffuz5sq2fe9s0a"` in `grafana_client.py` documents this reasoning inline.

**Immediate staging recovery (read-only investigation → explicitly authorized state-changing recovery)**: ran the repository's own existing `grafana/plugin-src/wisewatts-live-datasource/build-plugin.sh` directly on staging (the intended, only build mechanism this repository already has — no parallel mechanism invented), installed the resulting artifact into `/opt/ems-platform/grafana/plugins/wisewatts-live-datasource/`, then `docker compose restart grafana` — the **only** container restarted (`deploy_release.sh` deliberately never touches Grafana; this restart was a manual, explicitly authorized, one-time action, not an automated pipeline step). Verified via `GET /api/plugins`: Grafana now reports `wisewatts-live-datasource` (`WiseWatts Live`, unsigned, as expected given `GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS`).

**Durable fix (architectural gap closed)**: `GrafanaClient.provision_organization()` now provisions/reconciles **two** datasources per organization, not one — `ems-timescaledb` (unchanged) and the new `create_live_datasource()`/`update_live_datasource()` pair for `wisewatts-live-datasource`, sharing the same generic create/verify (`_create_datasource`) and update/health-check-verify (`_update_datasource`) internals `ems-timescaledb`'s methods now delegate to, so the two cannot drift in verification behavior (in particular: the live datasource's reconciliation also does **not** treat Grafana's `version` field as a success signal, for the same reason documented above — it uses the same post-update `/health` check, which the plugin's own `CheckHealth()` implements). The live-datasource payload carries no `url`/`database`/`user`/`secureJsonData` — the plugin reads its live-stream connection details (`EMS_LIVE_TELEMETRY_WS_BASE_URL`, `EMS_GRAFANA_STREAM_TOKEN`) from the Grafana process's own environment, not per-instance settings. `provision_organization()`'s result dict, `reconcile_grafana_tenant()`, and the admin-portal's reconciliation-result UI (`organizations.html`) were all extended in parallel with the existing `datasource_*` fields.

**Onboarding durability**: `scripts/bootstrap/06a_build_grafana_live_plugin.sh` (new, inserted into `scripts/bootstrap.sh` between `06_start_telegraf.sh` and `07_start_grafana.sh`) runs `build-plugin.sh` as part of every fresh-host bootstrap, so a brand-new environment no longer silently reproduces this gap. This intentionally does **not** touch `deploy_release.sh` (the CI/CD-invoked redeploy script), which deliberately never restarts Grafana on every app deploy (`APP_SERVICES` is always named explicitly; `timescaledb`/`telegraf`/`grafana` are never in that list) — that boundary is preserved. **Residual manual step**: if the plugin's *source* changes in the future, `06a_build_grafana_live_plugin.sh` only runs again on a fresh bootstrap; an existing host needs `build-plugin.sh` re-run and Grafana manually restarted, the same deliberate-manual model already established for Grafana version upgrades (see the compose.yaml pinning comment).

## What each dashboard actually queries

## Troubleshooting approach (derived from the above, not a separate untested procedure)

1. Confirm the tenant has an `is_active=true` row in `metadata.grafana_organization_map`.
2. Confirm the underlying `analytics.v_grafana_*` view returns rows for that `grafana_org_id` directly via SQL (bypassing Grafana) — if it does and the dashboard still shows nothing, the problem is Grafana-side (wrong org selected, datasource UID mismatch, provisioning failure), not data-side.
3. Check whether the panel's expected time range matches how much telemetry history actually exists — a newly commissioned device with only minutes of history will legitimately show "no data" on a `now-24h` panel range for most of that window; this is not a query or backend failure. See `19-operations-and-diagnostics.md`.
