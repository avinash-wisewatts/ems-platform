B. EXACT ROOT CAUSE OF THE EMPTY DROPDOWNS
===============================================================================

Traced the real application code (not assumed): app/src/onboarding/repository.py
backs the onboarding UI's dropdowns via three read-only views:
    list_device_categories() -> admin.v_device_categories   (config.device_categories — populated, fine)
    list_gateway_models()    -> admin.v_gateway_models       (metadata.gateway_models — populated on staging, but NOT reproducible from any repo seed)
    list_device_models()     -> admin.v_device_models        (metadata.device_models — EMPTY, root cause of the empty "Device Model" dropdown)
    list_device_profiles()   -> admin.v_active_device_profiles (joins through config.device_profile_categories
                                 to expose device_category_ids/device_category_names per profile — with
                                 that join table empty, ENERGY_METER_ENISCOPE_V1 shows with no compatible
                                 category, so admin.create_device's compatibility check always fails)

app/src/device_management_service.py confirms the REAL "Create Device" action
calls admin.create_device(...) directly (the granular API), NOT the wizard-
style admin.onboard_energy_asset(...) — this rules out using the wizard
function as a workaround; it is not what the actual UI/app uses.

admin.create_device's own body (read in full, live) enforces both blockers
explicitly:
    IF NOT EXISTS (SELECT 1 FROM metadata.device_models dm
                    WHERE dm.id=p_device_model_id AND dm.device_category_id=p_device_category_id)
        THEN RAISE EXCEPTION 'Device model does not match the selected category.';
    IF NOT EXISTS (SELECT 1 FROM config.device_profiles dp
                    JOIN config.device_profile_categories dpc ON dpc.profile_id=dp.id
                    WHERE dp.id=p_profile_id AND dp.is_active AND dpc.device_category_id=p_device_category_id)
        THEN RAISE EXCEPTION 'Device profile is not compatible with the selected category.';

Confirmed exactly as the user's prior audit stated: both are genuine,
currently-blocking gaps for the real, actually-used commissioning path.

NEW finding beyond the prior audit: admin.create_gateway(...) ALSO requires
a valid p_gateway_model_id (IF p_gateway_model_id IS NULL OR NOT EXISTS
(SELECT 1 FROM metadata.gateway_models WHERE id=p_gateway_model_id) THEN
RAISE EXCEPTION 'Select a valid gateway model.'). metadata.gateway_models
happens to have 3 rows on staging today, but — see G — this is NOT
