3. DISCREPANCY REPORTED BEFORE PROCEEDING (per instruction)
===============================================================================

The repository's job-registration files are already canonical — there is no
buggy repository code to fix. The defect is entirely in the LIVE RUNNING job
configuration on staging, which fell out of sync with those already-correct
files (they execute once at initial deploy and are not automatically
re-applied). CICD_PIPELINE.md itself states the remediation is "likely by
re-running the relevant alter_job calls from the three postgres/jobs/*.sql
files against staging, under its own change control."

Given the constraint "do not touch staging directly," the correct minimal
production change — consistent with this project's only existing mechanism
for correcting staging state through code (a forward migration applied by
the established CI/CD pipeline) — is a NEW migration that reasserts the
canonical alter_job values on the three already-registered jobs. This is not
an improvisation: it is the literal remediation the source document
describes, expressed as a migration rather than a direct staging command, so
that it goes through the same review/approval/CI path as every other change
in this project. No other interpretation of "smallest production change"
was found to fit both constraints (fix the drift; never touch staging
directly) without this migration mechanism.

5. PRODUCTION/CONFIGURATION OBJECT CHANGED
===============================================================================

Migration 194 performs three idempotent, targeted DO blocks — one per job —
each locating the job by (proc_schema='telemetry', proc_name=<job>) and
calling alter_job(...) with the canonical values. It does not create or
replace any procedure, and does not call add_job — if a named job is found
missing, the migration deliberately raises an exception rather than silently
creating one (a missing job would be a different defect than the one
diagnosed here).

Before/after (documented drift -> corrected value, all three jobs):
    schedule_interval: (5 min | 1 min) -> 1 minute
    overlap (config):  (20 min | 1 min) -> 15 minutes
    max_runtime:       unspecified/unknown drift value -> 5 minutes
    max_retries:       unspecified/unknown drift value -> 3
    retry_period:      unspecified/unknown drift value -> 1 minute
    scheduled:         reasserted TRUE

(max_runtime/max_retries/retry_period were not individually itemized in the
documented drift table, which only tracked schedule/overlap — but the
migration reasserts all five parameters together, matching exactly what the
canonical postgres/jobs/*.sql files already assert on a clean install.)

6. TEST COVERAGE ADDED
===============================================================================

runtime TimescaleDB job catalog (timescaledb_information.jobs) for all three
jobs and asserts schedule_interval, max_runtime, max_retries, retry_period,

scripts/verify/verify_jobs.sh, and the three job-registration files'

test cannot drift in lockstep with a regression in the migration.

timescaledb_information.jobs — zero prior matches). This is a genuine,
previously-uncovered gap in local test coverage, and is part of why this
drift was never caught by CI before reaching staging.
