0. CORRECTIONS TO THE PHASE 2 DESIGN (found this pass — must land before code)
=====================================================================

C1. [FACT] telemetry.refresh_environment_daily() reads
    telemetry.environment_measurements DIRECTLY (its FROM clause, line ~125),
    NOT ca_environment_15min/hourly. The Phase 2 design (§B, §G, §Q Phase 5)
    assumed the env CAGGs were its source. They are not — the env CAGGs feed
    only the environment Grafana/semantic views. => environment_daily's
    parent_available_through is derived from environment_measurements, and the
    materialized_only=FALSE property of the env CAGGs is IRRELEVANT to Phase 1.

C2. [FACT] analytics.demand_intervals is a PLAIN TABLE, not a hypertable
    (Phase 2 §I wrongly listed it with a 7-day chunk + 7-day compression). It
    therefore has NO TimescaleDB retention or compression policy and grows
    unbounded (15-min resolution x per-PRIMARY_METER-asset + per-site). §E.

C3. [FACT] A native CAGG's materialization watermark is NOT a "real data
    exists through here" signal. When energy_measurements is stalled, the
    ca_energy_* refresh policy still runs on schedule and advances the
    materialization watermark across the stalled range (materialising zero
    rows for those buckets). So a CAGG watermark can sit AHEAD of real data.
    Consequence for Phase 1: a CAGG-fed child that advances its checkpoint to
    the CAGG watermark during an upstream stall will have "processed" an empty
    range; the later re-materialisation (once the source catches up, IF within
    the CAGG start_offset) is only re-picked-up by the trailing reconciliation
    pass. => reconcile_window for a CAGG-fed child MUST be >= that CAGG's
    start_offset. The Phase 2 design's "24h" 1-min reconcile window is too
    short (ca_energy_1min start_offset is 2 days).

C4. [REC] For the routing loaders (energy_measurements / normalized_points),
    pipeline_state.last_received_at is an INGEST time (platform_received_at),
    not a bucket time — it is not directly comparable to a child's bucket
    grain. For the two children that read those tables directly
    (demand_intervals, environment_daily), derive parent_available_through as
    max(<bucket/event time column>) FROM the parent table (a cheap indexed
    max), NOT from the parent's pipeline_state row. §B.

C5. [FACT] analytics.demand_intervals has TWO partial unique indexes
    (uq_demand_intervals_site_scope WHERE scope='SITE';
     uq_demand_intervals_asset_scope WHERE scope='ASSET'). A single
    "ON CONFLICT DO UPDATE" cannot target both. The status-guarded upsert must
    be written as two scope-branched INSERT statements (the finalisation loop
    already processes one scope per iteration, and the provisional demand_state
    block already branches SITE/ASSET — mirror that). §Plan / migration 210.

pipeline_state row names (reuse telemetry.pipeline_state; the 7 rows already
exist from migration 208 with last_received_at = NULL):
  energy_consumption_1min / _5min / _15min / _hourly / _daily / demand_intervals
  / environment_daily.

child_processed_through  == pipeline_state(child).last_received_at  (a BUCKET
time for these rows — documented divergence from the telemetry-tier rows, which
store an ingest time).

Per-run window (inside the existing advisory lock from 208):
  v_ckpt     = pipeline_state(child).last_received_at        -- NULL on first run
  v_parent   = <parent_available_through, per rule below>
  v_to       = LEAST( date_bin(<grain>, clock_timestamp()),  -- never a future bucket
                      v_parent,                               -- never past the parent
                      COALESCE(v_ckpt, <floor>) + v_max_catchup_window )  -- bounded
  v_from     = COALESCE(v_ckpt, v_to - <first-run floor>) - v_overlap
  IF v_to <= COALESCE(v_ckpt, v_from) THEN mark SUCCESS/NO_SOURCE_DATA, no-op, RETURN
  v_rows = <tier>.refresh_*(v_from, v_to)                     -- UNCHANGED calc fn
  -- advance is the LAST write in the same transaction:
  pipeline_state(child).last_received_at = v_to
  -- EXCEPTION -> FAILED + RAISE  => whole txn (incl. the advance) rolls back

first-run floor = the tier's CURRENT wall-clock lookback constant (30m / 30m /
2h / 2d / 8d / 3h / 8d) — used ONCE when v_ckpt is NULL, never again.

  Child                     | Parent(s)                        | parent_available_through (v_parent) RULE                                          | grain | schedule (KEEP) | max_catchup_window | overlap | reconcile_window
  ------------------------- | -------------------------------- | -------------------------------------------------------------------------------- | ----- | --------------- | ------------------ | ------- | ----------------
  energy_consumption_1min   | ca_energy_1min (CAGG)            | to_timestamp(cagg_watermark(ca_energy_1min))                                    | 1m    | 1 min           | 2 hours            | 2 min   | 2 days   (= ca_energy_1min start_offset, C3)
  energy_consumption_5min   | ca_energy_5min (CAGG)            | to_timestamp(cagg_watermark(ca_energy_5min))                                    | 5m    | 1 min           | 2 hours            | 10 min  | 7 days   (= ca_energy_5min start_offset)
  energy_consumption_15min  | energy_consumption_1min + _5min  | LEAST( cp('energy_consumption_1min'), cp('energy_consumption_5min') )            | 15m   | 5 min           | 6 hours            | 30 min  | 3 days

parent_available_through RULES, stated exactly (deliverable requirement):
  - Parent is a native CAGG (all materialized_only=TRUE here): v_parent =
    _timescaledb_functions.to_timestamp( watermark ) from
    _timescaledb_catalog.continuous_aggs_watermark joined by mat_hypertable_id
    from _timescaledb_catalog.continuous_agg. Wrap in a tiny helper
    analytics.cagg_available_through(regclass) RETURNS timestamptz so the
    wrappers never embed catalog spelunking. This is the materialisation
    frontier: buckets < it are authoritative; buckets >= it do not exist yet.
    It can sit AHEAD of real data after an outage (C3) -> that gap is the job
    of reconcile_window (= start_offset).
  - Parent is a persisted analytical table written by another watermark-driven
    child: v_parent = pipeline_state(parent_pipeline).last_received_at. That
    value IS "the parent child has durably processed through here" == "the
    parent table has authoritative rows through here". LEAST() over multiple
    such parents (15min has two).
  - Parent is a telemetry-tier SoT table whose own job checkpoints on INGEST
    time (energy_measurements, normalized_points, environment_measurements):
    v_parent = max(<bucket/event time column>) FROM the parent table (indexed
    max; a concurrent parent run mid-insert just yields a slightly stale value
    -> child processes slightly less -> safe). Do NOT use the parent's
    pipeline_state.last_received_at here (it is an ingest time, C4).
  - "last complete site-local day boundary" for the two daily tiers: a local
    day D is only eligible once now() (site-local) has passed
    D-end + a small grace; the daily refresh functions already compute
    local_day_end — intersect v_to with that.

Derivation of the numeric parameters ([INF] from grain + CAGG offsets +
conservatism; [UNK] staging durations — confirm via §H #4/#5 and tune):
  - max_catchup_window: enough that a plausible outage drains in a sane number
    of runs, small enough that one run stays well under max_runtime.
    1m tier @ 2h  -> 24h outage drains in 12 one-minute runs (~12 min).
    5m tier @ 2h  -> same; (moot — empty fleet).
    15m tier @ 6h -> 24h drains in 4 five-minute runs (~20 min); the cost
                     driver is the v_energy_semantic_rollup_15min recompute,
                     O(window) -> 6h keeps it bounded.
    hourly @ 2d   -> a week-long hourly outage drains in ~4 runs; reads the
                     small persisted 15min table, cheap.
    daily @ 8d    -> keep the current constant as the window; 8 rows/device.
    demand @ 3h   -> = today's lookback (behaviour unchanged until a gap); the
                     inner site x scope x interval loop is
                     ceil(window/15m) x scope-count x calculate_demand_window()
                     -> at 3h that is 12 x scope-count iterations. Do NOT
                     widen past ~6h without measuring (§G risk 3).
    environment_daily @ 8d -> as daily.
  - overlap: ~2 x grain (boundary-race + a just-closed bucket). 1m->2m,
    5m->10m, 15m->30m, 1h->2h, 1d->2d.
  - reconcile_window: for a CAGG-fed child = that CAGG's start_offset exactly
    (C3). For a persisted-table-fed child = >= sum of the upstream reconcile
    windows so a repaired hole propagates up (15min 3d > 1min 2d; hourly 10d;
    daily/env_daily 21d covers a month boundary + DST + upstream). demand 6h =
    the job-1077 replay-backoff ceiling (1h+2h+6h) — a late raw replay cannot
    land more than ~9h after the bucket, and demand's own finalisation grace
    covers the rest.

These 3 values per tier are NEW keys in each job's config JSONB
("max_catchup_window", "overlap", "reconcile_window"); the migration-208
validator (config.assert_analytical_lookback_job_config) already accepts
"max_catchup_window" and must be extended to accept "overlap" and
"reconcile_window" (positive finite intervals). "lookback" stays as the
first-run floor.

C. FAILURE ANALYSIS
=====================================================================

Assumes Phase 1 migrations (209 energy cascade + 210 demand + 211 env_daily +
212 reconciliation) all deployed; parameters from §B; and Phase 0 (207) so the
routing loaders self-drain.

  1. 15-MINUTE OUTAGE (ingest stops 15 min, then resumes)
     Routing loaders: 1-2 bounded runs close the gap (207). ca_energy_1min
     re-materialises the 15 min on its next 1-min refresh. energy_consumption_1min:
     outstanding = 15 min, v_max_catchup_window 2h -> drained in 1 run. 15min:
     v_parent = 1min checkpoint -> advances 1 run later. hourly/daily: within a
     bucket; caught on next run. NO permanent blank. No alert (below backlog
     thresholds). Recovery: < 5 min.

  2. 2-HOUR OUTAGE
     Routing: ~1 run (207 wrapper passes 2h). ca_energy_1min re-materialises
     (2h << 2d start_offset). energy_consumption_1min: outstanding 2h,
     v_max_catchup_window 2h -> 1 run. 15min: 1 run once 1min advances.
     hourly: 1 run. daily: within window. Recovery < ~10 min. Alert:
     source-watermark-not-advancing fired during the outage, auto-clears.

  3. 8-HOUR OUTAGE
     Routing: ~4 bounded runs (~4 min). ca_energy_1min re-materialises (8h < 2d).
     energy_consumption_1min: 8h / 2h = 4 one-minute runs (~4 min). 15min:
     8h / 6h = 2 five-minute runs. hourly: 1 run (8h < 2d window). daily: 1 run.
     Total pipeline caught up < ~20 min after ingest resumes. No permanent blank.

  4. 24-HOUR OUTAGE
     Routing: ~12 runs (~12 min). ca_energy_1min: 24h < 2d start_offset ->
     re-materialises automatically on schedule. energy_consumption_1min: 12
     one-minute runs. 15min: 4 runs. hourly: 1 run. daily: 1 run.
     Recovery < ~40 min, fully automatic, no operator backfill.
     Alert: source-watermark + recovery-runway warnings fire and auto-clear.

  5. BURST REPLAY AFTER NETWORK LOSS (e.g. gateway buffers 6h, dumps at once)
     raw_messages gets 6h of rows with a fresh received_at. Normalisation
     (205) + routing (207) drain it in bounded p_max_window steps -> no giant
     transaction. energy_measurements bucket_start values are the OLD event
     times. ca_energy_1min: the INSERTs into energy_measurements for those old
     buckets land inside its 2d start_offset -> the CAgg invalidation log picks
     them up -> next refresh re-materialises. energy_consumption_1min sees its
     v_parent (CAGG watermark) unchanged BUT its trailing reconcile pass
     (window 2d) re-runs refresh over [ckpt-2d, ckpt) and repopulates the
     now-materialised buckets. 15min/hourly/daily reconcile likewise, bottom-up.
     Recovery: forward drain for anything past the checkpoint + one
     reconciliation cycle for buckets below it. No permanent blank.

  6. CHILD FAILURE WHILE PARENT CONTINUES
     e.g. energy_consumption_15min job fails for 40 min while 1min keeps
     advancing. 15min checkpoint FROZEN (a failed run rolls back the advance).
     hourly/daily see 15min's frozen checkpoint as their v_parent and idle
     (NO_SOURCE_DATA, no false advance). On 15min recovery: outstanding =
     40 min + whatever 1min added; drained over bounded 6h-window runs.
     No data lost (bounded only by upstream retention). Alert: 15min
     consecutive_failures >= 3.

  7. CHILD FAILURE FOLLOWED BY PARENT RECOVERY  (the required scenario, §5)
     Parent available 09:00..18:00. Child checkpoint 09:00.
       run 1: 09:00 -> 11:00 (v_max_catchup_window 2h)  SUCCESS  ckpt = 11:00
       run 2: 11:00 -> 13:00  FAILS  -> txn rollback -> ckpt STAYS 11:00
       run 3: v_from = 11:00 - overlap ; v_to = LEAST(now_binned, v_parent,
              11:00 + 2h) = 13:00  -> RETRIES 11:00 -> 13:00 (NOT 13->15).
     Parent later advances to 20:00: run 3's v_to is still
     LEAST(..., 11:00 + 2h) = 13:00. The child cannot skip its own failed
     interval because v_to is anchored to v_ckpt + window, and v_ckpt only
     moves on success. [proven by test "cascade correctness" + "failure before
     checkpoint update".]

  8. INTERNAL HOLE  (09:00 OK, 10:00 FAILED-partial, 11:00 OK — hole below HWM)
     Can only arise from a partial write inside a slice or a late/config-driven
     source change below the checkpoint (contiguous oldest-first advance
     prevents a hole forming from ordinary forward runs). The per-tier trailing
     reconciliation job re-runs the tier's own refresh_*() over
     [checkpoint - reconcile_window, checkpoint) on a low cadence; the
     idempotent ON CONFLICT DO UPDATE repopulates 10:00; rows_changed is
     logged. Alert only if the same pipeline reports rows_changed > 0 on N
     consecutive reconcile runs, or a discrepancy older than reconcile_window.
     [proven by test "internal-hole reconciliation".]

  9. DATABASE RESTART (mid-slice)
     WAL recovery rolls back the in-flight slice transaction (refresh writes +
     the checkpoint advance together). Checkpoint unmoved. bgw_job_stat
     .consecutive_crashes increments; the job is rescheduled with backoff. Next
     run retries the identical bounded slice. No false advance, no manual step.

  10. WORKER TIMEOUT (run exceeds max_runtime 5m/10m)
      The TimescaleDB launcher cancels the worker; the statement (incl. the
      checkpoint advance) rolls back; retried after retry_period (5 min), up to
      max_retries (3), then waits for the next fixed slot. Because
      v_max_catchup_window bounds the slice, a correctly-sized run finishes
      well inside max_runtime; a run that still times out means
      v_max_catchup_window is too large for current scale -> tune the config
      value down (no code change). At most one bounded slice is lost per
      timeout; it is retried.

Where the CAGG materialisation watermark LIMITS downstream processing:
  Only energy_consumption_1min and energy_consumption_5min take a CAGG as
  parent. Their v_to is capped at the CAGG watermark, so they can never process
  a bucket the refresh has not yet materialised. Every tier above them
  (15min/hourly/daily) is capped by the PERSISTED child checkpoint of the tier
  below — the CAGG watermark does not propagate directly past the 1min/5min
  tables.

After an upstream outage:
  - outage <= CAGG start_offset (2d for 1min, 7d for 5min): the CAgg
    invalidation log + next scheduled refresh re-materialise the range
    automatically; the child's trailing reconciliation (window = start_offset)
    re-derives from the re-materialised rows. Fully automatic.
  - outage > CAGG start_offset: the refresh policy will NOT revisit that range.
    A one-time manual `CALL refresh_continuous_aggregate('telemetry.ca_energy_1min',
    <old_start>, <end>)` is required, after which the child's bounded catch-up
    (or a manually widened reconcile) drains Tier 5. This is standard
    TimescaleDB operation; Phase 1 does not change it and MUST NOT silently
    widen start_offset (that raises every-cycle refresh cost — see §F/§G).

Can the CAGG refresh itself create a downstream gap? [INF] Yes, in two ways:
  (a) if `policy_refresh_continuous_aggregate` for ca_energy_1min fails/stalls
      (it has max_runtime = 0), the watermark stops advancing and every child
      above it correctly idles — no false data, but a stall. Detect via
      cagg-refresh-lag (§G obs).
  (b) the "materialised-empty-then-backfilled" case (C3) — closed by
      reconcile_window = start_offset.

Rationale for the flagged items:
  - raw_messages 48h -> 7d: this is the SINGLE cap on automatic recovery for
    the entire pipeline (nothing downstream can self-heal an outage older than
    it — every Phase-1 tier ultimately roots here). 48h did not comfortably
    cover the ~15h incident found hours later; 7d covers "Friday stall found
    Monday". COST: highest-volume table — size the delta first (§H #6). If
    storage is the blocker, 96h is the floor. This directly enlarges what
    Phase 1's self-healing can actually recover.
  - normalized_points compress_after 1d -> 7d: it is upsert-updated by the
    normalisation catch-up path AND read directly by demand finalisation. At
    1d, routine catch-up and demand backfill fight chunk decompression. Align
    to energy_measurements (7d). (7-day chunks mean real exposure is smaller
    than "1 day" implies, but it is still tighter than every sibling for no
    benefit.) [UNK] confirm current staging chunks a backfill would touch (§H #6).
  - demand_intervals no policy (C2): 15-min x per-asset + per-site, plain
    table, ever-growing, uncompressed. Set an explicit 3-year retention (or
    convert to a hypertable). Not urgent but real. [UNK] current size (§H #8).
  - capture_bucket_samples: unbounded plain working table on the hot
    normalisation path. Add an app-level prune (delete NORMALIZED rows older
    than a few days; keep unresolved longer). P-H1, not Phase 1.

RECOVERY-CEILING MATRIX (publish in docs/platform-manual/11-aggregation.md):
  max_auto_recovery(child) = MIN over its dependency path of { every upstream
  table retention, every native-CAGG start_offset }. For the whole energy
  path today: raw_messages 48h  <  ca_energy_1min start_offset 2d  <
  everything else. Raising raw_messages to 7d moves the MIN to the CAGG
  start_offset (2d); only THEN is widening any start_offset worthwhile.

G. RISKS STILL REMAINING  (actively hunted — job-1000-class and adjacent)
=====================================================================

R1. [job-1000 class] ca_energy_1min's `policy_refresh_continuous_aggregate`
    has max_runtime = 0 (unlimited). A very large invalidation backlog (huge
    burst spanning much of the 2-day start_offset) could make one refresh run
    long and contend. TimescaleDB refreshes are internally bounded by
    start_offset, so this is lower risk than the custom jobs were, and a
    policy refresh cannot "not progress" the way job 1000 did — but it CAN
    lag. Phase 1 does not (and should not) change CAGG policies. Mitigation:
    the cagg-refresh-lag alert (§Obs). Flag for a separate policy review only
    if staging shows it lagging.

R2. [job-1000 class, PARTIALLY OPEN] The routing loaders 1001/1012 got
    p_max_window in 207 and the SCHEDULED wrapper passes a bounded 2h — so an
    unattended stall self-drains. But `run_normalization_job` (job 1000
    itself) STILL passes NULL (its wrapper was deliberately not changed by
    205/207). A fresh unattended multi-hour normalisation stall still requires
    an operator to run bounded `load_normalized_points_incremental(...,
    '30 minutes')` calls. This is the ORIGINAL failure's residue. RECOMMEND: a
    tiny follow-up making run_normalization_job pass a bounded max_window like
    the routing jobs. NOT Phase 1 scope, but it is the closest remaining
    job-1000-shaped hole.

R3. [demand loop] refresh_demand_analytics's inner loop is
    ceil(p_lookback / demand_interval_seconds) + 2 iterations x #sites x
    #scopes, each calling calculate_demand_window(). If Phase 1 ever lets
    demand's max_catchup_window grow large during recovery, this loop and its
    per-iteration function calls scale linearly and could exceed max_runtime.
    Mitigation: keep demand max_catchup_window <= ~6h; the loop is per-run
    bounded by it. [UNK] measure on staging (§H #5).

R4. [CAGG watermark ahead of real data, C3] If reconcile_window <
    (source-stall duration + source->CAGG re-materialisation latency), a
    bucket the child "processed" while the CAGG was empty is never revisited
    -> permanent hole. Mitigation: reconcile_window = CAGG start_offset
    exactly (§B). Residual: an outage LONGER than start_offset needs the
    manual refresh_continuous_aggregate + a manually widened reconcile — same
    as any TimescaleDB deployment; documented, alerted (gap-older-than-window).

R5. [retention cliff] normalized_points / energy_measurements 90d retention vs
    a >90d undetected stall = "source deleted before repair". Bounded to
    irrelevance today by raw_messages 48h (can't recover past that anyway) —
    but if raw_messages retention is raised (§E) without also widening the
    detection/alerting on source-watermark-not-advancing, a long quiet stall
    could still burn the runway. Mitigation: the recovery-runway alert
    (oldest backlog vs MIN upstream retention on path).

R6. [P-H3, OPEN] A late job-1077 raw replay landing AFTER
    energy_measurements' per-bucket correction_deadline leaves a STALE
    register snapshot in energy_measurements (the UPDATE branch is
    deadline-guarded; only the INSERT branch is unconditional). Phase 1's
    reconciliation re-derives energy_consumption_* from energy_measurements —
    so it faithfully re-derives from the STALE row. Phase 1 does NOT fix this.
    It is its own sub-phase (relax the correction_deadline guard for a bounded
    window matching the 1077 backoff ceiling, OR have 1077 recovery re-drive
    the affected routing window). Flag prominently; keep out of Phase 1.

R7. [pipeline_state RUNNING not durably observable] Carried from 0b. With one
    transaction per run and no intermediate COMMIT, RUNNING/backlog is not
    visible to another session and a timeout loses the whole run (retried).
    ACCEPTABLE for Phase 1 because each run is ONE bounded slice
    (max_catchup_window) — a timeout just retries that slice. If staging shows
    runs approaching max_runtime, a Phase 1.5 option is a job-1077-style
    per-slice COMMIT loop inside one run (advance the checkpoint atomically
    with each committed slice) — makes RUNNING durable and caps loss at one
    slice. Not needed now; noted.

R8. [capture_bucket_samples unbounded, P-H1] Still open. Not Phase 1.

R9. [demand two partial unique indexes, C5] Not a runtime risk — an
    implementation constraint. The status-guarded upsert MUST be two
    scope-branched statements; a single ON CONFLICT DO UPDATE would silently
    only ever fix one scope.

R10.[5min tier, structurally empty] refresh_energy_consumption_5min only
    processes capture_interval_seconds = 300 sites; the whole fleet is 60.
    [UNK — confirm on staging §H #10] The 5min tier MUST still become
    watermark-driven (so a future 300s site works correctly) but every test /
    alert / dashboard must treat "energy_consumption_5min NO_SOURCE_DATA
    forever" as EXPECTED, and the 15min tier's
    LEAST(cp(1min), cp(5min)) must keep advancing via the 5min tier's no-op
    SUCCESS runs (which DO set last_received_at = v_to). Verified in the local
    run: a no-op wrapper run sets NO_SOURCE_DATA and (in Phase 1) will still
    advance the checkpoint — so cp(5min) tracks the CAGG watermark and does
    not stall the 15min LEAST().
