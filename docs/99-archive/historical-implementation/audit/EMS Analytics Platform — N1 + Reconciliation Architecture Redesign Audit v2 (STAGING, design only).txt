1. EXECUTIVE DECISION SUMMARY
===============================================================================

1.1  N1 — GO.  [VERIFIED defect; RECOMMENDATION for the fix]
     telemetry.run_normalization_job calls the loader with ONE argument, so
     p_max_window = NULL, so the loader's forward endpoint is
     max(raw_messages.received_at) with no cap, processed in ONE transaction.
     This is the exact 2026-08-26 stall mechanism, one hop upstream of where
     migration 207 fixed the routing jobs. The loader already has p_max_window
     (migration 205) and the full advisory-lock / pipeline_state /
     EXCEPTION->FAILED->RAISE contract. The fix is the migration-207 wrapper
     pattern applied to run_normalization_job: derive v_max_window from
     config.max_window (default provisional 2h), ALWAYS pass it, merge the key
     via alter_job. No calculation-semantic change. Manual NULL/unrestricted
     rebuild path (postgres/maintenance/45_rebuild_normalized_history.sql)
     unaffected. Own tiny migration.

1.2  RECONCILIATION — GO, with a REVISED architecture.  [RECOMMENDATION]
     A truthful, already-persisted completeness signal exists for every tier
     (source_sample_count on 1min/5min from the CAGG's count; source_interval_count
     on 15min/hourly/daily = count of parent rows). Reconciliation compares the
     child's stored fingerprint against the LIVE parent per (device, bucket) and
     re-drives only mismatches. An empty parent range is left alone — never
     "healthy because the watermark is ahead", because the detector never reads
     the watermark.
     CHANGE FROM v1: the automated reconcile jobs DO NOT call
     refresh_continuous_aggregate(). PROBE (§8) proved that call is rejected
     ("cannot run inside a transaction block") from BOTH an explicit
     transaction AND any plpgsql BEGIN...EXCEPTION block (a subtransaction).
     Instead: set reconcile_window(1min)=2d and reconcile_window(5min)=7d
     EQUAL TO each CAGG's automatic refresh start_offset, so the CAGG's own
     policy keeps it current across the whole reconcile window and the detector
     always compares two fresh values. Backfill OLDER than the start_offset is
     surfaced by v_pipeline_health as an ALERT (not auto-repaired); the operator
     remedy is a one-off top-level  CALL refresh_continuous_aggregate(...)  then
     the next reconcile pass repairs the children. This removes an entire class
     of concurrency/locking/legality risk from the automated path.

1.3  N2 — energy_consumption_15min reconcile_window 3d is INSUFFICIENT.  [VERIFIED
     chain]  15min = rollup of energy_consumption_1min UNION ALL
     energy_consumption_5min; ca_energy_5min start_offset = 7d.
     RECOMMENDATION: 8 days (7d + 1d margin), tied to the ca_energy_5min
     start_offset. One config value in the reconciliation migration.

1.4  DEMAND max_catchup_window — KEEP 6h; do NOT raise to 12h.  [RECOMMENDATION]
     max_catchup_window (forward bounded catch-up per run) and reconcile_window
     (trailing repair horizon) are DIFFERENT purposes and must not be conflated.
     6h forward is fine (the incident it guards against is a stall, and 6h/run
     drains a day in 4 runs). The demand REPAIR horizon question is
     reconcile_window, which is currently also 6h; §9 recommends 12h for the
     RECONCILE window only, pending a staging cost read (§13). No change to
     max_catchup_window.

1.5  DECOMPOSITION — RE-EVALUATED, still three migrations but re-scoped:
       212  N1 normalization bounded forward window (wrapper + job config).
       213  analytics.pipeline_reconciliation_log + per-tier reconcile
            procedures + reconcile jobs + the N2 15min reconcile_window value
            + the demand reconcile_window value.
       214  analytics.v_pipeline_health (read-only view).
     213 and 214 could ship together; keeping 214 separate lets the health view
     land even if 213 needs another iteration. N1 (212) is independent of both.
     Retention/compression/CAGG-policy/Grafana/normalization-calc/routing
     changes are OUT of scope for all three.

1.6  NO-GO conditions (§20) are NOT triggered by anything in the repo or local
     DB. Two remain gated on staging reads (§13): the N1 max_window default
     (2h vs 1h) and the demand reconcile cost (6h vs 12h). One remaining local
     verification (a real one-off job execution that materialises a tiny CAGG
     window) is needed to close the "CALL refresh_continuous_aggregate from a
     scheduled job action" question to 100% — but the revised design (1.2) does
     NOT depend on it, so it is a nice-to-have, not a blocker.

2.1  EXACT CURRENT WRAPPER CALL SIGNATURE.  [VERIFIED]
     telemetry.run_normalization_job(IN job_id integer, IN config jsonb)
       LANGUAGE plpgsql  (no SET search_path; SECURITY INVOKER)
       DECLARE v_overlap INTERVAL := INTERVAL '15 minutes';
       - reads config->>'overlap' if present and non-blank;
       - RAISE EXCEPTION if v_overlap < 0;
       - CALL telemetry.load_normalized_points_incremental(v_overlap);   <-- ONE arg
       - RAISE NOTICE start/complete (cosmetic).
     NO advisory lock, NO pipeline_state handling, NO EXCEPTION block in the
     WRAPPER — it delegates entirely to the loader.

2.2  EXACT DEFAULT SEMANTICS OF p_max_window.  [VERIFIED]
     telemetry.load_normalized_points_incremental(
        IN p_overlap    interval DEFAULT '00:05:00',
        IN p_max_window interval DEFAULT NULL)
     Guard: IF p_max_window IS NOT NULL AND p_max_window <= 0 THEN RAISE.
     A one-argument CALL => p_max_window resolves to DEFAULT NULL => the cap
     below is skipped.

2.3  EXACT v_window_start / v_window_end.  [VERIFIED]
       SELECT max(received_at) INTO v_window_end FROM telemetry.raw_messages;
       IF v_window_end IS NULL -> pipeline_state NO_SOURCE_DATA + RETURN.
       -- migration-205 cap (ONLY when a caller passes p_max_window):
       IF p_max_window IS NOT NULL AND v_previous_checkpoint IS NOT NULL THEN
           v_window_end := LEAST(v_window_end, v_previous_checkpoint + p_max_window);
       END IF;
       -- dynamic trailing overlap from enabled capture policies:
       v_dynamic_overlap := make_interval(secs => GREATEST(
           COALESCE(max(capture_interval_seconds + late_arrival_tolerance_seconds), 0),
           extract(epoch FROM p_overlap)::int))
         over enabled config.telemetry_capture_policies whose effective window +
         (capture_interval + late_arrival_tolerance) still reaches the previous
         checkpoint (migration 129 effective-policy lookback);
       v_window_start := CASE
           WHEN v_previous_checkpoint IS NULL
             THEN GREATEST(v_window_end - INTERVAL '48 hours',
                           COALESCE((SELECT min(received_at) - INTERVAL '1 microsecond'
                                     FROM telemetry.raw_messages), v_window_end))
           ELSE v_previous_checkpoint - v_dynamic_overlap
         END;
     => FIRST run is inherently bounded to 48h. Every SUBSEQUENT run's forward
        edge is max(raw_messages.received_at) unless p_max_window is supplied.

2.4  EXACT TRANSACTION BOUNDARY.  [VERIFIED]  ONE transaction for the whole
     loader body: CREATE TEMP TABLE ... ON COMMIT DROP (x4), the
     capture_bucket_samples INSERT ... ON CONFLICT DO NOTHING, the
     normalized_points INSERT ... ON CONFLICT (event_time,device_id,
     logical_point_id) DO UPDATE (provenance-only, newer-wins), the
     device_point_state / device_telemetry_state upserts, and the terminal
     pipeline_state UPDATE (last_received_at = v_window_end, SUCCESS). NO
     intermediate COMMIT. A max_runtime cancellation rolls the entire run back
     -> zero durable progress -> the retry faces an equal-or-wider window.

2.5  EXISTING ADVISORY-LOCK BEHAVIOUR.  [VERIFIED]  In the LOADER:
       pg_try_advisory_xact_lock(hashtextextended(
         'telemetry.load_normalized_points_incremental', 0))
       -> on miss: pipeline_state SET last_status='SKIPPED_LOCKED' + RETURN.
     The SAME key is also taken (coordination, not a call) by
     ddl/126/127/128/129 (frequency recovery / legacy recovery), so those
     cannot run concurrently with the loader.

2.6  EXISTING pipeline_state BEHAVIOUR.  [VERIFIED]  In the LOADER:
     v_previous_checkpoint read FOR UPDATE from
     telemetry.pipeline_state WHERE pipeline_name='normalized_points';
     RUNNING transition; NO_SOURCE_DATA when max(received_at) IS NULL;
     on success -> last_received_at = v_window_end, last_inserted_rows = v_rows
     (GET DIAGNOSTICS from the normalized_points upsert), SUCCESS.

2.7  EXISTING FAILURE / ROLLBACK BEHAVIOUR.  [VERIFIED]  In the LOADER:
       EXCEPTION WHEN OTHERS THEN
         UPDATE telemetry.pipeline_state SET last_status='FAILED',
           last_error = SQLSTATE||': '||SQLERRM, ... ;
         RAISE;
     Because the whole body is one transaction, RAISE aborts it -> the FAILED
     write AND every target write AND the checkpoint all roll back. Net effect
     of a failed/cancelled run: nothing moved.

2.8  EXISTING CONFIG VALIDATION PATH.  [VERIFIED]  NONE. Job 1000 has no
     check_config (neither do 1001/1012 — only the analytics tier got a

3.2  WRAPPER BODY.  [RECOMMENDATION — mirrors deployed run_energy_routing_job]
       DECLARE
         v_overlap    INTERVAL := INTERVAL '15 minutes';
         v_max_window INTERVAL := INTERVAL '2 hours';         -- provisional; §4
       BEGIN
         IF config ? 'overlap'    THEN v_overlap    := (config->>'overlap')::INTERVAL;    END IF;
         IF config ? 'max_window' THEN v_max_window := (config->>'max_window')::INTERVAL; END IF;
         IF v_overlap    <  INTERVAL '0 seconds'  THEN RAISE EXCEPTION 'normalization overlap cannot be negative: %', v_overlap; END IF;
         IF v_max_window <= INTERVAL '0 seconds'  THEN RAISE EXCEPTION 'normalization max_window must be positive: %', v_max_window; END IF;
         CALL telemetry.load_normalized_points_incremental(v_overlap, v_max_window);   -- TWO args, always bounded
       END;
     Re-assert ALTER PROCEDURE ... OWNER TO ems_admin and a COMMENT documenting
     "Migration 212: bounded forward window via config.max_window (default 2h),
     mirroring migration 207 for the routing wrappers; a bare / explicit-NULL
     manual CALL of the loader remains unrestricted."

3.3  JOB CONFIG.  [RECOMMENDATION]
       DO $cfg$ DECLARE v_job_id INT; BEGIN
         FOR v_job_id IN SELECT job_id FROM timescaledb_information.jobs
           WHERE proc_schema='telemetry' AND proc_name='run_normalization_job'
         LOOP
           PERFORM alter_job(v_job_id, config =>
             COALESCE(config,'{}'::jsonb) || jsonb_build_object('max_window','2 hours'));
           RAISE NOTICE 'Migration 212: job % config += max_window=2 hours', v_job_id;
         END LOOP;
       END $cfg$;

3.4  STEADY STATE.  [INFERRED]  Unchanged. LEAST(max(received_at),
     checkpoint + 2h) = max(received_at) whenever the checkpoint is current.
     Same rows, same latency, same cadence. (Identical LEAST(...) construct
     proven benign by migrations 205 and 207.)

3.5  RECOVERY.  [INFERRED]  After an N-hour stall, successive 1-minute runs each
     advance the checkpoint by <= 2h and durably commit. A 24h backlog drains
     in ~12 runs (~12 min wall). No operator action.

3.6  FAILURE / ROLLBACK.  [VERIFIED structure]  Identical to today (one txn;
     advisory lock; SUCCESS writes last_received_at last; EXCEPTION -> FAILED ->
     RAISE rolls the whole run incl. the checkpoint back). A cancelled capped
     run leaves the checkpoint where it was; the retry reprocesses the same
     <= 2h window, now far more likely to fit in max_runtime 5m.

3.7  MIGRATION ROLLBACK.  [RECOMMENDATION]  CREATE OR REPLACE the prior wrapper
     body + alter_job to drop the max_window key (or leave it inert — the
     reverted wrapper ignores unknown keys; dropping is cleaner).

6. RECONCILIATION INVARIANTS  (the mechanism MUST enforce all of these)
===============================================================================

INV-A  MUST NOT write telemetry.pipeline_state.last_received_at.  [enforced by
       construction + an automated test that greps every deployed reconcile_*
       body for that assignment and fails if present.]

INV-B  MUST NOT treat a CAGG materialisation watermark as proof of source
       completeness. The detector compares BUCKET-LEVEL row/count evidence, and
       never reads cagg_available_through / continuous_aggs_watermark for the
       repair decision. (cagg_available_through IS used in v_pipeline_health for
       the OVERSHOOT_RISK signal — that is observation, not repair.)

INV-C  CAGG-fed tiers (1min, 5min) use source_sample_count vs
       ca_energy_{1,5}min.sample_count per (device, bucket).

INV-D  If the CAGG can be stale because a backfill landed OUTSIDE its automatic
       start_offset: reconcile_window is SET EQUAL TO the start_offset so the
       automatic policy keeps the CAGG current across the entire reconcile
       window (auto-repair). A backfill older than start_offset is DETECTED by
       v_pipeline_health (a bucket-count deficit vs energy_measurements directly,
       beyond the window) and ALERTED — NOT silently declared healthy and NOT
       auto-repaired by the job. (Option "reconcile calls refresh_continuous_aggregate"
       is REJECTED — see §8.)

INV-E  Idempotent: two back-to-back reconcile runs — the second finds every
       coarse bucket healthy (src == chi) and performs 0 refresh_* calls,
       logs outcome='HEALTHY', rows_repaired=0.

INV-F  MUST NOT double-apply demand_state: the demand reconcile calls
       refresh_demand_analytics with p_now = clock_timestamp() and
       p_finalize_from/to bounding ONLY the historical finalisation loop. The
       live demand_state block stays keyed to p_now (current interval only).
       [VERIFIED this is exactly the 210 re-finalisation path proven by test
       T-Refin-E / T-DS.]

INV-G  MUST NOT turn NO_DATA/INCOMPLETE into a misleading VALID merely because a
       child row exists. For demand this is the 210 guard (quality only improves
       via calculate_demand_window's own lattice; VALID frozen). For
       environment_daily a re-run of refresh_environment_daily recomputes
       honestly from whatever source is present (no quality lattice; a thin day
       stays thin). For energy tiers the child's quality columns come from
       refresh_* itself; the reconcile does not re-judge them.

INV-H  MUST distinguish (the truth table, §7):
       MISSING_CHILD | STALE_COUNT | QUALITY_REGRESSION | EXPECTED_NO_DATA |
       LATE_SOURCE | PARENT_UNAVAILABLE | CAGG_STALE_BEYOND_HORIZON |
       OUTSIDE_REPAIR_HORIZON | HEALTHY.

INV-I  MUST NOT move any production watermark backwards. (Reconcile never writes
       last_received_at at all — INV-A — so this is trivially satisfied; stated
       explicitly because the old design's "reconcile over [cp - rw, cp)" could
       be misread as touching cp.)

INV-J  MUST be bounded: window = [cp - reconcile_window(tier), cp), entirely at
       or below the HWM; coarse detector buckets capped; a hard cap N_max on
       refresh_* sub-window invocations per run (outcome='PARTIAL' beyond it;
       the next cadence continues).

INV-K  A reconcile FAILURE is observable (pipeline_reconciliation_log row with
       outcome='FAILED' + SQLSTATE, plus job_stats.consecutive_failures) and
       CANNOT corrupt or advance the normal pipeline checkpoint (reconcile owns
       no checkpoint; its only pipeline_state touch is optional advisory
       metadata last_reconcile_at/rows, whose rollback loses nothing).

7.1  EXPECTED PARENT FINGERPRINT PER RECONCILE BUCKET.  [VERIFIED basis]
     The grain of comparison is dictated by the child PK and the CAGG GROUP BY:

     reconcile operates only on closed buckets.

8. CAGG REFRESH FEASIBILITY  (local read-only-equivalent probes this session)
===============================================================================

8.1  refresh_continuous_aggregate is public.refresh_continuous_aggregate,
     prokind='p' (PROCEDURE), signature
     (continuous_aggregate regclass, window_start "any", window_end "any",
      force boolean, options jsonb).  [VERIFIED]

8.2  PROBE 1 — explicit transaction block:
       BEGIN;
       CALL refresh_continuous_aggregate('telemetry.ca_energy_1min',
            TIMESTAMPTZ '2000-01-01 00:00:00+00', TIMESTAMPTZ '2000-01-01 00:00:00+00');
       ROLLBACK;
     RESULT: ERROR: refresh_continuous_aggregate() cannot run inside a
             transaction block.  [VERIFIED — nothing materialised.]

8.3  PROBE 2 — inside a plpgsql BEGIN...EXCEPTION block (a SUBTRANSACTION):
       DO $$ BEGIN
         CALL refresh_continuous_aggregate('telemetry.ca_energy_1min', <ts>, <ts>);
       EXCEPTION WHEN OTHERS THEN RAISE NOTICE 'caught: %', SQLERRM;
       END $$;
     RESULT: NOTICE: caught: refresh_continuous_aggregate() cannot run inside a
             transaction block.  [VERIFIED]
     => a plpgsql EXCEPTION handler establishes a subtransaction, which the
        guard rejects. The reconcile procedure CANNOT call
        refresh_continuous_aggregate from inside ANY BEGIN...EXCEPTION block.

8.4  PROBE 3 — plain DO block, NO exception handler, autocommit, degenerate
     window:
       DO $$ BEGIN
         CALL refresh_continuous_aggregate('telemetry.ca_energy_1min', <ts>, <ts>);
       END $$;
     RESULT: got PAST the transaction-block guard to argument validation:
             ERROR: refresh window too small ... must cover at least one bucket.
     [VERIFIED — no materialisation; validation rejected the zero-width window.]
     => a plain plpgsql block (no EXCEPTION handler), invoked via top-level
        CALL / DO, is NOT itself a "transaction block" for this guard. The call
        is LEGAL from that context.

8.5  CONCLUSION.  [VERIFIED for the local DB, TSDB 2.29.2]
     CALL refresh_continuous_aggregate(...) is permitted from a plpgsql
     procedure body ONLY when:
       (i)  no explicit transaction is open (autocommit / job-runner context), AND
       (ii) it is NOT inside a plpgsql BEGIN...EXCEPTION subtransaction, AND
       (iii) it is not called from a plain FUNCTION (functions are atomic).
     [INFERRED, high confidence, consistent with the TimescaleDB 2.x
      documented "custom job that refreshes a CAGG" pattern] a TimescaleDB
      scheduled-job ACTION procedure satisfies (i) (the job runner permits
      transaction control in the action proc). NOT independently confirmed by a
      real job execution this pass (that would materialise a window).
     [UNKNOWN — needs a real one-off job execution] absolute confirmation in
      THIS deployment's job-runner context. Safest next verification step:
      register a THROWAWAY job whose action proc does exactly
        CALL public.refresh_continuous_aggregate('telemetry.ca_energy_1min',
             now() - INTERVAL '20 minutes', now() - INTERVAL '5 minutes');
      run it once via  CALL run_job(<id>);  inspect; then  SELECT delete_job(<id>);
      This materialises a ~15-minute window that is idempotent with the existing
      automatic policy (no data change of consequence). Requires explicit
      authorisation because it writes.

8.6  DESIGN CONSEQUENCE — REJECT refresh_continuous_aggregate IN THE AUTOMATED
     RECONCILE PATH.  [RECOMMENDATION]
     Reasons:
       - §8.3: it cannot coexist with the BEGIN...EXCEPTION error-capture the
         reconcile proc needs for INV-K. Restructuring around it (CAGG refresh
         as a bare top-level statement, then a separate exception-guarded block)
         is possible but fragile.
       - Concurrency: two reconcile jobs, or the automatic CAGG refresh policy
         and a reconcile, both calling refresh_continuous_aggregate on the same
         CAGG can serialise on the CAGG's internal invalidation-log locks and
         inflate runtime; an advisory lock on the CAGG name would be an extra
         moving part.
       - Cost: [UNKNOWN] a bounded refresh over 2d/7d at staging scale (§13).
     Instead: set reconcile_window(1min) = ca_energy_1min start_offset = 2d and
     reconcile_window(5min) = ca_energy_5min start_offset = 7d. The AUTOMATIC
     refresh policy (every 1min / 5min, covering exactly that trailing window)
     keeps the CAGG current across the whole reconcile window with no help from
     the reconcile job. The detector then always compares two fresh values.
     Backfill OLDER than the start_offset is NOT auto-repaired — it is an
     ALERT in v_pipeline_health (a direct energy_measurements count vs child
     count beyond the window) + a documented one-off operator remedy
     (top-level CALL refresh_continuous_aggregate, then next reconcile).

8.7  IF §13 later shows staging routinely receives backfill older than 2d/7d
     (job-1077 replay, or bulk corrections), REVISIT: either widen the reconcile
     window (and accept a manual/top-level CAGG refresh step run by a SEPARATE
     tiny job that does ONLY the CALL, no exception handler, no detector), or
     accept the alert-only degraded mode (NO-GO NG-R1, §20). Do not fold that
     into 213 now.

9. RECONCILIATION HORIZON ANALYSIS
===============================================================================

reconcile_window(P) := the trailing repair horizon = "how old a sub-watermark
hole can be and still self-repair". Distinct from max_catchup_window (the
FORWARD bounded slice per normal run). They are NOT interchangeable.

  tier                      driver of the horizon                              value  cur.   verdict
  ------------------------- ------------------------------------------------ ------ ------ -------------------
  energy_consumption_1min   ca_energy_1min automatic refresh start_offset      2d    2d    KEEP  [VERIFIED offset]
  energy_consumption_5min   ca_energy_5min automatic refresh start_offset      7d    7d    KEEP  [VERIFIED offset]
  energy_consumption_15min  max(reconcile(1min)=2d, reconcile(5min)=7d) + 1d   8d    3d    RAISE 3d->8d  (N2)
  energy_consumption_hourly >= reconcile(15min)=8d ; DST/month margin          10d   10d   KEEP
  energy_consumption_daily  >= reconcile(15min)=8d ; DST/month margin          21d   21d   KEEP
  demand_intervals          late source into energy_measurements/normalized_   12d?  6h    see 9.1
                            points can be corrected by the routing/normali-
                            zation overlap up to ~2d back; job-1077 failed-
                            raw replay backoff ceiling is 1h+2h+6h ~ 9h
  environment_daily         capture correction deadline (<= ~capture_interval  35d   35d   KEEP
                            + late_arrival_tolerance, canonical 16 min; CHECK
                            ceiling 24h) + operational slack; source retention
                            1y

9.1  DEMAND reconcile_window — 6h vs 12h.  [RECOMMENDATION: 12h, pending §13.]
     - The job-1077 backoff ceiling (1h+2h+6h) is where 210 set 6h. That covers
       a FAILED raw message replayed late.
     - It does NOT cover a raw message that was merely LATE (not failed) and
       normalised/routed into energy_measurements 1-2 days after its event time
       — that path has no fixed ceiling but is bounded in practice by the
       routing/normalization dynamic overlap (which itself scales with capture
       policy late_arrival_tolerance).
     - Demand re-finalisation is CHEAP: the 210 status-guarded upsert skips
       VALID rows entirely; the loop is bounded by
       v_max_n = ceil(reconcile_window / demand_interval_seconds) + 2.
       At 12h / 900s that is 50 iterations per (site x scope) — still small.
     - RECOMMENDATION: 12h, unless §13 O-D2 shows a 12h demand reconcile for the
       busiest site costs > ~2-3 min, in which case KEEP 6h and accept that a
       demand hole aged 6h..~2d is alert-only.
     - max_catchup_window (forward) STAYS 6h — unrelated purpose, no evidence to
       change it.

9.2  15min = 8d — VERIFICATION.  [VERIFIED chain -> RECOMMENDATION]
     energy_consumption_15min consumes energy_consumption_1min UNION ALL
     energy_consumption_5min. A late source correction reaches
     energy_consumption_5min via ca_energy_5min up to that CAGG's start_offset
     = 7 DAYS. When the 5min reconcile repairs a 5min row 6 days old, the 15min
     reconcile must revisit that 15-min bucket. With a 3-day 15min
     reconcile_window it never does -> a 15min hole older than 3 days persists.
     Therefore 15min reconcile_window MUST be >= 7d. 8d = 7d + 1d margin, tied
     to the ca_energy_5min start_offset (an UPSTREAM RECOVERY BOUNDARY), not an
     arbitrary number. Cadence stays slow (every 6h). ACCEPT 8d.

9.3  All reconcile_windows are well inside their tiers' source retention
     (energy_measurements 90d; environment_measurements 1y) [VERIFIED], so
     ground truth is always available for a repair within the window.

===============================================================================
10. DEMAND-SPECIFIC SEMANTICS  (why demand != the energy cascade)
===============================================================================

10.1 NO COUNT FINGERPRINT. demand_intervals has quality_status + observed/
     expected_observations + coverage_percent + finalized_at, NOT a
     "source_sample_count" the reconcile can diff against a parent count. The
     detector for demand IS the recompute: run refresh_demand_analytics over
     the trailing window; GET DIAGNOSTICS tells you how many rows it changed.

10.2 TWO PARTIAL UNIQUE INDEXES. A generic ON CONFLICT cannot target them.
     refresh_demand_analytics already contains the correct scope-branched
     upserts (SITE arbiter WHERE scope_type='SITE'; ASSET arbiter WHERE
     scope_type='ASSET'). The reconcile MUST call refresh_demand_analytics and
     MUST NOT write its own INSERT/ON CONFLICT. [VERIFIED — this is the 210 code.]

10.3 QUALITY LATTICE / VALID FREEZE. The 210 guard
     (quality_status <> 'VALID' AND ... IS DISTINCT FROM ...) means:
     reconcile can only IMPROVE a non-VALID row (per calculate_demand_window's
     own rules) and can NEVER regress a VALID row. INV-G is satisfied by
     reusing this code, not by adding logic.

10.4 demand_state. The live accumulator must not be replayed historically.
     refresh_demand_analytics(p_now, lookback, p_finalize_from, p_finalize_to):
     the demand_state block is keyed to p_now = clock_timestamp(); the
     p_finalize_* args bound ONLY the historical demand_intervals loop. A
     reconcile over an old window therefore updates demand_state for the CURRENT
     interval only — proven by 210 test T-DS. INV-F satisfied by construction.

10.5 SITE-LOCAL INTERVALS + PER-ENTITY GAP. resolve_demand_interval produces
     site-local-aligned 15/30-min buckets. The parent-availability scalar
     (LEAST(max(em.bucket_start), max(np.event_time))) cannot see a single
     site's stall. The reconcile's recompute-is-detector approach handles this:
     it re-runs every (site, scope) in the window; a site whose source arrived
     late gets a materially different (better) result -> DO UPDATE fires.

10.6 => demand reconcile = a THIN wrapper that (a) reads cp (never writes it),
     (b) CALL refresh_demand_analytics(clock_timestamp(), lookback,
     cp - reconcile_window, cp), (c) GET DIAGNOSTICS -> rows_repaired,
     (d) writes one pipeline_reconciliation_log row. No detector loop, no
     count comparison, no CAGG. Simplest of the seven.

===============================================================================
11. ENVIRONMENT-DAILY-SPECIFIC SEMANTICS  (why env_daily != the energy cascade)
===============================================================================

11.1 SITE-LOCAL CALENDAR DAYS, DST-AWARE. refresh_environment_daily localises
     each environment_measurements.bucket_start to metadata.sites.timezone and
     groups by (device, local calendar day). It emits ONLY complete local days
     (local_day_end <= p_to). The reconcile MUST preserve this: it passes a
     specific day's [local_day_start, local_day_end) to the function and lets
     the function do all timezone/DST math. It does NOT compute UTC buckets and
     does NOT reinterpret local days. (This is the explicit instruction: "do
     NOT turn it into a generic UTC bucket reconciliation algorithm.")

11.2 NO QUALITY LATTICE, NO NO_DATA ROW. A device/day with no source produces
     NO row. So EXPECTED_NO_DATA for env_daily = "no source buckets for
     (device, day) AND no row" — indistinguishable from a real gap until source
     arrives. That is correct (same as an eternally-empty energy bucket).

11.3 sample_count IS the fingerprint, but there is NO expected-count column.
     The strict, false-positive-free detector:
       - env_daily row exists with sample_count = S, and
         count(environment_measurements buckets for (device, day) NOW) = C > S
         => LATE_SOURCE -> re-drive that day.
       - source buckets exist for (device, day) in the window with NO env_daily
         row => MISSING_CHILD -> re-drive that day.
     Both compare the child's stored count against the LIVE source count for the
     same (device, local-day). Neither reads the watermark.

11.4 THIN DAY (device offline mid-day). A row with sample_count far below a
     plausible full day, where C == S (no new source). Re-driving it just
     rewrites the same thin row (0 rows_changed) — harmless but noisy. DEFAULT:
     do NOT trigger a repair on this alone; surface it in v_pipeline_health if
     C < expected_buckets * plausibility_frac. plausibility_frac starts unset
     (strict "C > S" only); add it later only if §13 O-E3 shows systemic thin
     days worth flagging.

11.5 CALCULATED_AT CHURN. refresh_environment_daily's DO UPDATE is
     unconditional, so any re-drive rewrites calculated_at. Acceptable
     (env_daily has NO live consumer). A "skip if materially unchanged" guard
     would be a change to refresh_environment_daily -> OUT of scope. The
     reconcile mitigates churn by only re-driving days that fail the strict
     C > S test.

11.6 max_catchup_window (2d) / overlap (1d) / reconcile_window (35d) are the
     211 values; §9 keeps reconcile_window at 35d. env_daily reconcile cadence:
     every 24h (matches its 1h forward job's much-slower effective advance —
     the watermark only moves once per UTC day).

12. RECONCILIATION ARCHITECTURE — OPTIONS + RECOMMENDATION
===============================================================================

12.1 OPTION A — one generic reconcile proc parameterised by tier.
     Pros: least code. Cons: a giant CASE on tier for parent source, fingerprint
     column, grain, refresh function, upsert shape; demand and env_daily do not
     fit the "count fingerprint vs parent count" mould at all (§10, §11);
     one bug affects every tier; hard to test in isolation; failure of one
     tier's branch risks the shared proc. REJECT — code reuse at the cost of
     semantic safety, which the brief explicitly forbids.

12.2 OPTION B — one reconcile wrapper per tier, no shared helpers.
     Pros: total isolation; each proc is small and tier-specific; a bad tier
     cannot touch another. Cons: ~5 near-identical energy-tier detector loops
     (duplication of the count-deficit logic).

12.3 OPTION C — tier-specific procs sharing a small, SIDE-EFFECT-FREE helper.
     Structure:
       analytics.reconcile_energy_consumption_1min(config jsonb)
       analytics.reconcile_energy_consumption_5min(config jsonb)
       analytics.reconcile_energy_consumption_15min(config jsonb)
       analytics.reconcile_energy_consumption_hourly(config jsonb)
       analytics.reconcile_energy_consumption_daily(config jsonb)
       analytics.reconcile_demand_intervals(config jsonb)          -- no helper, §10.6
       analytics.reconcile_environment_daily(config jsonb)         -- own detector, §11.3
     Shared helper (read-only, returns a set, NO writes, NO refresh_* call):
       analytics.reconcile_energy_deficits(
           p_tier text, p_win_start timestamptz, p_win_end timestamptz,
           p_coarse interval)
         RETURNS TABLE (coarse_bucket_start timestamptz,
                        src_rows bigint, chi_rows bigint,
                        src_vol bigint, chi_vol bigint)
       -- one SELECT per tier via a CASE on p_tier choosing the parent
       -- relation and the fingerprint column; returns only MISMATCHING coarse
       -- buckets. Pure function, trivially testable, cannot corrupt anything.
     Each reconcile_<energy tier> proc:
       1. read cp (SELECT last_received_at ... ; NO FOR UPDATE, NO write)
       2. if cp IS NULL -> log 'NO_CHECKPOINT', RETURN
       3. v_ws := cp - reconcile_window(tier)
       4. advisory lock hashtextextended('<the tier's NORMAL job proc>', 0);
          on miss -> log 'SKIPPED_LOCKED', RETURN  (BEFORE any detector read)
       5. FOR r IN SELECT * FROM analytics.reconcile_energy_deficits(tier, v_ws, cp, '1 hour'):
            n_mismatch++ ; IF n_mismatch > N_max THEN outcome:='PARTIAL'; EXIT; END IF;
            BEGIN
              v_changed := <the tier's refresh_* function>(r.coarse_bucket_start,
                            r.coarse_bucket_start + '1 hour');
              rows_repaired += v_changed;
            EXCEPTION WHEN OTHERS THEN
              v_err := SQLSTATE||': '||SQLERRM; EXIT;   -- captured, not swallowed
            END;
          END FOR
       6. INSERT INTO analytics.pipeline_reconciliation_log(...);
          IF v_err IS NOT NULL THEN RAISE; END IF;      -- surface after logging
     Note: NO refresh_continuous_aggregate anywhere (§8.6). The BEGIN...EXCEPTION
     in step 5 is fine because it wraps ONLY refresh_energy_consumption_*
     (plain plpgsql), never a CAGG refresh.
     Pros: tier isolation (B) + one tiny testable read-only helper for the 5
     energy tiers; demand and env_daily are fully bespoke (as they must be).
     Cons: 7 procs + 1 helper + 7 jobs.

12.4 OPTION D — a single dispatcher job that PERFORMs each reconcile_<tier> in
     a loop with per-tier EXCEPTION isolation.
     Pros: one scheduler slot. Cons: reintroduces a CALL chain / "second
     pipeline" feel; one dispatcher failure mode for all tiers; loses per-tier
     cadence and per-tier advisory-lock timing; a slow tier delays the rest.
     REJECT for the automated path (acceptable only as a MANUAL "reconcile
     everything now" operator proc, out of scope for 213).

12.5 RECOMMENDATION: OPTION C.  7 tier-specific reconcile procedures + 1
     read-only deficit helper (energy tiers only) + 7 per-tier reconcile jobs
     (§15). Demand and env_daily procs share NOTHING with the energy path.
     Rationale for not forcing demand/env_daily into the energy mould:
       - demand has no count fingerprint and two partial unique indexes; its
         only safe repair path is "re-run refresh_demand_analytics over the
         window" (§10). Trying to detect demand deficits with a count query
         would be a NEW, unproven completeness definition.
       - env_daily is site-local-day / DST / no-quality-lattice; its safe
         detector is "live source bucket count vs stored sample_count per
         (device, local-day)" and its repair is "re-run refresh_environment_daily
         for that day's local bounds" (§11). A UTC-bucket generic algorithm
         would violate the explicit site-local-day preservation requirement.

12.6 The options scored:
       criterion            A(generic)  B(per-tier)  C(per-tier+helper)  D(dispatcher)
       correctness          poor        good         good                ok
       tenant isolation     ok          ok           ok                  ok
       lock behaviour       shared risk isolated     isolated            shared timing
       CAGG handling        n/a (rejected everywhere: §8.6)
       demand semantics     forced      native       native              native
       env-daily semantics  forced      native       native              native
       observability        ok          ok           ok (helper testable) ok
       operational simplicity best       worst        middle              best sched
       testability          poor        good         best                middle
       failure isolation    worst       best         best                worst
     => C.

13. RECONCILIATION LOG DESIGN — analytics.pipeline_reconciliation_log
===============================================================================
(Design only. Do NOT create.)

13.1 TABLE vs HYPERTABLE.  [RECOMMENDATION]
     Expected write volume: 7 tiers x their cadences =
       1min:24 + 5min:24 + 15min:4 + hourly:2 + daily:1 + demand:24 + env:1
       ~= 80 rows/day ~= 29k rows/year. Tiny.
     -> a PLAIN TABLE with a scheduled DELETE is sufficient AND simpler.
     BUT the platform's convention for time-series operational data is a
     hypertable + a policy_retention drop_after. Either is defensible.
     RECOMMENDATION: hypertable on ran_at, chunk_interval 30 days,
     policy_retention drop_after 180 DAYS (not 400 — 6 months of reconcile
     forensics is ample; the table must not itself become an unbounded-history
     problem). This retention IS part of migration 213 (intrinsic to the new
     object), NOT the separate retention migration.
     Re-evaluation of the v1 "400 days": at 29k rows/year the storage
     difference between 180d and 400d is trivial; 180d is chosen for
     "keep operational logs short" hygiene, not for space.

13.2 COLUMNS.  [RECOMMENDATION — minimal]
       run_id            uuid        NOT NULL DEFAULT gen_random_uuid()  -- correlation id for one reconcile run
       tier              text        NOT NULL   -- = pipeline_name
       ran_at            timestamptz NOT NULL DEFAULT clock_timestamp()  -- (partition col)
       trigger_reason    text        NOT NULL   -- 'SCHEDULED' | 'MANUAL'
       window_start      timestamptz NOT NULL
       window_end        timestamptz NOT NULL   -- = the tier checkpoint at run time
       coarse_examined   integer     NOT NULL DEFAULT 0   -- coarse buckets checked by the detector
       coarse_mismatch   integer     NOT NULL DEFAULT 0
       rows_examined     bigint      NOT NULL DEFAULT 0   -- child rows the detector counted
       rows_repaired     bigint      NOT NULL DEFAULT 0   -- sum of GET DIAGNOSTICS from refresh_*
       outcome           text        NOT NULL
                          -- 'HEALTHY' | 'REPAIRED' | 'PARTIAL' | 'SKIPPED_LOCKED'
                          -- | 'NO_CHECKPOINT' | 'FAILED'
       duration_ms       integer
       error_sqlstate    text
       error_message     text
       created_at        timestamptz NOT NULL DEFAULT now()
     DELIBERATELY OMITTED (with reasons):
       - org_id / site_id / asset_id : reconcile runs are tier-global over a
         time window; per-entity detail is not produced by the detector and
         would bloat the log. If ever needed, a child detail table.
       - old_quality / new_quality / old_fingerprint / new_fingerprint : the
         reconcile does not track per-row before/after (it calls refresh_* which
         does the upsert). Recording per-row deltas would require the reconcile
         to read every row twice — rejected as scope creep. rows_repaired +
         coarse_mismatch answer "what did it repair" at the useful granularity.
       - detection_reason per row : the outcome enum + coarse_mismatch suffices;
         "why did it run" = trigger_reason.

13.3 KEYS / INDEXES.  [RECOMMENDATION]
       PRIMARY KEY (run_id, tier)   -- one row per tier per run; run_id groups a
                                    -- "reconcile everything" manual sweep
       INDEX (tier, ran_at DESC)                              -- "last reconcile for X"
       INDEX (tier, ran_at DESC) WHERE outcome IN ('FAILED','PARTIAL')  -- alert scans
     (If a hypertable: the PK must include the partition column ran_at ->
      PRIMARY KEY (tier, ran_at, run_id).)

13.4 The log answers: "what did reconciliation inspect (window_start..window_end,
     coarse_examined, rows_examined), what did it repair (rows_repaired,
     coarse_mismatch), why did it run (trigger_reason; outcome = HEALTHY vs
     REPAIRED), did it succeed (outcome, error_sqlstate, error_message,
     duration_ms), and which run (run_id)?"

14. PIPELINE HEALTH VIEW DESIGN — analytics.v_pipeline_health
===============================================================================
(Design only. READ-ONLY. Do NOT create. Must not mutate state or trigger repair.)

14.1 GRAIN: one row per analytical pipeline (7 tiers; optionally also
     normalized_points / energy_measurements / environment_measurements for a
     unified board). Pure SELECT over: telemetry.pipeline_state;
     timescaledb_information.jobs + .job_stats; analytics.cagg_available_through
     (which reads _timescaledb_catalog.continuous_aggs_watermark);
     analytics.pipeline_reconciliation_log; and per-tier max(bucket_start) /
     max(interval_start) probes.

14.2 OVERSHOOT_RISK — exact timestamp semantics.  [VERIFIED then RECOMMENDATION]
     - cagg_available_through(P) returns the materialisation watermark as a
       timestamptz (microseconds-since-epoch under the hood), NULL for the
       -infinity sentinel.  [VERIFIED — the sentinel maps to NULL locally.]
     - The energy CAGGs are materialized_only = TRUE with end_offset = 1 minute
       [VERIFIED]. So in HEALTHY flow the automatic policy materialises up to
       ~now() - 1min, i.e. cagg_available_through ~= now() - 1min (rounded to a
       bucket boundary), while max(energy_measurements.bucket_start) ~= now().
       => the HEALTHY value of  (cagg_available_through - max(bucket_start))  is
       NEGATIVE, roughly -1 to -2 minutes.
     - OVERSHOOT: source stalls at T. max(bucket_start) freezes at T. The
       policy keeps advancing cagg_available_through toward now()-1min over
       empty buckets. After a few minutes the difference turns POSITIVE.
     - THEREFORE the v1 formula  "cagg_watermark - max(bucket_start) > 0"  is
       DIRECTIONALLY correct but needs a jitter margin. RECOMMENDATION:
         OVERSHOOT_RISK when
           cagg_available_through('telemetry.ca_energy_1min')
             - (SELECT max(bucket_start) FROM telemetry.energy_measurements)
           > INTERVAL '2 minutes'
       (2 x end_offset). Same for ca_energy_5min with its own view.
       A NULL max(bucket_start) (no source at all) or NULL watermark => report
       state UNKNOWN, not OVERSHOOT.

14.3 COLUMNS / EXPRESSIONS.  [RECOMMENDATION]
       pipeline_name
       last_status                pipeline_state.last_status
       last_started_at / last_completed_at / last_error
       child_checkpoint           pipeline_state.last_received_at
       parent_available_through   per-tier: 1min/5min cagg_available_through;
                                  15min LEAST(cp_1min,cp_5min); hourly/daily
                                  cp_15min; demand LEAST(max(em.bucket_start),
                                  max(np.event_time)); env_daily
                                  max(environment_measurements.bucket_start)
       child_lag                  parent_available_through - child_checkpoint
       source_max_bucket          per-tier real source max() (NULL where the
                                  parent is another analytical tier)
       cagg_watermark             1min/5min only; else NULL
       cagg_minus_source          1min/5min: cagg_watermark - source_max_bucket
       last_success_age           now() - last_completed_at WHERE last_status='SUCCESS'
       consecutive_failures       job_stats (total_failures since last success /
                                  bgw_job_stat.consecutive_failures)
       last_run_status            job_stats.last_run_status  (surfaces a current
                                  SKIPPED_LOCKED / a hung RUNNING)
       no_source_data_streak      consecutive last_status='NO_SOURCE_DATA' runs
       last_reconcile_at          MAX(ran_at) FROM pipeline_reconciliation_log
       last_reconcile_outcome
       last_reconcile_rows_repaired
       reconcile_repair_streak    consecutive recent reconcile rows with rows_repaired > 0
       reconcile_age              now() - last_reconcile_at
       health                     derived enum (14.4)

14.4 health ENUM.  [RECOMMENDATION]
       OK               forward status in (SUCCESS, NO_SOURCE_DATA) AND
                        child_lag within one max_catchup_window AND
                        consecutive_failures = 0 AND reconcile_age <= 2x cadence
                        AND reconcile_repair_streak < 3 AND
                        cagg_minus_source <= INTERVAL '2 minutes' (or NULL).
       LAGGING          child_lag > one max_catchup_window but < a hard ceiling;
                        no failures. (Draining a backlog — benign.)
       STALLED          last_success_age > N x schedule_interval, OR
                        child_checkpoint not advancing across >= 3 runs while
                        parent_available_through is.
       FAILING          consecutive_failures >= 3 OR last_status = 'FAILED'.
       OVERSHOOT_RISK   cagg_minus_source > INTERVAL '2 minutes'  (the N3
                        condition, surfaced BEFORE it becomes a hole).
       RECONCILE_STALE  reconcile_age > 2x cadence (the safety net isn't running).
       RECONCILE_BUSY   reconcile_repair_streak >= 3 (persistent upstream issue).
       NO_DATA_EXPECTED for energy_consumption_5min on an all-60s fleet:
                        no_source_data_streak large BUT child_lag small AND
                        parent has data => a benign, expected state, not a fault.
       UNKNOWN          pipeline_state row missing / never run / NULL inputs.

14.5 The view NEVER calls refresh_*, refresh_continuous_aggregate, or writes any
     table. It is a diagnostic SELECT. Alerting (turning these states into
     pages) is a separate, later concern — 214 only EXPOSES the states.
