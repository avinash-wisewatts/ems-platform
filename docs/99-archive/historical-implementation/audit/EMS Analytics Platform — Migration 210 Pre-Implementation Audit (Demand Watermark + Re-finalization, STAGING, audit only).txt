=====================================================================
B. CURRENT DEMAND EXECUTION MODEL
=====================================================================

Every 60s: run_demand_calculation_job -> CALL refresh_demand_analytics(now(), 3h).
Per site x scope, per call:
  * 2 x DELETE demand_state (stale-scope cleanup)              -- cheap
  * 1 x calculate_demand_window(p_final=FALSE) + demand_state upsert  -- live
  * ~ceil(3h/interval)+2 = 14 iterations of the finalize loop, of which
    ~12 do real work (each: resolve_demand_interval + calculate_demand_window
    (p_final=TRUE) + INSERT ON CONFLICT DO NOTHING).
Defect: DO NOTHING => once a closed bucket has ANY row (typically NO_DATA
written during an upstream stall), it is NEVER reconsidered; and anything older
than 3h is never revisited even without a row.

C. DEMAND PARENT-AVAILABILITY SEMANTICS

[FACT] calculate_demand_window reads energy_measurements (by bucket_start) and
normalized_points (by event_time). The routing pipeline_state checkpoints
('energy_measurements', 'environment_measurements') are keyed on
platform_received_at (INGEST time) — NOT comparable to a demand bucket time
(readiness-audit C4). resolve_demand_capability reads only config/metadata (no
source data) so it does not affect availability.

[REC] parent_available_through(demand) =
    LEAST(
        (SELECT max(bucket_start) FROM telemetry.energy_measurements),
        (SELECT max(event_time)   FROM telemetry.normalized_points)
    )
  Both are single-row reverse-index probes:
    energy_measurements_bucket_start_idx (bucket_start DESC)
    normalized_points_event_time_idx    (event_time DESC)
  [INF] In a healthy pipeline normalized_points always leads energy_measurements
  (routing reads normalized_points), so the LEAST resolves to
  max(energy_measurements.bucket_start) in practice — the binding term and the
  correct "closed-bucket data exists through here" signal. The normalized_points
  term is kept for defensive explicitness of the dual source dependency; it is
  cheap. Do NOT use a pipeline_state checkpoint here.

  [FLAG R2] For a hypothetical pure-METER_NATIVE site (demand register that never
  reaches energy_measurements) the LEAST would be gated by other sites'
  energy_measurements progress. Non-issue on the current all-ENISCOPE fleet
  (every site emits energy_measurements). Conservative direction (never
  over-finalizes) => safe.

D. DEMAND WATERMARK SEMANTICS
=====================================================================

pipeline_state('demand_intervals').last_received_at
  = highest demand bucket boundary (interval_start-space, but stored as an
    arbitrary timestamptz — see §E on alignment) THROUGH which a successful
    watermark-driven run has finalized demand_intervals for the whole fleet.
  It is NOT parent_available_through (an input), and NOT the live demand_state
  position, and NOT per-site/scope.
  Advanced ONLY as the last write of a successful run's single transaction.
  A FAILED / cancelled / max_runtime-timed-out / exception run: the wrapper's
  EXCEPTION handler sets FAILED and RAISEs; the TimescaleDB job runner aborts
  the whole job transaction; RUNNING, all demand_intervals writes, and the
  advance all roll back -> last_received_at unchanged. (Identical contract to
  migration 209.)
  First run (last_received_at IS NULL): v_start floor = clock_timestamp() -
  config.lookback (default 3h) — lookback becomes a FIRST-RUN FLOOR only,
  exactly as in 209.

E. CATCH-UP WINDOW
=====================================================================

Per run, inside the 208 advisory lock, with v_ckpt read FOR UPDATE:

  v_grace  := make_interval(secs =>
                COALESCE((SELECT max(late_arrival_tolerance_seconds)
                          FROM config.site_demand_policies WHERE is_enabled), 0)
                + 300);                                  -- <= 3900s (A14 ceiling)
  v_parent := LEAST( max(energy_measurements.bucket_start),
                     max(normalized_points.event_time) );        -- §C
  v_start  := COALESCE(v_ckpt, clock_timestamp() - v_lookback);   -- lookback = first-run floor
  v_to     := date_bin(INTERVAL '15 minutes',
                LEAST( clock_timestamp() - v_grace,
                       v_parent,
                       v_start + v_max_catchup_window ),
                TIMESTAMPTZ '2000-01-01 00:00:00+00');
  IF v_parent IS NULL OR v_to IS NULL OR v_to <= v_start:
      pipeline_state -> NO_SOURCE_DATA (or SUCCESS if v_to = v_ckpt); DO NOT advance; RETURN.
  v_from   := v_start - v_overlap;
  CALL analytics.refresh_demand_analytics(clock_timestamp(), v_lookback, v_from, v_to);
  -- on success:
  UPDATE pipeline_state('demand_intervals') SET last_received_at = v_to, last_status = 'SUCCESS', ...

WHY the grace clamp (v_to <= now - v_grace): the finalize loop's own grace
check (interval_end + late_arrival_tolerance + 5min > p_now -> CONTINUE) would
otherwise SKIP the newest intervals inside [v_from, v_to) while the checkpoint
still advanced to v_to -> a permanent hole below the watermark. Clamping v_to to
now - v_grace guarantees every interval in [v_from, v_to) is already past its
grace, so the loop finalizes all of them and the checkpoint safely advances.
Buckets in (v_to, now) are picked up on a later run once they age past the
grace. The inner grace check stays as belt-and-braces.

WHY date_bin to 15 minutes: keeps the checkpoint on a clean 15-minute boundary.
For 30-minute-policy sites this can cause a <=15-minute over-reach on the last
interval of a run (idempotent, past grace) — acceptable; documented.

max_catchup_window: [REC] 6 hours. [FACT] Validated against cost — see §L. At
6h/15min the finalize loop is bounded to ceil(6*3600/900)+2 = 26 iterations per
scope per site. Do NOT exceed 6h without staging measurement (§O).

overlap: [REC] 30 minutes (= 2 x 15-min interval). Re-finalizes the boundary
interval(s) each run (idempotent via §F). Does NOT need to cover the grace
(grace is handled by the v_to clamp).

lookback: [REC] keep 3 hours (first-run floor only).

reconcile_window: [REC] 6 hours. Stored in config now; CONSUMED BY MIGRATION 212
only (not read by 210). Covers the common late-arrival horizon (job-1077 raw
replay backoff is 1h+2h+6h; a demand-affecting late energy_measurements
correction typically lands within a few hours). A very-late correction (>6h)
needs a manual widened re-finalization (§F, §P R-late).

=====================================================================
G. demand_state SAFETY
=====================================================================

[FACT] The wrapper ALWAYS passes p_now = clock_timestamp() (real wall clock).
The new p_finalize_from / p_finalize_to control ONLY the finalize loop (block
(b)). Block (a) — the live demand_state upsert — uses p_now and
resolve_demand_interval(site, interval_sec, p_now) = the genuinely-current
interval. Therefore:
  * A 6-hour catch-up run does NOT push historical data into demand_state.
  * demand_state is never keyed by a historical interval_start.
  * No summation / accumulation exists in demand_state (it is fully overwritten
    for the current interval), so "revisiting a bucket" cannot double-count.
  * The historical re-finalization path (block (b) + §F) writes ONLY
    demand_intervals, never demand_state.
Architecture preserved: live current bucket -> demand_state ; closed buckets ->
demand_intervals. Migration 210 does not blur this line.

The two DELETE demand_state (stale scope cleanup) still run every call including
catch-up runs — they are metadata-driven (policy disabled / PRIMARY_METER
removed), idempotent, and unrelated to the time window. Safe.

=====================================================================
H. IDEMPOTENCY
=====================================================================

Case F: run the same [v_from, v_to) twice with unchanged source:
  * Block (b): every iteration recomputes the same v_calc; the ON CONFLICT
    DO UPDATE WHERE ... IS DISTINCT FROM (...) is FALSE for every already-
    written row -> zero row writes, finalized_at unchanged.
  * A bucket with no row yet + no source -> INSERT NO_DATA (first run);
    second run -> ON CONFLICT, EXCLUDED = existing -> no write.
  * Block (a) demand_state: idempotent overwrite of the current interval (same
    as today).
  * Checkpoint: advances to the same v_to (v_to is a pure function of
    clock-ish inputs; a second immediate run computes v_start = v_ckpt (now =
    v_to_prev), v_parent unchanged -> v_to' >= v_to_prev but only by real elapsed
    time; re-running the SAME window (reset v_ckpt) -> same v_to). Proven by test.

Idempotency does NOT rely on any new calculation logic — only on
calculate_demand_window's existing determinism + the DISTINCT guard.

=====================================================================

Single transaction per run, NO intermediate COMMIT (consistent with 209 R7).
  Case G (exception after some calculations, before checkpoint advance):
    refresh_demand_analytics raises -> wrapper EXCEPTION -> UPDATE
    pipeline_state FAILED -> RAISE -> job runner AbortCurrentTransaction() ->
    the RUNNING write, EVERY demand_intervals / demand_state write in that run,
    the FAILED write, and the (not-yet-issued) checkpoint advance ALL roll back.
    last_received_at is left exactly at its pre-run value. Retry (next schedule
    slot, up to max_retries 3, retry_period 5m) reprocesses the identical
    [v_from, v_to). No partial demand_intervals rows persist.
  Job timeout (max_runtime 10m): identical rollback (statement cancel).
    max_catchup_window 6h keeps a correctly-sized run well under 10m (§L), so a
    timeout implies max_catchup_window is set too large for current scale ->
    tune the config value, no code change.
  Worker crash / DB restart mid-run: WAL recovery rolls the in-flight txn back;
    bgw_job_stat.consecutive_crashes++; job rescheduled. Checkpoint unmoved.
  Scheduler restart: no effect on committed state; job resumes on schedule.
  Repeated failure: consecutive_failures climbs (visible in bgw_job_stat);
    the checkpoint stays frozen at the last successful boundary (correct — the
    backlog is preserved, not skipped). Alert threshold in §N.

Invariant proven: a non-successful run advances NOTHING.

[FACT] run_demand_calculation_job keeps the migration-208

L. PERFORMANCE SIZING
=====================================================================

Cost of one refresh_demand_analytics call =
  #sites x [ 2 DELETE demand_state
           + #scopes_per_site x ( 1 calc(p_final=FALSE) + demand_state upsert          -- live block (a)
                                + v_max_n x ( resolve_demand_interval
                                            + calc(p_final=TRUE)
                                            + 1 scope-branched upsert ) ) ]            -- finalize block (b)
  #scopes_per_site = 1 (SITE, if enabled) + #PRIMARY_METER assets at that site.
  calc() ~= resolve_demand_capability (config/metadata joins)
          + resolve_*_demand_policy (effective-dated config lookup)
          + resolve_site_capture_bucket (config lookup)
          + 3-4 indexed range reads on energy_measurements
            (device_id + bucket_start range, energy_measurements_device_bucket_start_idx;
             ~15-30 rows per 15-min interval) OR normalized_points
            (device_id + logical_point_id + event_time range).
  => calc() ~ a handful of small indexed lookups. [INF ~0.2-1 ms warm.]

Steady state (checkpoint at now - grace, parent not ahead):
  v_win_to - v_win_from = overlap 30 min  ->  v_max_n = ceil(1800/900)+2 = 4.
  => finalize block shrinks from today's ~12 iterations to ~4.
  => Migration 210 REDUCES steady-state demand finalization cost ~3x.

6-hour catch-up (one run, once, after an outage):
  v_max_n = ceil(6*3600/900)+2 = 26.
  Total finalize calc() calls = #sites x #scopes_per_site x 26.
  [UNK staging scale — §O #6/#7. Meenaxy is small: ~few sites, ~20 devices.]
  Estimate at 5 sites x 5 scopes: 5*5*26 = 650 calc() ~ 0.15-0.65 s + the
  unchanged live block. At 10x scale (50 sites x 10 scopes): 13000 calc()
  ~ 3-13 s. Both well inside max_runtime 10 min. If a real staging measurement
  (§O #8) shows a single 6h catch-up > ~2-3 min, reduce max_catchup_window
  (config, no code) — the backlog then drains over more, smaller runs.

reconcile_window (migration 212) worst case = same as a 6h catch-up (26
iterations x scopes x sites), run once per reconcile cadence (e.g. hourly) and
NOT every minute. Bounded, off the hot path.

Anti-pattern avoided: the finalize loop is bounded by
(v_win_to - v_win_from) <= max_catchup_window <= 6h, NEVER by a growing history.
The 1-minute steady-state run does ~4 finalize iterations/scope, not days.

    wrapper watermark-driven with the SAME pattern migration 209 already proved.
    calculate_demand_window, resolve_demand_interval, and the entire live
    demand_state path are untouched.
  * It satisfies every stated safety property: bounded (max_catchup_window 6h,
    v_max_n <= 26), idempotent (DISTINCT guard), tenant-safe (per-site/scope
    processing unchanged; global watermark bounds time only), concurrency-safe
    (208 advisory lock + FOR UPDATE), restart-safe (single txn, no false
    advance), efficient under 1-min operation (steady-state finalize cost DROPS
    ~3x), safe during multi-hour outages (bounded catch-up drains the backlog
    over successive runs), safe on child failure / timeout (checkpoint frozen,
    retry same window), safe on late data (forward window within grace +
    migration 212's trailing reconcile for older), and safe on an internal hole
    (migration 212 re-finalizes the trailing window WITHOUT moving the
    watermark; calculate_demand_window is a pure STABLE function reusable by
    reconciliation).
  * demand_state cannot become a second accumulator: the wrapper always passes
    p_now = clock_timestamp(); the finalize window is a separate parameter pair;
    demand_state has no summation and is keyed to the current interval only.
  * The write-once defect (ON CONFLICT DO NOTHING) is replaced by a design that
    provably (live-tested on pg16) repairs NO_DATA/INCOMPLETE -> VALID when
    source arrives, and provably never rewrites a finalized VALID row.

BETTER/SIMPLER ALTERNATIVE CONSIDERED — "DO UPDATE + fixed 6h lookback, NO
watermark": simpler wrapper (no pipeline_state read/advance), self-heals any
outage <= 6h automatically. REJECTED because (a) it does NOT self-heal an
outage > 6h without operator action, contradicting the stated objective and the
Phase 2 cascade commitment; (b) it makes the 1-minute steady-state run scan 6h
(~24 finalize iterations/scope) EVERY minute — the exact anti-pattern the brief
forbids; the watermark approach shrinks steady state to ~4 iterations/scope.
The watermark approach is both safer AND cheaper. Other alternatives (split
finalizer procedure; trigger/queue on energy_measurements) add code, drift risk,
or hot-path overhead for no benefit.

NO-GO would apply only if §O reveals: a demand policy with
late_arrival_tolerance approaching 3600s AND a business need for a demand
freshness tighter than ~65 min (would force a config `grace` key + validator
change — small, but out of the "consistent with 209's 4 keys" constraint); or a
6h catch-up measured > ~5 min on staging (would require a materially smaller
max_catchup_window and more runs to drain — still workable, just re-tune).
Neither is likely.
