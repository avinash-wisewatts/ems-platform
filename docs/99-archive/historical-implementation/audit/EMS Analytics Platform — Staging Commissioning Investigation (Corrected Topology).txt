1. PROVEN TOPOLOGY FROM MQTT (empirical, not assumed)
===============================================================================

Inspected real, currently-arriving raw_messages payloads directly (not
historical fixtures). Each Eniscope's MQTT message has exactly one
top-level key, "rtdata", an ARRAY. telemetry.v_rtdata (postgres/ddl/
122_telemetry_pipeline_performance_state.sql) already parses it this way
via jsonb_array_elements — confirming the repository's own ingestion
design already expects multiple entries per message, not one.

Each rtdata array element carries: uid (the real, stable per-meter MQTT_UID,
format 80:34:28:xx:xx:xx:xx:xx, matching admin.create_device's required
regex exactly), C (a channel number), did (an internal Eniscope hardware
slot index, not linearly related to either uid or C), ts, and ~55
electrical measurement fields (A1-3, D1-3, E1-3, I1-3, P1-3, PF1-3, Q1-3,
S1-3, U1-3, V1-3, RE*, REx*, AE*, Ex*, F, In — matching the already-seeded
62-row profile_field_mapping for ENERGY_METER_ENISCOPE_V1). No model,
type, or profile field exists anywhere in the payload — device-model/
profile assignment is purely an EMS-side onboarding decision, never
derivable from the wire data itself.

This directly and empirically confirms your corrected topology: one
Eniscope unit = one MQTT topic = one gateway = one message per cycle, and
that single message's rtdata array enumerates that Eniscope's onboard
energy meters, each independently addressable by its own uid — exactly
the "one gateway with up to 8 onboard meters, each a separate DEVICE"
architecture you described. The three existing gateway rows (Eniscope_1/
2/3_Meenaxy_Unit2) are consistent with this and should NOT be deleted,
merged, or re-modeled — my prior conclusion to the contrary was wrong and
is withdrawn.
