===============================================================================
1. EXECUTIVE SUMMARY
===============================================================================

The prior reconciliation document ("Post-1D Energy-Consumption
Reconciliation and Phase 1E Recommendation") correctly identified that two
real, live implementations compute the same classified-consumption metric
and that only one is read by Grafana. It did NOT verify the two
implementations' output contracts column-by-column, or trace which objects
the "duplicate" view chain feeds besides the reporting layer. This
investigation did both, and found:

    (a) The four v_energy_reporting_* views expose six per-flow quality-
        detail columns (import_gap_intervals, export_gap_intervals,
        import_reset_intervals, export_reset_intervals, import_rollover_
        intervals, export_rollover_intervals) that analytics.get_canonical_
        energy_read directly consumes to compute independently-meaningful
        import_quality_status/export_quality_status values. The persisted
        analytics.energy_consumption_{15min,hourly,daily} tables do NOT
        have these columns — Phase 1B deliberately persisted only COMBINED
        (import-OR-export) gap/reset/rollover counters. There is no way to
        reconstruct the per-flow values from the persisted schema without
        either extending that schema (touching a "DO NOT touch" object) or
        silently degrading the output (a real behavior change for the one
        live dashboard consumer, detailed in §3).

    (b) analytics.v_energy_semantic_rollup_15min is not solely a "duplicate
        query-time path" — analytics.refresh_energy_consumption_15min()
        (Phase 1B's OWN function, explicitly on the "DO NOT touch" list)
        reads FROM it directly (postgres/migrations/180_fix_persisted_
        energy_consumption_15min.sql:104). It cannot be retired under any
        version of this phase, because doing so would break the very
        "canonical" persisted-table population Phase 1E is meant to
        promote. The two lineages are not cleanly separable at the
        15-minute tier; they share this object as required infrastructure.

    (c) analytics.v_energy_reporting_5min's underlying rollup (v_energy_
        semantic_rollup_5min) represents "a 5-minute bucket of whichever
        native granularity a site actually captures at" (works for both
        1-minute and 5-minute capture sites). analytics.energy_consumption_
        5min represents something different: Phase 1B's persisted NATIVE
        tier, populated only for sites whose capture interval is exactly
        5 minutes (mutually exclusive with energy_consumption_1min by
        site). Retargeting the 5-minute reporting view to the persisted
        5-minute table would return no data at all for any 1-minute-
        capture site. This is not a column gap; it is a conceptual mismatch
        in what the two objects represent.

These are reported now, before proposing an implementation, per the
explicit instruction to do so on discovering a material discrepancy.

3. EXACT ARCHITECTURAL GAP
===============================================================================

Not one gap but two independent ones, each individually sufficient to
block the literally-scoped objective:

Gap 1 (column/semantic-fidelity loss, 15min/hourly/daily tiers): the six
per-flow columns cannot be sourced from the persisted tables. Concrete
consequence for the one real consumer (asset-overview.json's "Total Energy
vs previous period" panel, which filters `WHERE e.import_quality_code =
'GOOD'`): today, an interval where only the EXPORT flow had a gap still
shows import_quality_code = 'GOOD' and is correctly included in the "Total
Energy" (import) sum. If quality_status were computed from the combined
counters instead, that same interval would show import_quality_code =
'GAPS_DETECTED' (because SOME flow gapped) and would be incorrectly
excluded from the sum. This is not a hypothetical edge case; it is a
direct, mechanical consequence of collapsing per-flow to combined counts,
and it changes real dashboard output for the one confirmed live consumer.

Gap 2 (conceptual mismatch, 5-minute tier only): v_energy_reporting_5min's
"5-minute bucket of native data" concept has no persisted equivalent for
1-minute-capture sites. energy_consumption_5min only has rows where a
site's native capture interval is exactly 5 minutes. Retargeting would
silently return zero rows for every other site.

Gap 3 (retirement infeasibility, 15min tier only): even independent of
Gaps 1/2, v_energy_semantic_rollup_15min cannot be retired while
refresh_energy_consumption_15min() (explicitly protected) depends on it.

4. CURRENT LINEAGE (both, confirmed unchanged from Phase 1D's finding)
===============================================================================

Shared native tier (real data, actively populated by 5 scheduled jobs,
Phase 1B): energy_consumption_1min / energy_consumption_5min (mutually
exclusive per site) -> analytics.v_energy_consumption_native (UNION ALL).

Live/consumed lineage: v_energy_consumption_native -> v_energy_semantic_
rollup_5min/15min (live GROUP BY, date_bin) -> v_energy_reporting_5min/
15min (tenant-wrapped) -> v_energy_reporting_hourly/daily (live GROUP BY
over the 15min view) -> get_canonical_energy_read -> get_grafana_asset_
energy_intervals -> asset-overview.json.

Persisted/unconsumed-for-reads lineage: v_energy_consumption_native (via
v_energy_semantic_rollup_15min, shared with the line above) -> refresh_
energy_consumption_15min() -> energy_consumption_15min (persisted) ->
refresh_energy_consumption_hourly()/daily() -> energy_consumption_hourly/
daily (persisted). Zero read consumers of the three rollup-tier persisted
tables. energy_consumption_1min/5min themselves (native tier) are also
unread by anything outside their own contract tests, despite being the
same tables the live/consumed lineage reads through v_energy_consumption_
native — i.e., the NATIVE data is real and shared; only the ROLLUP-TIER
persisted tables (15min/hourly/daily) are genuinely unread duplicates.

8. PROPOSED TARGET ARCHITECTURE
===============================================================================

Not proposed this turn. Three non-exclusive resolution paths exist, each
requiring a decision this document cannot make unilaterally:

Path 1 — Extend the persisted schema first (a separate, prerequisite
    phase, NOT Phase 1E as scoped): add import/export-split gap_intervals,
    reset_intervals, rollover_intervals columns to energy_consumption_
    {15min,hourly,daily}, update their refresh functions to populate them
    from the already-per-flow-aware native tier. This directly requires
    touching two objects on Phase 1E's explicit "DO NOT touch" list
    (energy_consumption_* definitions and their refresh functions) — it
    would have to be its own phase, upstream of any reporting-view
    retarget, with its own Phase-1B-style contract test.
Path 2 — Accept combined-only quality granularity for import_quality_
    status/export_quality_status and document the behavior change,
    explicitly confirming with the user whether the one real dashboard
    consumer's "Total Energy" filter (WHERE import_quality_code='GOOD')
    is acceptable to become slightly more conservative (excluding a few
    additional GOOD-import-but-gapped-export intervals). This is a real,
    user-visible change requiring explicit sign-off, not a safe default.
Path 3 — Narrow Phase 1E to hourly/daily only, using energy_consumption_
    hourly/daily (both structurally similar rollups of the same kind as
    15min, so Gap 2 does not apply to them) while leaving 5min/15min on
    the live path — still blocked by Gap 1 (identical missing columns at
    hourly/daily) and Gap 3 (15min's refresh-function dependency, though
    Gap 3 only blocks RETIRING v_energy_semantic_rollup_15min, not
    retargeting v_energy_reporting_15min itself — retargeting is still
    blocked by Gap 1 regardless).

No path above can be selected without user input; none is "the smallest
coherent next phase" implied by the original recommendation once Gaps 1-3
are accounted for.

20. FINAL RECOMMENDATION
===============================================================================

STOP — DISCREPANCY REQUIRES DECISION.

Phase 1E as literally specified (retarget the four reporting views to the
persisted tables, changing nothing else) is not safely implementable
within its own stated boundaries: it would either require touching two
explicitly protected objects (Path 1), silently change real dashboard
output for the one live consumer (Path 2), or is conceptually incoherent
for the 5-minute tier regardless of path (Gap 2), and cannot retire
v_energy_semantic_rollup_15min under any variant while refresh_energy_
consumption_15min() depends on it (Gap 3). Please indicate which
resolution path (or a different one) to pursue; the corresponding
sections 9-19 will then be produced with the same rigor applied throughout
Phases 1A-1D before any implementation begins.
