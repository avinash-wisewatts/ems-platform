1. EXECUTIVE DECISION
===============================================================================

1.1  The v2 reconciliation architecture (Option C: seven tier-specific reconcile
     procedures + one read-only energy deficit helper + seven per-tier jobs +
     analytics.pipeline_reconciliation_log) REMAINS CORRECT against the post-212
     repository and database. RE-VERIFIED NOW: none of the seven calculation
     functions writes telemetry.pipeline_state; the forward watermark is written
     by exactly 12 procedures (the 7 analytical wrappers + 5 telemetry
     loaders) and by nothing else. The reconciliation-vs-forward separation is
     therefore structurally enforceable.

1.2  Two design refinements are REQUIRED beyond v2, both discovered by
     re-reading the deployed refresh_* bodies this session:
       (a) The energy 1min / 5min detector MUST replicate the calculation
           function's device filter (resolve_site_capture_bucket(...)
           .capture_interval_seconds <= 60 for 1min, = 300 for 5min). Without it
           the detector would falsely flag every 300s/900s device's ca_energy_1min
           rows as "missing 1min children". (§7, §9)
       (b) energy_consumption_15min persists BOTH source_interval_count
           (count of native rows) AND source_sample_count (sum of the native
           rows' source_sample_count); energy_consumption_hourly / _daily persist
           source_interval_count = SUM(parent.source_interval_count) (NOT a plain
           count of parent rows). The fingerprint comparison per tier differs
           accordingly. (§7)

1.3  N2 CONFIRMED: energy_consumption_15min reconcile_window is currently 3 days
     (RE-VERIFIED NOW); it must be >= max(1min 2d, 5min 7d) = 7 days because
     15min consumes energy_consumption_1min UNION ALL energy_consumption_5min
     and a ca_energy_5min-fed 5min repair can be up to 7 days old.
     RECOMMENDATION: 8 days.

1.4  DEMAND reconcile_window: RECOMMEND 12 hours (from the current 6 hours),
     PENDING one staging cost read. max_catchup_window stays 6 hours (different
     purpose). If the staging read shows a 12h demand re-finalisation for the
     busiest site costs > ~2–3 minutes, retain 6 hours.

1.5  refresh_continuous_aggregate() STAYS OUT of the automated reconcile path
     (v2 §8, RE-CONFIRMED: the five energy refresh_* are SECURITY DEFINER
     FUNCTIONS — atomic — so they cannot contain it, and the v2 probe proved it
     is rejected inside any (sub)transaction on 2.29.2). reconcile_window for
     1min/5min is set EQUAL TO each CAGG's automatic start_offset (2d / 7d) so
     the automatic refresh policy keeps the CAGG truthful within the window.
     Backfill older than the start_offset is a documented, log-recorded,
     operator-remedied limitation — NOT silently claimed repaired.

1.6  DECISION: GO WITH CONDITIONS — IMPLEMENT 213 AFTER the staging read-only
     checks in §28 resolve NG5 (detector cost at scale) and the demand
     reconcile-window value, and after a conservative-n_max first deployment
     step. Full statement in §30.

1.7  SCOPE HELD: exactly the seven approved tiers. No additional reconciliation
     tier is proposed. (The routing/normalization tiers are explicitly NOT
     reconciled — v2 §E, unchanged: they already re-scan a dynamic overlap
     every run and roll their checkpoint back atomically on failure; adding
     reconciliation there would be the "second forward pipeline" the contract
     forbids.)

4. CURRENT RECONCILIATION GAP
===============================================================================

After 209–211 every analytical tier advances a forward checkpoint only over a
contiguous bounded slice and rolls back atomically on failure. Three classes of
sub-checkpoint hole are still unhandled:

G1  LATE SOURCE below the checkpoint. Energy source data corrected/backfilled
    into energy_measurements after the forward run passed that bucket (routing/
    normalisation overlap, or a job-1077 replay); or a late environment_measurements
    bucket for an already-finalised local day; or late energy_measurements /
    normalized_points for an already-finalised demand interval.

G2  CAGG MATERIALISATION-WATERMARK OVERSHOOT (energy 1min/5min). During an
    upstream stall the CAGG refresh policy advances the scalar watermark while
    materialising no rows; the forward child job's v_to advances to that
    watermark, refresh_* writes 0 rows, and the child checkpoint advances over a
    range that has no CAGG rows. When source later arrives and the CAGG
    re-materialises (within its start_offset), the forward child never re-reads
    that range (its v_from is checkpoint - overlap, minutes).

G3  RETROACTIVE-CONFIG or BUG deficits: an effective-dated capture/quality/register
    policy change, or a bad manual intervention, that changes the correct value
    of already-finalised rows.

None of G1–G3 is a "trailing backlog"; a high-water mark cannot see them. 213
adds a bounded, observable, idempotent trailing re-drive that repairs them
WITHOUT advancing any forward checkpoint. 213 does NOT implement the health
view that EXPOSES the residual (CAGG-older-than-start_offset) limitation — that
is 214; 213 only RECORDS the evidence 214 needs (§22).

6. CAGG BOUNDARY AND WATERMARK ANALYSIS
===============================================================================

RE-VERIFIED NOW:
  ca_energy_1min : time_bucket('1 min', bucket_start) OVER telemetry.energy_measurements,
                   GROUP BY (bucket, organization_id, site_id, device_id);
                   sample_count = count(*); also active_power_sample_count =
                   count(active_power_total_w), import_energy_sample_count =
                   count(import_energy_total_wh). materialized_only = TRUE.
                   refresh policy: start_offset 2 days, end_offset 1 minute,
                   schedule 1 minute.
  ca_energy_5min : identical shape, time_bucket('5 min'); materialized_only = TRUE;
                   start_offset 7 days, end_offset 1 minute, schedule 5 minutes.

CONSEQUENCES (INFERRED FROM HISTORIC + CURRENT):
  C1  A ca_energy_1min row EXISTS for (device, minute) iff >= 1
      energy_measurements row exists there. sample_count is therefore always
      >= 1 and never NULL. There is no "empty materialised row".
  C2  materialized_only = TRUE => reading ca_energy_1min for a bucket beyond the
      materialisation watermark returns NOTHING even if source exists. So the
      detector MUST operate within a window the automatic policy keeps current.
  C3  end_offset = 1 minute => the automatic policy never materialises the
      current, still-filling bucket. The reconcile window ends at the tier
      checkpoint (always behind "now") so the reconcile never touches an
      unsettled bucket.
  C4  Within [checkpoint - start_offset, checkpoint) the automatic policy
      (running every 1 / 5 minutes) has re-materialised every bucket, INCLUDING
      any recent backfill. So ca_energy_1min.sample_count within that window
      EQUALS the current count(*) of energy_measurements for that (device,
      minute). The detector comparing child.source_sample_count vs
      ca_energy_1min.sample_count is truthful for the whole window.
  C5  BACKFILL OLDER THAN start_offset: the automatic policy does NOT
      re-materialise it. Both ca_energy_1min.sample_count and
      child.source_sample_count remain at their old (stale) values, so the
      detector sees "equal" and reports HEALTHY — a MISS. This is the
      OLDER-BACKFILL LIMITATION. 213 does NOT auto-repair it; 213 records
      window_start/window_end in the log so 214 can compare against
      energy_measurements directly and flag it; the operator remedy is a
      one-off top-level  CALL refresh_continuous_aggregate('telemetry.ca_energy_1min',
      old_from, old_to)  (legal at the top level per the v2 probe), after which
      the next reconcile pass repairs the children.

DESIGN DECISION [DESIGN]:
  reconcile_window(1min) = 2 days  = ca_energy_1min start_offset
  reconcile_window(5min) = 7 days  = ca_energy_5min start_offset
  The detector NEVER reads analytics.cagg_available_through or
  _timescaledb_catalog.continuous_aggs_watermark (NG3). It compares
  per-(device, coarse-bucket) row counts and fingerprint sums only.

  comparison per (device_id, hour):
      count(15min rows)                          -- used for MISSING/COUNT sanity
      sum(15min.source_interval_count)           vs  child.source_interval_count
  no device filter.

--- energy_consumption_daily ----------------------------------------------
  child fingerprint       : source_interval_count = SUM(parent.source_interval_count)
                           over the SITE-LOCAL day.
  authoritative parent    : analytics.energy_consumption_15min, bucketed by
                           (s.bucket_start AT TIME ZONE site.timezone)::date.
  comparison per (device_id, site-local day):
      count(15min rows in the local day)
      sum(15min.source_interval_count)           vs  child.source_interval_count
  grain = site-local day (metadata.sites.timezone). The candidate query computes
  each site's local-day UTC bounds; the re-drive passes those exact bounds.

MISMATCH CONDITION (all energy tiers):
    coalesce(parent_row_count, 0)      <> coalesce(child_row_count, 0)
 OR coalesce(parent_fingerprint_sum,0) <> coalesce(child_fingerprint_sum,0)
for at least one (device_id, tier-bucket) inside a coarse bucket
=> that coarse bucket is a REPAIR CANDIDATE.

DO NOT ASSUME plain COUNT(*) is sufficient: hourly/daily persist SUM(child
fingerprint), so the reconcile MUST compare the summed fingerprint, not just
row counts. 15min compares BOTH count and summed source_sample_count.

PROCEDURE analytics.reconcile_energy_consumption_1min(job_id integer, config jsonb)
  LANGUAGE plpgsql  SECURITY DEFINER  owner ems_admin
  SET search_path = pg_catalog, analytics, telemetry, config, metadata   -- match refresh_energy_consumption_1min

  CONSTANTS:
    v_pipeline  = 'energy_consumption_1min'
    v_fwd_lock  = 'analytics.run_energy_consumption_1min_job'   -- the FORWARD wrapper's advisory key
  CONFIG (all optional, validated positive):
    reconcile_window  default INTERVAL '2 days'
    coarse            default INTERVAL '1 hour'
    n_max             default 24
  LOCALS:
    v_run uuid := gen_random_uuid(); v_started := clock_timestamp();
    v_cp timestamptz; v_ws timestamptz;
    v_coarse_examined int := 0; v_coarse_mismatch int := 0;
    v_rows_examined bigint := 0; v_rows_repaired bigint := 0; v_err_count int := 0;
    v_first_sqlstate text; v_first_errmsg text; v_outcome text;

  1. IF NOT pg_try_advisory_xact_lock(hashtextextended(v_fwd_lock, 0)) THEN
        INSERT pipeline_reconciliation_log(v_run, v_pipeline, v_started,'SCHEDULED',
               NULL, NULL, 0,0,0,0,0,'SKIPPED_LOCKED', NULL,NULL,
               (extract(ms FROM clock_timestamp()-v_started))::int);
        RETURN;                       -- single txn; implicit commit; no analytical work
     END IF;
  2. SELECT last_received_at INTO v_cp FROM telemetry.pipeline_state
        WHERE pipeline_name = v_pipeline;                 -- READ ONLY; no FOR UPDATE
     IF v_cp IS NULL THEN
        INSERT pipeline_reconciliation_log(... 'NO_CHECKPOINT' ...);  RETURN;
     END IF;
  3. v_ws := v_cp - reconcile_window;
  4. -- CANDIDATE DETECTION (single set query, oldest-first, LIMIT n_max+1):
     WITH parent AS (
       SELECT ca.device_id,
              date_trunc('hour', ca.bucket_start) AS coarse,
              ca.bucket_start,
              ca.sample_count AS p_vol
       FROM telemetry.ca_energy_1min ca
       CROSS JOIN LATERAL telemetry.resolve_site_capture_bucket(ca.site_id, ca.bucket_start) cp
       WHERE ca.bucket_start >= v_ws AND ca.bucket_start < v_cp
         AND cp.policy_id IS NOT NULL
         AND cp.capture_interval_seconds <= 60
     ),
     child AS (
       SELECT device_id, date_trunc('hour', bucket_start) AS coarse, bucket_start,
              source_sample_count AS c_vol
       FROM analytics.energy_consumption_1min
       WHERE bucket_start >= v_ws AND bucket_start < v_cp
     ),
     mism AS (
       SELECT COALESCE(p.coarse, c.coarse) AS coarse
       FROM parent p FULL JOIN child c
            ON p.device_id = c.device_id AND p.bucket_start = c.bucket_start
       WHERE COALESCE(p.p_vol, -1) IS DISTINCT FROM COALESCE(c.c_vol, -1)
         AND NOT (p.p_vol IS NULL AND c.c_vol IS NOT NULL)   -- SOURCE_RETRACTED: warn, do not repair
     )
     SELECT coarse, count(*) AS mism_rows
     FROM mism GROUP BY coarse ORDER BY coarse LIMIT n_max + 1;
     -- (SOURCE_RETRACTED rows, i.e. child present & parent absent, are counted
     --  separately into a warn tally, not into mism.)
  5. FOR rec IN <the query above> LOOP
        v_coarse_examined := v_coarse_examined + 1;
        IF v_coarse_examined > n_max THEN v_outcome := 'PARTIAL'; EXIT; END IF;
        v_coarse_mismatch := v_coarse_mismatch + 1;
        v_rows_examined := v_rows_examined + rec.mism_rows;
        BEGIN
          v_rows_repaired := v_rows_repaired
              + analytics.refresh_energy_consumption_1min(rec.coarse, rec.coarse + coarse);
        EXCEPTION WHEN OTHERS THEN
          v_err_count := v_err_count + 1;
          IF v_first_sqlstate IS NULL THEN
             v_first_sqlstate := SQLSTATE; v_first_errmsg := left(SQLERRM, 1000);
          END IF;
          EXIT;                        -- stop after the first repair error; do not hammer
        END;
     END LOOP;
  6. v_outcome := COALESCE(v_outcome,
        CASE WHEN v_err_count > 0 THEN 'FAILED'
             WHEN v_coarse_mismatch > 0 THEN 'REPAIRED'
             ELSE 'HEALTHY' END);
     INSERT pipeline_reconciliation_log(v_run, v_pipeline, v_started, 'SCHEDULED',
        v_ws, v_cp, v_coarse_examined, v_coarse_mismatch, v_rows_examined,
        v_rows_repaired, v_err_count, v_outcome, v_first_sqlstate, v_first_errmsg,
        (extract(ms FROM clock_timestamp()-v_started))::int);
     -- proc ends -> single-transaction implicit COMMIT: all successful
     --   refresh_* repairs from step 5 + this log row commit atomically.
     --   The xact advisory lock is released here.

TIER-SPECIFIC VALUES for 1min:
  source/parent       telemetry.ca_energy_1min
  bucket grain         1-minute UTC (comparison); 1-hour coarse (candidate + re-drive)
  window               [v_cp - 2 days, v_cp)
  candidate detection  the FULL JOIN above, with the <=60 capture filter on the
                       parent side
  mismatch condition   per (device, minute): ca.sample_count IS DISTINCT FROM
                       energy_consumption_1min.source_sample_count, OR one side
                       missing (excluding SOURCE_RETRACTED)
  repair call          analytics.refresh_energy_consumption_1min(coarse, coarse + '1 hour')
  row-level behaviour  ON CONFLICT (device_id, bucket_start) DO UPDATE — a
                       healthy row is rewritten with identical values (counts in
                       ROW_COUNT but no semantic change); a stale/missing row is
                       corrected/created.
  no-source behaviour  no ca row -> not a candidate -> HEALTHY
  missing-child        ca row present, child absent -> candidate -> repaired (INSERT)
  logging status       HEALTHY | REPAIRED | PARTIAL | FAILED | SKIPPED_LOCKED | NO_CHECKPOINT
  error behaviour      per-coarse-bucket BEGIN..EXCEPTION; first error stops the
                       loop; outcome='FAILED', error fields set; the log row
                       still commits (single-txn); earlier successful re-drives
                       in the same run also commit; the failed coarse bucket is
                       re-flagged next run. The proc does NOT RAISE, so

  bounded work         <= n_max coarse buckets re-driven per run; oldest-first =>
                       guaranteed forward progress across runs; PARTIAL outcome
                       when > n_max.
  idempotency          refresh_* is an idempotent ON CONFLICT DO UPDATE; a

  v_pipeline  = 'energy_consumption_15min'

  reconcile_window default INTERVAL '8 days'    (N2 — raised from the current 3d; §1.3, §15)
  coarse      INTERVAL '1 hour'   (contains 4 fifteen-minute buckets)
  bucket key  b15 := date_bin('15 minutes', native.bucket_start,
                     TIMESTAMPTZ '2000-01-01 05:30:00+05:30')

  CANDIDATE DETECTION:
    WITH native AS (
      SELECT device_id,
             date_bin('15 minutes', bucket_start, TIMESTAMPTZ '2000-01-01 05:30:00+05:30') AS b15,
             source_sample_count AS ss
      FROM analytics.energy_consumption_1min
      WHERE bucket_start >= v_ws - INTERVAL '15 minutes' AND bucket_start < v_cp
      UNION ALL
      SELECT device_id,
             date_bin('15 minutes', bucket_start, TIMESTAMPTZ '2000-01-01 05:30:00+05:30') AS b15,
             source_sample_count
      FROM analytics.energy_consumption_5min
      WHERE bucket_start >= v_ws - INTERVAL '15 minutes' AND bucket_start < v_cp
    ),
    parent AS (
      SELECT device_id, b15, count(*) AS p_cnt, sum(ss) AS p_ss
      FROM native GROUP BY device_id, b15
    ),
    child AS (
      SELECT device_id, bucket_start AS b15, source_interval_count AS c_cnt,
             source_sample_count AS c_ss
      FROM analytics.energy_consumption_15min
      WHERE bucket_start >= v_ws AND bucket_start < v_cp
    ),
    mism AS (
      SELECT COALESCE(p.b15, c.b15) AS b15
      FROM parent p FULL JOIN child c ON p.device_id=c.device_id AND p.b15=c.b15
      WHERE p.p_cnt IS DISTINCT FROM c.c_cnt
         OR COALESCE(p.p_ss,-1) IS DISTINCT FROM COALESCE(c.c_ss,-1)
    )
    SELECT date_trunc('hour', b15) AS coarse, count(*) AS mism_rows
    FROM mism GROUP BY 1 ORDER BY 1 LIMIT n_max + 1;

  repair call  analytics.refresh_energy_consumption_15min(coarse, coarse + '1 hour')
  no-source    a 15-min bucket with no native rows -> not a candidate -> HEALTHY
  missing-child native rows present, no 15min row -> candidate -> repaired
  everything else (concurrency / bounded work / idempotency / logging / error) as §8.

  RATIONALE for 8 days: 15min consumes energy_consumption_5min, which the 5min
  reconcile repairs over its 7-day window (= ca_energy_5min start_offset). A
  15min reconcile_window shorter than 7 days would fail to propagate a 6-day-old
  5min repair. 8d = 7d + 1d margin, tied to the ca_energy_5min start_offset (an
  upstream recovery boundary), not an arbitrary number.

[DESIGN] PROCEDURE telemetry.reconcile_environment_daily(job_id integer, config jsonb)
  -- schema: telemetry (matches refresh_environment_daily and the forward
  --   wrapper telemetry.run_environment_daily_job)
  LANGUAGE plpgsql  SECURITY DEFINER  owner ems_admin
  SET search_path = pg_catalog, telemetry, metadata
  CONSTANTS: v_pipeline='environment_daily';
             v_fwd_lock='telemetry.run_environment_daily_job'
  CONFIG:    reconcile_window default INTERVAL '35 days'
             n_max            default 35   (max local days re-driven per run)

  1. advisory xact lock on v_fwd_lock; on miss -> log 'SKIPPED_LOCKED', RETURN.
  2. SELECT last_received_at INTO v_cp FROM telemetry.pipeline_state
        WHERE pipeline_name='environment_daily';   -- READ ONLY
     IF v_cp IS NULL -> log 'NO_CHECKPOINT', RETURN.
     -- v_cp is a UTC-day boundary meaning "every site-local day whose
     --   local_day_end <= v_cp has been finalised" (migration 211 semantics).
  3. v_ws := v_cp - reconcile_window;
  4. CANDIDATE DETECTION — per (device_id, site-local day D) where D's
     local_day_start (in UTC) is in [v_ws, v_cp):
       -- STRICT, false-positive-free signal:
       WITH sites AS (SELECT id AS site_id, timezone FROM metadata.sites
                      WHERE COALESCE(lifecycle_status,'ACTIVE') <> 'DECOMMISSIONED'),
       -- local-day grid per site over [v_ws, v_cp):
       days AS (
         SELECT s.site_id, s.timezone, d::date AS local_date,
                (d::date::timestamp   AT TIME ZONE s.timezone)      AS local_start_utc,
                ((d::date + 1)::timestamp AT TIME ZONE s.timezone)  AS local_end_utc
         FROM sites s,
              generate_series( (v_ws AT TIME ZONE s.timezone)::date,
                               (v_cp AT TIME ZONE s.timezone)::date, INTERVAL '1 day') g(d)
       ),
       src AS (
         SELECT em.device_id, dy.site_id, dy.local_date, dy.local_start_utc, dy.local_end_utc,
                count(*) AS src_buckets
         FROM days dy
         JOIN telemetry.environment_measurements em
           ON em.site_id = dy.site_id
          AND em.bucket_start >= dy.local_start_utc
          AND em.bucket_start <  dy.local_end_utc
         GROUP BY 1,2,3,4,5
       ),
       chi AS (
         SELECT device_id, site_id, bucket_start, sample_count
         FROM telemetry.environment_daily
         WHERE bucket_start >= v_ws AND bucket_start < v_cp
       )
       SELECT s.local_start_utc, s.local_end_utc
       FROM src s
       LEFT JOIN chi c
         ON c.device_id = s.device_id AND c.bucket_start = s.local_start_utc
       WHERE c.device_id IS NULL                      -- MISSING_CHILD: source exists, no daily row
          OR s.src_buckets > c.sample_count           -- LATE_SOURCE: more source than the row reflects
       GROUP BY s.local_start_utc, s.local_end_utc
       ORDER BY s.local_start_utc
       LIMIT n_max + 1;
  5. FOR rec IN <above> LOOP  (n_max cap; per-day BEGIN..EXCEPTION)
        v_rows_repaired := v_rows_repaired
            + telemetry.refresh_environment_daily(rec.local_start_utc, rec.local_end_utc);
     END LOOP;
  6. log one row (outcome HEALTHY | REPAIRED | PARTIAL | FAILED | SKIPPED_LOCKED
     | NO_CHECKPOINT), same shape as §8.

  DESIGN NOTES:
   - LOCAL-DAY BOUNDARIES: computed per site from metadata.sites.timezone via
     AT TIME ZONE; the repair passes [local_start_utc, local_end_utc) so
     refresh_environment_daily does ALL its own tz/DST math (unchanged). This is
     NOT a UTC-bucket algorithm.
   - PARTIAL CURRENT DAY: v_cp is a past UTC-day boundary; the generate_series
     upper bound is (v_cp AT TIME ZONE tz)::date, so today's still-incomplete
     local day is never a candidate. Consistent with migration 211's
     complete-days-only rule.
   - MISSING SOURCE: a (device, local-day) with no environment_measurements rows
     produces no `src` row -> never a candidate -> HEALTHY (EXPECTED_NO_DATA).
   - THIN DAY (device offline mid-day, src_buckets = sample_count, both low):
     NOT a candidate under the strict signal. A plausibility-fraction check

16. RECONCILIATION JOB / CADENCE DESIGN
===============================================================================

[DESIGN] SEVEN per-tier jobs (v2 §J; Option D dispatcher rejected — a slow/failed
tier must not starve the others, and per-tier cadence + per-tier advisory-lock
timing are required).

 reconcile job                              schedule  max_runtime  max_retries  retry_period  config (proposed)
 ----------------------------------------- --------- ----------- ----------- ------------ ----------------------------------------------
 analytics.reconcile_energy_consumption_1min   1 hour   5 min        3           15 min       {"reconcile_window":"2 days","coarse":"1 hour","n_max":24}
 analytics.reconcile_energy_consumption_5min   1 hour   5 min        3           15 min       {"reconcile_window":"7 days","coarse":"1 hour","n_max":24}
 analytics.reconcile_energy_consumption_15min  6 hours  10 min       3           30 min       {"reconcile_window":"8 days","coarse":"1 hour","n_max":24}
 analytics.reconcile_energy_consumption_hourly 12 hours 10 min       3           30 min       {"reconcile_window":"10 days","coarse":"1 hour","n_max":24}
 analytics.reconcile_energy_consumption_daily  24 hours 10 min       3           30 min       {"reconcile_window":"21 days","coarse":"1 day","n_max":21}
 analytics.reconcile_demand_intervals          1 hour   10 min       3           15 min       {"reconcile_window":"12 hours","lookback":"3 hours"}
 telemetry.reconcile_environment_daily         24 hours 10 min       3           30 min       {"reconcile_window":"35 days","n_max":35}

 CADENCE RATIONALE:
  - fast tiers (1min/5min/demand) every hour — they feed the slower tiers and a
    1-hour cadence bounds the "how long a late correction takes to surface".
  - 15min every 6h, hourly every 12h, daily/env every 24h — matches how slowly
    those tiers' forward checkpoints actually advance; a faster cadence would
    just find HEALTHY repeatedly.
  - schedule_interval / max_runtime deliberately > the forward jobs' 5-minute
    max_runtime for the fast tiers (10 min for the slow ones) because a
    reconcile run may re-drive up to n_max coarse buckets whereas a forward run
    processes one bounded slice.
  - retry_period 15–30 min (not the forward jobs' 5 min): a failed reconcile is
    not urgent; it retries next cadence anyway.

 INITIAL_START / PHASE OFFSET:
  add_job's initial_start should be set so each reconcile job fires OFF the
  hour/:00 boundary where the forward jobs run, e.g.
     initial_start => date_trunc('hour', now()) + INTERVAL '33 minutes'  (demand)
     ... '37 minutes' (1min) ... '39' (5min) ... '41' (15min) ... '43' (hourly)
     ... '47' (daily) ... '51' (env)
  so a reconcile does not lose the advisory-lock race to a forward job every
  single run. If a reconcile does coincide with a forward run it simply logs
  SKIPPED_LOCKED and retries next cadence — correct, just less efficient.

 JOB IDS: assigned by add_job at implementation time and CANNOT be
 predetermined. All 213 code (the reconcile procs, the check_config wiring, any
 test) must look jobs up by (proc_schema, proc_name) via
 timescaledb_information.jobs — exactly as migrations 208–211 do. State this
 explicitly; do not hard-code IDs.

 check_config: a NEW tiny validator
     config.assert_reconciliation_job_config(config jsonb) RETURNS void
   accepting ONLY keys {reconcile_window, coarse, n_max, lookback}, each
   (interval keys) a positive finite interval and n_max a positive integer.
   RECOMMENDATION: a dedicated validator rather than extending
   config.assert_analytical_lookback_job_config — the reconcile key set is
   distinct and mixing them would loosen the forward-job validator.

18. TRANSACTION / LOCK / ERROR / CONCURRENCY DESIGN
===============================================================================

TRANSACTION BOUNDARY [DESIGN]:
  Each reconcile procedure is EXACTLY ONE transaction. NO explicit COMMIT /
  ROLLBACK anywhere in the body. (This avoids all TimescaleDB job-proc
  transaction-control uncertainty and is the simplest provably-safe shape.)
  On normal completion the job runner commits: the successful refresh_* repairs
  from the loop + the single pipeline_reconciliation_log row commit ATOMICALLY.
  On max_runtime cancellation or an uncaught error the job runner rolls back:
  nothing is repaired, nothing is logged, nothing is advanced — safe; the next
  cadence retries; the operator sees job_stats.last_run_status='Failed'.

PER-REPAIR ATOMICITY (NG2) [DESIGN]:
  Each refresh_* call is wrapped in a plpgsql  BEGIN ... EXCEPTION WHEN OTHERS
  ... END  subtransaction. A single refresh_energy_consumption_*(a,b) call
  either fully recomputes [a,b) (its INSERT ... ON CONFLICT DO UPDATE completes)
  or its subtransaction rolls back that one coarse bucket entirely. There is no
  half-recomputed bucket. On the FIRST repair error the loop EXITs (does not
  hammer); earlier successful coarse-bucket repairs in the same run remain in
  the outer transaction and commit with the log row.
  NOTE: this BEGIN..EXCEPTION subtransaction is SAFE here because the reconcile
  procs call ONLY refresh_energy_consumption_* / refresh_demand_analytics /
  refresh_environment_daily — never refresh_continuous_aggregate (which the v2
  probe proved is rejected inside a subtransaction on 2.29.2). NG4 is structurally
  prevented: refresh_continuous_aggregate does not appear anywhere in 213.

ADVISORY LOCK [DESIGN]:
  pg_try_advisory_xact_lock( hashtextextended( '<the FORWARD job proc name>', 0 ) )
    1min   -> 'analytics.run_energy_consumption_1min_job'
    5min   -> 'analytics.run_energy_consumption_5min_job'
    15min  -> 'analytics.run_energy_consumption_15min_job'
    hourly -> 'analytics.run_energy_consumption_hourly_job'
    daily  -> 'analytics.run_energy_consumption_daily_job'
    demand -> 'analytics.run_demand_calculation_job'
    env    -> 'telemetry.run_environment_daily_job'
  RATIONALE (RE-VERIFIED NOW): the five refresh_energy_consumption_* FUNCTIONS,
  refresh_demand_analytics and refresh_environment_daily take NO advisory lock
  of their own (touches_advisory_lock = FALSE for all seven). The ONLY thing
  serialising forward runs of a tier is the FORWARD WRAPPER's
  pg_try_advisory_xact_lock on hashtextextended('<wrapper proc>', 0). A
  reconcile that takes the SAME key therefore:
    - cannot run concurrently with that tier's forward job (whichever starts
      second gets the try-lock miss -> SKIPPED_LOCKED, logs it, RETURNs — no
      analytical work);
    - cannot run concurrently with another reconcile run of the same tier;
    - is independent of every other tier.
  The lock is transaction-scoped -> released automatically at the single
  implicit commit/rollback. No pg_advisory_unlock bookkeeping, no session-lock
  leak risk.

CONCURRENT-INVOCATION / FORWARD-JOB-PROCESSING-SAME-PERIOD:
  Handled by the shared lock above. If the forward job is mid-run, the reconcile
  gets SKIPPED_LOCKED and retries next cadence — over a window that now includes
  the forward job's fresh work, still correct.

TIMEOUT: max_runtime cancellation -> whole outer transaction aborts -> no
  repairs, no log row -> safe; job_stats records the timeout.

PARTIAL STATE ON FAILURE: impossible for a single repair (subtransaction). A
  run that repaired buckets 1–2 then errored on bucket 3 commits 1–2 + a
  log row with outcome='FAILED' + error_*; bucket 3 (and any later) are
  re-flagged next run. Each of 1–2 is a complete recompute of its window, so
  the committed state is internally consistent.

DOES THE LOG SURVIVE A ROLLBACK? On an UNCAUGHT failure / timeout: NO (whole
  txn rolls back) — accepted; job_stats records it and 214 can surface
  "job ran but wrote no log row" as a health signal. On a CAUGHT repair
  failure: YES — the loop EXITs, the log row is written with outcome='FAILED'
  in the same (committing) transaction. This is the DELIBERATE trade-off
  spelled out in §19.

EXCEPTION HANDLING: used ONLY as the per-coarse-bucket subtransaction wrapper
  around each refresh_* call, plus (optionally) a top-level catch that records
  outcome='FAILED' and re-raises for the timeout case. No EXCEPTION block ever
  wraps a refresh_continuous_aggregate call (there are none).

21. EMPTY-5min SEMANTICS
===============================================================================

HISTORICAL R10 PRESERVED (RE-VERIFIED NOW that the filters are <=60 / =300):

  energy_consumption_5min is empty for the current all-60s fleet because
  refresh_energy_consumption_5min filters capture_interval_seconds = 300.

  (ca_energy_5min via resolve_site_capture_bucket). For a 60s device NO
  ca_energy_5min row qualifies, so the FULL JOIN has:
      parent side: 0 rows     child side: 0 rows     -> 0 mismatches -> HEALTHY.
  => perpetual absence of 5min rows is ALWAYS reported HEALTHY,
     rows_repaired = 0, error_count = 0.

  DISTINCTION the completeness logic makes:
    - "no source data"                : no ca_energy_5min row at all -> HEALTHY.
    - "expected empty tier"            : ca_energy_5min rows exist but ALL fail
                                        the =300 filter -> parent side empty ->
                                        HEALTHY. (This is the 60s-fleet case.)

                                        -> repaired.
  Consistent with the forward semantics: the forward 5min job returns
  NO_SOURCE_DATA when refresh_energy_consumption_5min yields 0 rows but still
  advances its checkpoint; the reconcile likewise does not treat the empty
  result as a hole.

29. NO-GO CONDITIONS

 NG1  A reconciliation repair path can advance a forward pipeline_state
      checkpoint.
      STATUS: NOT triggered. Proven §19 (the 7 calc objects do not write
      pipeline_state; the 12 writers are exactly the wrappers + loaders; the
      reconcile procs call calc objects, not wrappers; contract-gate test).

 NG2  A reconciliation path can partially commit analytical repairs leaving
      inconsistent state.
      STATUS: NOT triggered. Each refresh_*(a,b) is atomic within a
      per-coarse-bucket BEGIN..EXCEPTION subtransaction; a run either commits a
      set of FULLY-recomputed coarse buckets + a log row, or (timeout/uncaught)
      commits nothing.

 NG3  CAGG completeness detection relies solely on the materialisation
      watermark.
      STATUS: NOT triggered. The detector compares per-(device,bucket) row
      counts and fingerprint sums; it never reads cagg_available_through or the
      watermark catalog.

 NG4  Automated reconciliation requires refresh_continuous_aggregate() inside a
      prohibited transaction context.
      STATUS: NOT triggered. 213 contains no refresh_continuous_aggregate call.
      reconcile_window(1min/5min) = the CAGG start_offset so the automatic
      policy suffices within the window; older backfill is alert-only (§22).

 NG5  Candidate detection is unbounded enough to violate job max_runtime.
      STATUS: OPEN — the detector's cost at staging fleet scale is UNKNOWN.
      RESOLUTION: O-C2 (time the detector on staging) must pass before enabling
      each energy reconcile job; max_runtime is finite so a runaway detector is
      killed and the run rolls back safely; coarse / n_max / reconcile_window
      are config-tunable for a conservative first deploy. This is the primary
      reason for GO-WITH-CONDITIONS.

 NG6  Demand reconciliation cannot safely re-finalise historical rows without
      violating the 210 quality/status contract.
      STATUS: NOT triggered. The repair IS the 210 re-finalisation path
      (refresh_demand_analytics with p_finalize_from/to; status-guarded upsert;
      VALID frozen), proven by 210 test T-Refin-E.

 NG7  Environment reconciliation cannot preserve site-local-day / DST semantics.
      STATUS: NOT triggered. The reconcile passes [local_day_start_utc,
      local_day_end_utc) per candidate day; refresh_environment_daily does all
      tz/DST math (unchanged). The candidate query only derives the two UTC
      bounds from (local date, site timezone) via AT TIME ZONE.

 NG8  Tenant/site isolation cannot be proven through the existing calculation
      path.
      STATUS: NOT triggered. §23 — the calc functions derive org/site from
      source; the reconcile API is timestamps-only; no cross-tenant identifier
      is expressible.

 NG9  First-run work cannot be bounded.
      STATUS: NOT triggered (with a deployment step). n_max per run +
      oldest-first ordering + PARTIAL outcome = bounded, resumable. Deploy with
      n_max small; raise after log observation (§20).

 NG10 The reconciliation log introduces unacceptable write amplification or
      unbounded growth.
      STATUS: NOT triggered. One row per run (~80/day ~29k/yr); 180-day
      retention policy; ~14k steady-state rows; no bucket-level detail.

 NG11 (added) A reconcile proc's advisory lock could deadlock or livelock
      against the forward job.
      STATUS: NOT triggered. pg_try_advisory_xact_lock is non-blocking: on a
      miss the reconcile immediately logs SKIPPED_LOCKED and returns. No
      blocking lock is ever taken. Cadence offsets (§16) minimise contention.

 NG12 (added) The 900s-capture-device class corrupts the energy fingerprint.
      STATUS: NOT triggered for the fingerprint (the <=60 / =300 filter
      replication excludes 900s devices from both the 1min and 5min detector).

      consumption tier) — documented as constraint R-900, NOT fixed by 213,
      flagged for 214 to surface. Current fleet is 100% 60s so the exposure is
      latent.
