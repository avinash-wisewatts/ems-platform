Status: PLAN ONLY. No implementation, staging, commit, push, or deployment

===============================================================================
1. EXECUTIVE SUMMARY
===============================================================================

Investigation (prior document) established that resolution-routing
consistency is already substantially implemented: analytics.get_grafana_
asset_energy_intervals already delegates to analytics.get_canonical_energy_
read via analytics.resolve_grafana_energy_routing_resolution, and get_
canonical_energy_read is not orphaned — it is the live, correctly-tiered
(native/5m/15m/1h/1d) implementation with a real grafana_reader grant. The
one concretely remaining gap, confirmed against the current repository and
independently corroborated by the pre-existing Phase 0 Current-State
Inventory ("The router's ELSE branch never returns '1d'"), is that
resolve_grafana_energy_routing_resolution's current (migration 045)
definition only ever returns native/15m/1h — very long ranges (>14 days)
are permanently served at hourly resolution. Migration 044's original
version DID include a '1d' branch (<=24h->15m, <=14d->1h, >14d->1d); it was
dropped when migration 045 shifted every bracket one tier finer, apparently
as an oversight rather than a deliberate removal.

Phase 1D, as now scoped, is a single-function correction: add a fourth
bracket so very long ranges route to '1d' instead of falling through
indefinitely to '1h'. Every downstream object (get_canonical_energy_read's
'1d' branch, analytics.v_energy_reporting_daily, analytics.energy_
consumption_daily) already exists, is already correct (proven in Phase 1B),
and already reachable through get_canonical_energy_read — this phase only
has to make the router actually choose that path for long ranges.

Extend analytics.resolve_grafana_energy_routing_resolution so that ranges

3. CURRENT-STATE ARCHITECTURE (confirmed empirically this session)
===============================================================================

    analytics.resolve_grafana_energy_routing_resolution(p_from, p_to)
        LANGUAGE SQL, IMMUTABLE, no table dependency
        CASE
            WHEN p_to - p_from <= INTERVAL '24 hours' THEN 'native'
            WHEN p_to - p_from <= INTERVAL '14 days'  THEN '15m'
            ELSE '1h'
        END
        Not directly grantable to Grafana/app roles (internal helper only,
        invoked from within SECURITY DEFINER callers); REVOKE ALL FROM
        PUBLIC only, no compensating GRANT — callers reach it only because
        they run as its owner (ems_admin) under SECURITY DEFINER.

    analytics.get_grafana_asset_energy_intervals(org_id, asset_id, from, to)
        Unchanged signature since before migration 044. Calls the router,
        then CROSS JOIN LATERAL analytics.get_canonical_energy_read(...,
        <tier>, 'native'). Sole Grafana consumer: grafana/dashboards/core/
        asset-overview.json, "Total Energy vs previous period" panel.

    analytics.get_canonical_energy_read(org_id, asset_id, from, to,
    requested_resolution, fallback_policy)
        Already dispatches all five tiers correctly, including '1d' via
        analytics.v_energy_reporting_daily (site-local, 15-minute-derived
        only — Phase 1B invariant preserved). Grants: ems_admin,
        grafana_reader (migration 043).

        No dashboard consumer found; automatically inherits the same fix

5. RESOLUTION-ROUTING MATRIX (target state after this phase)
===============================================================================

    Tier | Canonical source              | Site-tz | Query path via router                  | Change in this phase
    1m   | energy_consumption_1min       | n/a     | 'native' request, <=24h, 1-min sites   | none
    5m   | energy_consumption_5min       | n/a     | 'native' request, <=24h, 5-min sites   | none

Threshold value: no source document specifies one. Proposed default: 90
days — long enough that hourly resolution remains practical for typical
"quarter to date" / 90-day dashboard views, short enough that a multi-month
or multi-year view (the case this gap actually affects) gets daily
resolution instead of thousands of hourly points. This is a judgment call,
not a documented requirement; state explicitly if a different threshold
(e.g. 60 or 180 days) is preferred before implementation.

12. SEMANTIC CONTRACT TEST PLAN
===============================================================================

Fixture (one organization, one site with a distinct, deterministic
timezone e.g. Asia/Kolkata for consistency with Phase 1B, one gateway, one
device, one asset with a PRIMARY_METER asset_devices relationship — the
same minimal chain get_canonical_energy_read's tenant-resolution CTE
requires; no device_models/lifecycle complexity needed since this path
does not touch metadata.device_models or lifecycle triggers the way Phase
1A's connectivity fixture did).

A site-specific config.telemetry_capture_policies row is required (not the
platform default, whose effective_from is wall-clock "now" at whatever
instant the disposable DB was deployed and is therefore non-deterministic
for a test needing a >90-day-old range) — capture_interval_seconds=60,
effective_from set far before the fixture's fixed reference instant, so
telemetry.resolve_site_capture_bucket resolves cleanly at every point in
the tested ranges without tripping get_canonical_energy_read's genuine-
policy-change rejection.

Persisted rows seeded directly (Phase 1B discipline: continuous aggregates
cannot be refreshed inside BEGIN/ROLLBACK, so native-tier population is out
of scope here entirely — this test only needs analytics.energy_
consumption_hourly and analytics.energy_consumption_daily rows, both plain
persisted tables with no CAGG dependency, so they can be inserted directly
with realistic, internally-consistent values without needing to fake any
canonical calculation: the test does not assert on the correctness of the
hourly/daily numbers themselves — Phase 1B already proved that — it asserts
only that the ROUTER sends a long-range query to the daily rows instead of
the hourly rows).

Test cases:
    1. Pure router assertions (no fixture needed — IMMUTABLE, no table
       dependency): resolve_grafana_energy_routing_resolution returns
       'native' for a 1-hour range, '15m' for a 7-day range, '1h' for a
       30-day range, '1h' for exactly 90 days, '1d' for 91 days.
    2. End-to-end long-range routing: seed one analytics.energy_
       consumption_daily row (fixed consumption_date, known kWh) for the
       fixture device; call get_grafana_asset_energy_intervals with a
       >90-day range covering it; assert the returned row's elapsed_minutes
       = 1440 (proving a daily-width interval, not hourly) and its
       import_consumption_kwh matches the seeded value exactly.
    3. Regression guard for the unchanged bracket: seed one analytics.
       energy_consumption_hourly row; call get_grafana_asset_energy_
       intervals with a 30-day range covering it; assert elapsed_minutes =
       60 (still hourly, unchanged behavior).
    4. Tenant isolation: call get_grafana_asset_energy_intervals with a
       >90-day range but a grafana_org_id that does not own the fixture
       asset; assert zero rows (reusing the proven grafana_organization_map
       + PRIMARY_METER pattern; no new isolation logic is introduced by
       this phase, so this is a guard, not new coverage).
    5. Fallback behavior: unchanged by this phase (fallback_policy is fixed
       to 'native' by the caller, as before); not re-tested here beyond
       what Section item 2/3 already exercises implicitly.

Distinguished explicitly, per the user's stated discipline: items 2 and 3
directly exercise the real, unmodified get_canonical_energy_read and get_
grafana_asset_energy_intervals functions against real (not faked) persisted
rows; item 1 directly exercises the real, corrected router function; none
of this fakes a canonical calculation output — the daily/hourly kWh values
inserted are simple, arbitrary, internally-consistent test constants, exactly
as Phase 1B's daily-tier fixture used arbitrary-but-consistent kWh values to
prove routing/splitting behavior rather than re-deriving real classifier
math (which Phase 1B already proved separately). No staging fixtures are
introduced; everything runs in the local disposable database only.

15. QUERY-PERFORMANCE IMPLICATIONS (CORRECTED after further inspection)
===============================================================================

CORRECTION to the original plan: analytics.v_energy_reporting_hourly and
analytics.v_energy_reporting_daily are NOT reads of Phase 1B's persisted
analytics.energy_consumption_hourly/daily tables. Verified empirically
(pg_get_viewdef against the live local database) that both are live,
query-time GROUP BY aggregations built on analytics.v_energy_reporting_15min,
which is itself a live GROUP BY (analytics.v_energy_semantic_rollup_15min,
date_bin('15 minutes', ...)) over analytics.v_energy_consumption_native
(the native energy_consumption_1min/5min tables). This is an older,
separate reporting-view lineage (postgres/ddl/147, predating Phase 1B) that
was never repointed at Phase 1B's persisted 15min/hourly/daily tables —
which is consistent with, and now explains, Phase 1B's own finding that its
persisted energy_consumption_* rollup chain has zero real consumers.

Consequence for this phase: routing a >90-day range to '1d' does NOT avoid
a native-data scan — the database still aggregates every native interval
in the requested range (the same rows it would scan to produce '1h'), just
grouped one level coarser. The benefit of this phase is real but narrower
than originally stated: fewer, more compact result rows returned to
Grafana/the client for very long ranges (365 daily rows instead of up to
8,760 hourly rows for a 1-year view), not a reduction in server-side scan
cost. Short/medium-range behavior (<=90 days) is completely unchanged.
Repointing the Grafana-facing reporting views at Phase 1B's persisted,
already-proven tables (which would deliver the originally-assumed scan-cost
reduction) is a separate, larger change explicitly out of scope for this
phase — noted as a candidate for the later energy-consumption consolidation
phase (Section 19).
