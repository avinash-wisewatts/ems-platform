===============================================================================
1. EXECUTIVE SUMMARY
===============================================================================

The Phase 1D objective as stated ("get_grafana_asset_energy_intervals lacks
resolution/tier routing"; "get_canonical_energy_read is an orphaned
implementation needing reconciliation") does NOT match the current
repository state. Both claims trace back to the Architecture Gap Analysis
and Final Reconciliation documents, which describe a state that migrations
042-046 (already in the repository, already applied to staging) resolved.
Specifically:

    - analytics.get_grafana_asset_energy_intervals ALREADY routes by
      resolution tier: it calls analytics.resolve_grafana_energy_routing_
      resolution(p_from, p_to) to choose a tier, then delegates to
      analytics.get_canonical_energy_read to fetch already-classified
      energy at that tier. This was confirmed empirically by querying
      pg_get_functiondef() against a fully deployed + migrated local
      database (the exact mechanism CI and staging deployment both use),
      not by reading a possibly-stale file.

    - analytics.get_canonical_energy_read is NOT orphaned. It has a real
      grafana_reader EXECUTE grant (migration 043, described in the
      manifest as "for the Panel 13 pilot cutover") and IS the live
      implementation actually backing get_grafana_asset_energy_intervals,
      confirmed by the same empirical query.

    - The dashboard contract (signature, column names) is completely
      unchanged from the pre-routing version, so no dashboard update was
      ever needed for this wiring — it already achieves exactly the
      "preferred outcome" architecture this task described.

One genuine, narrower gap remains and is still accurately described by the
Architecture Gap Analysis: analytics.resolve_grafana_energy_routing_
resolution (current, migration-045-corrected definition) never returns '1d'
— its three branches are <=24h -> native, <=14d -> 15m, >14d -> 1h. Very
long ranges (>14 days) are served at hourly resolution rather than daily,
which is functionally correct but not maximally efficient for e.g.
multi-year views. This is the one part of the original "resolution-routing
consistency" gap that has NOT been closed.

A second, separate, lower-severity discrepancy was found: postgres/ddl/141_
asset_energy_persisted_read_path.sql (the fresh-install "canonical database"
baseline snapshot for this specific function) still contains the OLD,
pre-migration-044 direct-native-only function body. It never causes
incorrect live behavior, because every real deployment path (local test DB,
CI, staging) applies the full forward-migration set after the ddl/ baseline,
and migration 044 has genuinely executed (not silently "baselined") on every
environment checked. But the file is misleading to a reader (it misled this
investigation initially) and is a latent documentation-consistency risk.

4. RESOLUTION-ROUTING MATRIX
===============================================================================

    Tier | Canonical source                    | Site-tz aware | Hourly-first-daily risk | Reached via get_canonical_energy_read | Reached via the Grafana auto-router (resolve_grafana_energy_routing_resolution)
    1m   | energy_consumption_1min (native)     | n/a            | n/a                      | yes ('native', 1-min-capture sites)   | yes, for ranges <=24h on a 1-min-capture site
    5m   | energy_consumption_5min (native)     | n/a            | n/a                      | yes ('native', 5-min-capture sites)   | yes, for ranges <=24h on a 5-min-capture site (never via an explicit '5m' request)
    15m  | energy_consumption_15min             | n/a (UTC bucket)| n/a (native-derived)    | yes                                    | yes, for ranges <=14 days
    1h   | energy_consumption_hourly            | n/a (UTC bucket)| n/a (15min-derived, confirmed in Phase 1B) | yes                | yes, for ranges >14 days (also serves what should arguably be daily-tier long ranges)
    1d   | energy_consumption_daily             | YES (site-local midnight, Phase 1B-proven 15min-only derivation) | not applicable -- correctly 15min-derived | yes | NO -- resolve_grafana_energy_routing_resolution never returns '1d'

The Phase 1B invariant (daily must derive from 15-minute, never from hourly)
is preserved throughout: v_energy_reporting_daily -> energy_consumption_daily
-> refresh_energy_consumption_daily, which Phase 1B already proved reads
only analytics.energy_consumption_15min. get_canonical_energy_read's '1d'
branch reads v_energy_reporting_daily directly -- it never routes through
the hourly tier. No violation found.

7. WHAT REMAINS GENUINELY OPEN (CANDIDATE PHASE 1D SCOPE, NOT YET IMPLEMENTED)
===============================================================================

A. Extend analytics.resolve_grafana_energy_routing_resolution so that very
   long ranges (a threshold to be decided, e.g. >90 days or >180 days) route
   to '1d' instead of always falling through to '1h' beyond 14 days. This is
   a small, single-function change, does not touch get_canonical_energy_read
   or get_grafana_asset_energy_intervals's own bodies, and preserves the
   existing Grafana boundary exactly (same signature, same single consumer).

B. (Optional, lower priority, hygiene-only) Correct the stale postgres/ddl/
   141_asset_energy_persisted_read_path.sql baseline snapshot so a genuinely
   from-scratch ddl-only install would not transiently expose the old
   non-routed body before forward migrations apply. This does not currently
   cause any incorrect live behavior on any checked environment (local, CI,
   staging all apply forward migrations after the ddl baseline), so it is
   advisory, not urgent.

Neither of these matches the original Phase 1D framing ("reconcile an
orphaned function", "get_grafana_asset_energy_intervals lacks routing") --
both are much smaller than what was originally scoped.
