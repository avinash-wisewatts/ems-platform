EMS Analytics Platform — Development Bible v1.0
1. Product Vision

We are building a multi-tenant EMS analytics product, not a Grafana replacement in the narrow sense.

The customer-facing product will provide standard, purpose-built workflows and screens for:

Executives
Facility / Energy Managers
Site Operators
Service / Engineering teams

There will be no customer-created dashboards in the initial product.

The platform will eventually support:

Energy analytics
Demand analytics
Asset performance
Environmental analytics
Data quality
Alarms/events
Benchmarking
Cost/tariff analytics
Baselines
Anomaly detection
Automated insights
Recommendations
Reporting

The architecture must support all of these from day one, even where some capabilities are not initially exposed to customers.

2. The Most Important Architectural Decision

We are not replacing Grafana with another visualization tool.

We are replacing the role Grafana currently plays as the customer-facing analytical application.

The new architecture is:

                    TELEMETRY
                       │
                       ▼
                    TIMESCALE
                       │
              ┌────────┴────────┐
              │                 │
              ▼                 ▼
        TELEMETRY MODEL    ANALYTICS MODEL
              │                 │
              └────────┬────────┘
                       ▼
              EMS SEMANTIC LAYER
                       │
                       ▼
             ANALYTICS QUERY ENGINE
                       │
                       ▼
                  API LAYER
                       │
                       ▼
              EMS WEB APPLICATION
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    Executive      Facility       Service
      UX             UX             UX

Grafana becomes:

                    TIMESCALE
                       │
                       ▼
                 OPS / ENGINEERING
                       │
                       ▼
                    GRAFANA

Grafana remains valuable, but it is no longer the product's analytical UX.

4. Multi-Tenant SaaS Is a First-Class Requirement

This changes the architecture significantly.

The platform must understand:

Platform
 └── Organization
      ├── Users
      ├── Roles
      ├── Sites
      │    ├── Areas
      │    │    └── Assets
      │    │         └── Devices
      │    │              └── Points
      │    └── Energy configuration
      │
      └── Feature configuration

Every analytics request must be evaluated in the context of:

User
 ↓
Organization
 ↓
Permitted Site(s)
 ↓
Permitted Assets

The browser must never be trusted to enforce tenant isolation.

6. Standard Workflow Philosophy

Instead of:

"Here is a dashboard. Configure it yourself."

we provide:

"Here is the answer to the question you came here to answer."

Examples:

"How is my site performing?"

→ Site Overview

"Where am I consuming energy?"

→ Energy Breakdown

"When am I consuming energy?"

→ Load Profile

"What is driving my peak demand?"

→ Demand Analysis

"Which equipment is behaving abnormally?"

→ Asset Performance

"Can I trust this data?"

→ Data Quality

"What needs attention?"

→ Exceptions / Alerts

"Why did energy increase?"

→ Analysis / Insights

This is one of the biggest opportunities over Grafana.

7. Semantic Layer — Core of the Platform

This becomes the heart of the architecture.

The semantic layer defines what:

"Energy consumption"

actually means.

It should understand:

Metric
Dimension
Entity
Unit
Time
Resolution
Quality
Calculation
Aggregation
Scope

For example:

Metric:
    Energy Consumption

Entity:
    Site

Unit:
    kWh

Native resolution:
    1 minute

Available:
    1m / 5m / 15m / 1h / 1d

Aggregation:
    SUM

Timezone:
    Site timezone

Quality:
    Validated

Scope:
    Organization / Site / Area / Asset

The frontend should never need to know which table contains this.

8. Cost/Tariff Architecture

This is an important decision from your answer.

Build now. Expose later.

Therefore the analytical model should already support:

Tariff
 ├── Energy rate
 ├── Demand rate
 ├── Time-of-use periods
 ├── Peak periods
 ├── Fixed charges
 ├── Taxes
 ├── Currency
 └── Effective dates

Then:

Energy Consumption
       +
Tariff Model
       ↓
Energy Cost

The UI can simply hide this capability initially.

This avoids a major future data-model migration.

9. Baselines and Intelligence

Because you want automated insights eventually, we should design the analytical model to support:

Actual
   │
   ├── Baseline
   │
   ├── Expected
   │
   └── Forecast

Then the platform can eventually produce:

Chiller 3 consumed 18% more energy than its expected baseline.

That requires:

historical context
normalized metrics
operating conditions
baseline models
data quality
comparison periods
anomaly scores
confidence

Therefore data quality is not an operational side feature.

It becomes a prerequisite for intelligence.

10. Analytics Layers

I recommend formally separating the platform into these conceptual layers.

L0  Raw Telemetry
        ↓
L1  Normalized Telemetry
        ↓
L2  Domain Measurements
        ↓
L3  Aggregated Measurements
        ↓
L4  Validated / Semantic Metrics
        ↓
L5  Analytical Features
        ↓
L6  Insights / Recommendations
        ↓
L7  Presentation

This is important.

We should not allow:

React
  ↓
random SQL
  ↓
raw telemetry

or:

Grafana panel
  ↓
custom SQL calculation

The calculation belongs in the analytical platform.

11. Resolution Architecture

The system should support:

1 minute
5 minute
15 minute
1 hour
1 day

But users should not select resolutions as a technical concept.

They select:

Today
7 Days
30 Days
3 Months
1 Year

The analytics engine determines the appropriate physical resolution.

For example:

30-day chart
       ↓
analytics engine
       ↓
15-minute data

rather than:

User
 ↓
Choose 15-minute

This is a key UX improvement.

12. Analytics API

The API should speak in EMS concepts.

Not:

/query?table=v_grafana_normalized_points

Instead:

/sites/{site_id}/energy/consumption
/sites/{site_id}/energy/demand
/sites/{site_id}/energy/load-profile
/sites/{site_id}/assets
/sites/{site_id}/alarms
/sites/{site_id}/data-quality

Eventually:

/sites/{site_id}/insights
/sites/{site_id}/benchmarks
/sites/{site_id}/forecast
/sites/{site_id}/cost

This gives us a stable contract even if the database architecture changes.

16. Critical Gates

We should explicitly prevent ourselves from rushing ahead.

Gate 1

Do not build React screens until the semantic model is approved.

Gate 2

Do not redesign database tables until the current analytics inventory is complete.

Gate 3

Do not build APIs around existing Grafana SQL.

Gate 4

Do not optimize queries before establishing representative workloads.

Gate 5

Do not build AI/insights until data quality is measurable.

Gate 6

Do not remove Grafana until the replacement has passed numerical parity testing.

17. The First Actual Work Package

Given everything we've established, I recommend we do not start implementation yet.

Our immediate task should be:

Analytics Platform Discovery — Phase 0

We need Claude to perform another investigation-only audit, similar to the telemetry audit you just gave me.

This one should answer:

"What exactly is the current EMS analytics platform, from raw telemetry through database analytics tables/views/functions/jobs and finally every Grafana dashboard/panel/query?"

No redesign recommendations in the audit. Facts first.
