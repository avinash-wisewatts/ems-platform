A1. N1 (normalization forward-window still unbounded) is a REAL, live defect of
    the exact class of the 2026-08-26 job-1000 incident, and it is SAFE to fix
    with the migration-207 pattern applied to telemetry.run_normalization_job.
    The fix is small, mechanical, and changes no steady-state calculation
    semantics. [VERIFIED for the defect; DESIGN for the fix]
    RECOMMENDATION: implement N1 as its own tiny migration (proposed number 212)
    BEFORE the reconciliation work. Provisional default max_window = 2 hours,
    to be confirmed against a staging job-1000 runtime read (§O). GO.

A2. The redesigned reconciliation migration (proposed number 213, formerly
    "212") is SAFE to build PROVIDED it is completeness-aware for the two
    CAGG-fed tiers. A truthful completeness signal EXISTS and is already
    persisted:
      - ca_energy_1min / ca_energy_5min are time_bucket aggregates DIRECTLY over
        telemetry.energy_measurements; a CAGG row exists iff >=1 source row
        exists in that (bucket x device) cell — there is NO such thing as an
        "empty materialised CAGG row". [VERIFIED]
      - analytics.energy_consumption_1min / _5min persist source_sample_count
        (= the CAGG bucket's sample_count as of the run). [VERIFIED]
      - analytics.energy_consumption_15min / _hourly / _daily persist
        source_interval_count (= count of parent rows rolled up). [VERIFIED]
    => reconciliation can compare, per bucket, the child's persisted
    source-count fingerprint against the live parent, and repair only the
    buckets that mismatch or are missing. An empty parent range is correctly
    left alone (nothing to reconcile), NOT declared "healthy because the
    watermark is ahead". This directly solves N3. GO, with the design in §F/§J.

A3. N2 (energy_consumption_15min reconcile_window = 3 days) IS insufficient.
    15min is calculated from analytics.v_energy_consumption_native =
    energy_consumption_1min UNION ALL energy_consumption_5min. [VERIFIED]
    A late source correction can reach energy_consumption_5min up to
    ca_energy_5min's start_offset = 7 days back. [VERIFIED]
    => 15min reconcile_window must be >= 7 days. RECOMMEND 8 days (7d + 1d
    margin). This is a one-line config change, made as part of migration 213.

A4. NO-GO conditions (§S) are NOT triggered by anything found in the repo /
    local DB. Two are gated on staging reads (§O): (i) a demonstrably too-
    expensive 6h demand catch-up or reconcile pass, (ii) a job-1000 runtime

    parameter-tuning outcomes, not architecture blockers.

A5. Decomposition (§N): three small migrations, each independently reviewable:

      213  reconciliation log + completeness-aware reconcile procedures + jobs

C. N1 NORMALISATION FINDINGS
===============================================================================

The 10 required proofs (all from the deployed bodies, local DB):

C1. WHAT COMPUTES THE CURRENT FORWARD BOUNDARY?  [VERIFIED]
    telemetry.load_normalized_points_incremental(p_overlap, p_max_window):
        SELECT max(received_at) INTO v_window_end FROM telemetry.raw_messages;
        IF p_max_window IS NOT NULL AND v_previous_checkpoint IS NOT NULL THEN
            v_window_end := LEAST(v_window_end, v_previous_checkpoint + p_max_window);
        END IF;
    The window start is v_previous_checkpoint - v_dynamic_overlap (steady state)
    or GREATEST(v_window_end - 48h, min(received_at)-1us) on the very first run
    (checkpoint NULL). So the FIRST run is inherently bounded to 48h; every
    subsequent run's forward edge is max(raw_messages.received_at) UNLESS
    p_max_window is supplied.

C2. CAN THE ENTIRE BACKLOG STILL BE PROCESSED IN ONE TRANSACTION?  [VERIFIED] YES.
    The whole loader body is a single transaction: temp tables ON COMMIT DROP,
    every INSERT/UPDATE (capture_bucket_samples, normalized_points,
    device_point_state, device_telemetry_state), and the terminal
    pipeline_state UPDATE (last_received_at = v_window_end, SUCCESS) are all in
    one txn. NO intermediate COMMIT. If the window is a multi-hour backlog and
    the run exceeds max_runtime (5m), the TimescaleDB job runner cancels it =>
    the whole transaction rolls back => zero durable progress => the retry faces
    an equal-or-wider window. THIS IS THE 2026-08-26 INCIDENT MECHANISM,
    one hop upstream of where migration 207 fixed it.

C3. IS THERE A MAX-WINDOW PARAMETER?  [VERIFIED] YES.
    p_max_window INTERVAL DEFAULT NULL was added by migration 205 to this exact
    loader. It is fully implemented (the LEAST(...) cap above) and tested
    (scripts/test/assert_normalization_bounded_catchup_window.sql).

C4. DOES THE SCHEDULED WRAPPER PASS NULL OR AN UNBOUNDED VALUE?  [VERIFIED]
    telemetry.run_normalization_job body:
        CALL telemetry.load_normalized_points_incremental(v_overlap);
    -- ONE positional argument => p_max_window resolves to its DEFAULT NULL.
    Job 1000 config carries only {"overlap":"15 minutes"} -- NO max_window key.
    => the scheduled path is currently UNBOUNDED. [VERIFIED]

C5. IS MANUAL UNRESTRICTED CATCH-UP STILL POSSIBLE?  [VERIFIED] YES, and it is
    intended. postgres/maintenance/45_rebuild_normalized_history.sql calls the
    loader directly for a full historian rebuild; the migration-205 COMMENT
    explicitly documents that a one-argument or explicit-NULL manual CALL
    performs unrestricted catch-up. This capability MUST be retained.

C6. DOES NORMALISATION ALREADY HAVE THE REQUIRED TRANSACTIONAL FAILURE
    BEHAVIOUR?  [VERIFIED] YES, at the LOADER layer:
      - pg_try_advisory_xact_lock(hashtextextended(
          'telemetry.load_normalized_points_incremental',0)) -> on miss:
        pipeline_state SET last_status='SKIPPED_LOCKED' + RETURN.
      - v_previous_checkpoint read FOR UPDATE; RUNNING transition;
        max(received_at) IS NULL -> NO_SOURCE_DATA + RETURN;
        on success -> last_received_at = v_window_end, SUCCESS;
        EXCEPTION WHEN OTHERS -> FAILED + RAISE (whole txn, incl. the checkpoint,
        rolls back).
    The WRAPPER (run_normalization_job) has NO advisory lock and NO pipeline_state
    handling of its own -- it relies entirely on the loader. That is acceptable
    (the loader's lock covers self-overlap) and matches how 1001/1012 are
    structured post-207 (their loaders own the lock; the wrappers only derive
    and pass max_window).
    The same advisory-lock key is also taken by ddl/126/127/128/129 (frequency
    recovery / legacy recovery) so those cannot run concurrently with the
    loader -- coordination, not a caller. [VERIFIED]

C7. WOULD A BOUNDED MAX WINDOW ALTER STEADY-STATE CALCULATION SEMANTICS?
    [INFERENCE, strong] NO. v_window_end := LEAST(max(received_at),
    checkpoint + p_max_window). In steady state the checkpoint is within
    p_max_window of max(received_at), so LEAST picks max(received_at) -- byte
    identical to today. The cap only engages when a backlog exceeds p_max_window.
    Everything downstream of v_window_start / v_window_end -- the policy
    resolution, local bucketing, DISTINCT ON, mapping priority, quality_code
    derivation, the normalized_points / device_point_state / device_telemetry_state
    upserts -- is unchanged. This is exactly the property migrations 205 and 207
    already proved for the identical LEAST(...) construct.

C8. CAN THE MIGRATION-205 PATTERN BE REUSED SAFELY?  [VERIFIED/DESIGN] YES.
    205 already put p_max_window on THIS loader. 207 already demonstrated the
    wrapper-side wiring for the SIBLING loaders (run_energy_routing_job /
    run_environment_routing_job): derive v_max_window from config.max_window
    (default INTERVAL '2 hours'), ALWAYS pass it to the loader, and merge
    {"max_window":"2 hours"} into the job config via alter_job. N1 = apply that
    identical wrapper wiring to run_normalization_job. Nothing new is invented.

C9. DOES JOB 1000 NEED THE SAME 2-HOUR DEFAULT AS 1001/1012, OR A DIFFERENT
    VALUE?  [UNKNOWN -> provisional 2h].
    Arguments for 2h: consistency with the sibling routing jobs; 1-minute
    schedule means a 24h backlog drains in ~12 successive runs (~12 min wall);
    the loader's own dynamic overlap already covers the trailing edge.
    Arguments it MIGHT need to be smaller: normalization's per-run cost profile
    is heavier than routing (jsonb_array_elements over rm.payload->'rtdata',
    the telemetry.v_rtdata view, three MATERIALIZED CTE stages, the
    device_point_state / device_telemetry_state upserts). If a 2h window on a
    busy staging fleet cannot finish inside max_runtime 5m, the job still makes
    zero progress -- the cap must be small enough that ONE capped window fits in
    5m with margin.
    EVIDENCE NEEDED (§O): staging job_stats for job 1000 -- last_run_duration
    distribution, total_successes/total_failures, consecutive_failures; and one
    timed read-only CALL of the loader over a 2h window on the busiest recent
    period, rolled back. If a 2h window > ~2 min, set the default to 1h (or
    30m). Do NOT ship 2h as fact; ship it as a config-overridable default with a
    staging check gating the value.

C10. ADDITIONAL HARDENING BEYOND BOUNDED CATCH-UP?  [VERIFIED/DESIGN]
     - max_runtime / max_retries / retry_period / scheduled on job 1000 are
       ALREADY finite and correct (5m / 3 / 1m / true) -- migration 194 + baseline.
       No change needed.
     - No check_config validator on 1000/1001/1012 (only the analytics tier got
       one, in 208). N1 should NOT add one (stay consistent with 207; a
       one-key {"max_window"} config is low-risk). Optional: a 2-line
       config.assert_routing_window_job_config could be added covering
       overlap/max_window for all three routing/normalization jobs -- defer,
       not required for correctness.
     - The wrapper's RAISE NOTICE lines are cosmetic; leave them.
     - First-run (checkpoint NULL) is already bounded to 48h in the loader --
       no change needed.
     - RECOMMENDATION: N1 does the minimum -- wrapper passes bounded max_window
       + alter_job. Nothing else.

     After a stall of N hours, successive 1-minute runs each advance the
     checkpoint by <= 2h and durably commit. A 24h backlog self-drains in ~12
     runs. No operator action, no manual backfill. (A DELIBERATE operator
     rebuild still uses the maintenance script's unbounded CALL.)

D12. ROLLBACK / FAILURE SEMANTICS
     Identical to today: the loader is one transaction; advisory lock; RUNNING;
     SUCCESS writes last_received_at = v_window_end as the last statement;
     EXCEPTION -> FAILED -> RAISE rolls the whole run back INCLUDING the
     checkpoint. A cancelled/timed-out capped run leaves the checkpoint where it
     was; the retry reprocesses the same <= 2h window (now more likely to fit
     in 5m). Migration rollback = CREATE OR REPLACE the prior wrapper body +
     alter_job to drop the max_window key (or leave it -- a stale key is inert
     because the reverted wrapper would ignore it; cleanest is to drop it).

F. CAGG COMPLETENESS ANALYSIS  (solves N3 — the most important part)
===============================================================================

F1. THE FALSE-AVAILABILITY MECHANISM, PRECISELY.  [FACT/VERIFIED]
    ca_energy_1min = SELECT time_bucket('1 min', bucket_start), org, site, device,
                            count(*) AS sample_count, ...
                     FROM telemetry.energy_measurements
                     GROUP BY 1, org, site, device;
    Consequences:
      (i)  A CAGG ROW EXISTS for (B, device) IFF >= 1 energy_measurements row
           exists in [B, B+1min) for that device. There is NO "empty
           materialised row". A time_bucket GROUP BY does not emit rows for
           empty buckets.
      (ii) The materialisation WATERMARK (a single scalar in
           _timescaledb_catalog.continuous_aggs_watermark, read by
           cagg_available_through) advances as the refresh policy runs, WHETHER
           OR NOT any rows were produced. During an upstream normalization/
           routing stall the watermark can sit at "now-ish" while
           energy_measurements has no rows for the last hour.
      (iii) run_energy_consumption_1min_job then computes
            v_to = LEAST(now_binned, cagg_available_through(ca_energy_1min),
                         checkpoint + max_catchup_window)
            = ~watermark, calls refresh_energy_consumption_1min(v_from, v_to)
            which finds NO ca_energy_1min rows -> writes 0 child rows ->
            NO_SOURCE_DATA -> BUT last_received_at ADVANCES to v_to.
      (iv) Later the stall clears; energy_measurements gets the backfilled rows;
           the ca_energy_1min REFRESH POLICY (start_offset = 2 days trailing)
           re-materialises the affected buckets -> ca_energy_1min rows now
           EXIST for the previously-empty range.
      (v)  But energy_consumption_1min's checkpoint is already past that range;
           its steady-state v_from = checkpoint - overlap (2 min) never reaches
           back to it. => a PERMANENT hole in energy_consumption_1min (and,
           cascading, 15min/hourly/daily), Grafana-visible via
           analytics.v_energy_consumption_1min and the asset dashboard read
           path (ddl/134, ddl/141). [VERIFIED the consumer path; INFERENCE the
           permanent-hole outcome absent reconciliation]

F2. THE TRUTHFUL COMPLETENESS SIGNAL EXISTS AND IS PERSISTED.  [VERIFIED]
    For each (device, 1-min bucket B):
      SOURCE-PRESENCE  = (a ca_energy_1min row exists for (B, device))
                       ~= EXISTS(energy_measurements in [B,B+1min) for device)
                          -- equivalent while both are within retention and the
                          CAGG is current for B.
      SOURCE-VOLUME    = ca_energy_1min.sample_count  (count(*) of source rows)
      CHILD-PRESENCE   = (an energy_consumption_1min row exists for (B, device))
      CHILD-VOLUME     = energy_consumption_1min.source_sample_count
                         (persisted = the CAGG's sample_count AS OF the last
                          run over B; refreshed on every ON CONFLICT DO UPDATE).
    The seven states the brief asks to distinguish map cleanly:

     #  Condition                                              Reconciliation verdict
     -- ---------------------------------------------------- -------------------------------
     1  source existed, result should exist                  CHILD-PRESENCE && CHILD-VOLUME
                                                             == SOURCE-VOLUME  -> HEALTHY, skip.
     2  source genuinely did NOT exist                       no CAGG row && no child row
                                                             -> HEALTHY (nothing to do).
                                                             NOT "declared healthy because
                                                             watermark ahead" -- there is
                                                             simply nothing to reconcile.
     3  CAGG watermark advanced across a stalled bucket      at the time: no CAGG row, no
                                                             child row. Indistinguishable
                                                             from #2 UNTIL source arrives
                                                             (#4). This is CORRECT: an
                                                             eternally-empty bucket and a
                                                             temporarily-stalled one look
                                                             the same and should be treated
                                                             the same (leave alone) until
                                                             real data exists.
     4  source arrived/backfilled into a previously-empty    CAGG row now EXISTS (sample_count
        bucket                                               > 0) && child row ABSENT
                                                             -> REPAIR (INSERT).
     5  child row missing despite source existing            CAGG row exists && child row
                                                             absent -> REPAIR (INSERT).
                                                             (same detector as #4)
     6  child row exists but stale/wrong                     child row exists &&
                                                             source_sample_count <>
                                                             ca_energy_1min.sample_count
                                                             -> REPAIR (DO UPDATE).
     7  bucket outside the source recovery/retention horizon energy_measurements retention
                                                             90d; ca_energy_1min retention
                                                             180d; raw_messages 48h.
                                                             If neither source nor CAGG has
                                                             the bucket any more, there is
                                                             no ground truth -> the
                                                             reconcile window MUST NOT reach
                                                             there. Bounded by
                                                             reconcile_window (§G) which is
                                                             well inside 90d.

F3. THE ONE GAP IN F2, AND HOW TO CLOSE IT.  [INFERENCE + DESIGN]
    ca_energy_1min's AUTOMATIC refresh policy only re-materialises the trailing
    start_offset window (2 days for 1min, 7 days for 5min). If a backfill lands
    in energy_measurements for a bucket OLDER than that start_offset, the CAGG
    is NOT automatically re-materialised there, so both ca_energy_1min.sample_count
    and energy_consumption_1min.source_sample_count stay at their old (stale)
    values and the F2 comparison says "HEALTHY" -- a MISS.
    Closure options, in order of preference:
      (a) [RECOMMENDED] The reconciliation procedure, for the CAGG-fed tiers,
          issues a BOUNDED  CALL refresh_continuous_aggregate('telemetry.ca_energy_1min',
          w_start, w_end)  over its OWN reconcile window BEFORE re-driving the
          child. This is an EXISTING TimescaleDB mechanism (not a new engine),
          it is bounded by reconcile_window, and it forces ca_energy_1min to
          reflect any backfill in that window. Then the F2 comparison is exact.
          Cost: a manual CAGG refresh over reconcile_window on a slow cadence
          (1h/6h). At this fleet size that is an indexed range recompute of at
          most a few days of 1-minute buckets -- cheap. [staging cost check §O #6]
      (b) Compare CHILD-VOLUME against energy_measurements DIRECTLY
          (count(*) FROM energy_measurements in the coarse bucket) instead of
          against the CAGG, for the portion of the window older than the CAGG
          start_offset. Truthful within energy_measurements retention (90d). No
          CAGG refresh needed, but two code paths.
      (c) Widen the CAGG refresh policy start_offset. REJECTED -- that changes
          CAGG cost/behaviour platform-wide and is explicitly out of scope.
    DECISION: (a). reconcile_window for 1min/5min is chosen (§G) so that
    reconcile_window <= a value where a manual refresh_continuous_aggregate is
    cheap, and >= the CAGG start_offset (so the manual refresh always covers at
    least what the automatic one would, plus the older tail).

F4. THE RECONCILIATION RULE FOR THE CAGG-FED TIERS (1min, 5min).  [DESIGN]
    reconcile_cagg_tier(P):                 -- P in {energy_consumption_1min, _5min}
      v_cp  := pipeline_state(P).last_received_at            -- NEVER advanced by this proc
      IF v_cp IS NULL THEN log NOOP; RETURN; END IF
      v_ws  := v_cp - reconcile_window(P)
      -- 1. force the CAGG current over the window (closes F3):
      CALL refresh_continuous_aggregate('telemetry.ca_energy_1min'::regclass, v_ws, v_cp);
      -- 2. cheap deficit detector over coarse (e.g. 1h) sub-buckets:
      FOR each 1h sub-window [a,b) in [v_ws, v_cp):
        SELECT count(*) FROM telemetry.ca_energy_1min  WHERE bucket_start >= a AND < b  -> src_rows
        SELECT count(*), sum(source_sample_count)
          FROM analytics.energy_consumption_1min       WHERE bucket_start >= a AND < b  -> chi_rows, chi_vol
        SELECT sum(sample_count)
          FROM telemetry.ca_energy_1min                WHERE bucket_start >= a AND < b  -> src_vol
        IF src_rows = chi_rows AND src_vol = chi_vol THEN  CONTINUE;  END IF   -- healthy, skip
        -- 3. repair only the mismatching sub-window:
        v_changed := analytics.refresh_energy_consumption_1min(a, b);   -- SAME function, idempotent upsert
        accumulate rows_examined, rows_repaired
      END FOR
      INSERT INTO analytics.pipeline_reconciliation_log(...);   -- §I
    Properties: (i) never touches pipeline_state.last_received_at; (ii) a clean
    window does 0 child writes (only the coarse-bucket count reads + one bounded
    CAGG refresh); (iii) a window with a backfilled/late range repairs exactly
    the affected sub-windows and logs the count; (iv) idempotent -- a second run
    finds src == chi and does nothing; (v) an empty range (no CAGG rows, no
    child rows) is HEALTHY and skipped -- the watermark being ahead is
    irrelevant because the comparison is bucket-level, not watermark-level.

F5. WHY F4 CATCHES THE OVERSHOOT.  [INFERENCE]
    The overshoot leaves "child watermark past B, no child row for B". After
    source arrives and step 1 re-materialises ca_energy_1min, step 2's coarse
    count sees src_rows > chi_rows for B's sub-window, step 3 re-drives it, and
    the child row is created with the correct source_sample_count. The detector
    is bucket-count based, so it can NEVER be fooled by "the watermark says
    processed" -- it does not consult the watermark at all.

F6. STATEMENT OF RESIDUAL IMPRECISION (do not pretend it is perfect).  [FACT]
    F4 establishes "a child row exists for every (device, bucket) that has
    source rows, and its source_sample_count matches the source". It does NOT
    establish:
      - that the EXPECTED set of devices reported (a device that never sent
        anything in a window is invisible to both source and child -- there is
        no per-site expected-device roster consulted by refresh_energy_consumption_1min);
      - value correctness beyond the sample-count fingerprint (a source row
        with a wrong meter value is counted the same as a right one -- quality
        columns exist on the child but the reconciler does not re-judge them
        beyond what refresh_* already does).
    These are ACCEPTABLE: the platform's completeness contract has always been
    "we aggregate what arrived", and the fingerprint match is the strongest
    defensible signal the persisted model supports. A per-site expected-device
    roster check belongs in v_pipeline_health as an ALERT (via
    analytics.v_device_telemetry_availability -- it has mapped_point_count,
    required_point_count, receiving/stale/silent thresholds), NOT in the
    repair path.

G. 15-MINUTE TIER ANALYSIS  (N2)

G1. DEPENDENCY CHAIN, VERIFIED.
    energy_measurements
      -> ca_energy_1min  (start_offset 2d)      -> energy_consumption_1min  (reconcile 2d)
      -> ca_energy_5min  (start_offset 7d)      -> energy_consumption_5min  (reconcile 7d)
    energy_consumption_1min UNION ALL energy_consumption_5min
      = analytics.v_energy_consumption_native
      -> analytics.v_energy_semantic_rollup_15min  (date_bin 15m, IST origin)
      -> refresh_energy_consumption_15min  ->  analytics.energy_consumption_15min
    [VERIFIED every arrow from the deployed view/function bodies.]

G2. CAN 15min CONTAIN A HOLE OLDER THAN 3 DAYS?  [INFERENCE] YES.
    A late source correction can reach energy_consumption_5min via ca_energy_5min
    up to 7 DAYS back (that CAGG's start_offset, and the reconcile window this
    audit assigns 5min). When the 5min reconciler repairs a 5min row 6 days old,
    the 15min tier must re-roll that 15-minute bucket to reflect it. If the
    15min reconcile_window is only 3 days, the 15min reconciler never revisits
    a bucket 6 days old -> the 5min repair does NOT propagate -> a 15min hole
    older than 3 days persists.
    (The all-60s fleet makes 5min empty TODAY, so this is latent, not active.
    But the design must be correct for a mixed fleet, and 209 already
    provisioned 5min's 7-day reconcile_window on that basis.)

G3. HOW A LATE RECOVERY PROPAGATES.
    energy_measurements backfill @ T
      -> (reconcile step 1) refresh_continuous_aggregate(ca_energy_1min / _5min)
         over [cp - rw, cp)  -- rw >= the CAGG start_offset, so T is covered
      -> (reconcile step 3) refresh_energy_consumption_1min / _5min over the
         mismatching sub-window -> 1min/5min rows corrected
      -> (15min reconcile) detects source_interval_count deficit for the
         affected 15-min buckets -> refresh_energy_consumption_15min re-rolls
      -> (hourly / daily reconcile) same, one level up.
    For this chain to close, EACH tier's reconcile_window must be
    >= max(reconcile_window of every tier it reads).

G4. REQUIRED reconcile_window VALUES  [DESIGN]
      tier                     upstream max reconcile_window   -> required   current   verdict
      ------------------------ ----------------------------- ------------- --------- -------
      energy_consumption_1min  ca_energy_1min start_offset 2d       >= 2d       2d    OK
      energy_consumption_5min  ca_energy_5min start_offset 7d       >= 7d       7d    OK
      energy_consumption_15min max(1min 2d, 5min 7d) = 7d           >= 7d       3d    TOO SMALL -> 8d
      energy_consumption_hourly 15min 8d                            >= 8d      10d    OK
      energy_consumption_daily  15min 8d (daily reads 15min direct) >= 8d      21d    OK (DST margin)
      demand_intervals         raw_messages 48h + routing lag ~ 2d;
                               job-1077 replay backoff 1h+2h+6h    >= 9h       6h    MARGINAL -> see G6
      environment_daily        capture correction deadline (<=24h)
                               + a few days operational slack      >= ~3d     35d    OK (very generous)

G5. RECOMMENDED 15min reconcile_window: 8 DAYS.
    = 7d (deepest upstream, ca_energy_5min start_offset / 5min reconcile) + 1d
    margin. Justification: it is tied to an UPSTREAM RECOVERY BOUNDARY
    (ca_energy_5min start_offset), not an arbitrary number. Cadence stays slow
    (every 6h). Cost: a re-roll of the mismatching 15-min buckets over an 8-day
    trailing window on a 6-hourly cadence -- at fleet size, a few indexed range
    scans; [staging cost check §O #6].

G6. DEMAND reconcile_window: RECONSIDER 6h -> 12h (NOT larger).  [DESIGN]
    6h was set (210) to = the job-1077 raw-replay backoff ceiling (1h+2h+6h).
    But a demand bucket's SOURCE (energy_measurements / normalized_points) can
    itself be corrected by the routing/normalization overlap up to ~2 days back
    if a raw message was merely late (not failed). The demand re-finalisation
    is cheap (status-guarded upsert, VALID rows skipped) and bounded by
    v_max_n = ceil(reconcile_window / demand_interval) + 2. At 12h that is
    ceil(12*3600/900)+2 = 50 iterations per (site x scope) -- still small.
    RECOMMEND 12h. Do NOT exceed 12h without a staging cost measurement
    (§O #7): a wide demand reconcile is the one place this could get expensive.
    reconcile_window for demand stays well inside energy_measurements 90d
    retention, so ground truth is always available.

H. ENVIRONMENT_DAILY COMPLETENESS ANALYSIS
===============================================================================

H1. VERIFIED 211 SEMANTICS (recap from §B9). refresh_environment_daily reads
    environment_measurements directly; site-local calendar days; DST-aware via
    AT TIME ZONE metadata.sites.timezone; complete-days-only
    (local_day_end <= p_to); a day with zero source rows for a device produces
    NO row; ON CONFLICT (device_id, bucket_start) DO UPDATE.

H2. IS max(bucket_start) ENOUGH TO ESTABLISH COMPLETENESS?  [INFERENCE] NO --
    for the same reason as demand: max() is a fleet-wide scalar. A local day D
    for device X can be finalised (D's local_day_end <= watermark, which is
    gated on the FLEET max minus grace) while device X itself sent nothing (or
    only a few buckets) on day D because it was offline mid-day. The row for
    (X, D) would then be absent (X sent nothing) or present with an implausibly
    low sample_count (X sent a few buckets). If X's buckets for day D arrive
    LATE (after the watermark passed D + overlap 1d), 211 alone never revisits
    D for X.

H3. CAN A LOCAL DAY BE FINALISED WITH AN INTERNAL BUCKET MISSING?  [FACT] YES.
    refresh_environment_daily does GROUP BY (device, local-day) with
    COUNT(*)/AVG()/MIN()/MAX() over WHATEVER buckets are present. It does not
    check for internal gaps. sample_count on the row is simply "how many buckets
    we had". There is no expected-count column and no gap flag.

H4. HOW SHOULD RECONCILIATION DETECT THIS?  [DESIGN] A PLAUSIBILITY rule, not a
    hard completeness proof:
    reconcile_environment_daily(P):
      v_cp := pipeline_state('environment_daily').last_received_at   -- never advanced
      v_ws := v_cp - reconcile_window(P='environment_daily')          -- 35d (keep)
      FOR each (device, local-day D) with an environment_daily row where
              D's bucket_start (local midnight in UTC) in [v_ws, v_cp):
        -- expected buckets for D for this device's site:
        v_expected := (seconds in D's local day) / site's capture_interval_seconds
        -- actual source buckets NOW present for D for this device:
        SELECT count(*) FROM telemetry.environment_measurements
          WHERE device_id = D.device_id
            AND bucket_start >= D.local_day_start AND bucket_start < D.local_day_end
          -> v_source_now
        IF v_source_now > environment_daily.sample_count
           OR (environment_daily.sample_count < v_expected * <plausibility_frac>
               AND v_source_now > environment_daily.sample_count) THEN
          -- late buckets have arrived OR the row is thin and more source exists:
          v_changed := telemetry.refresh_environment_daily(D.local_day_start,
                                                           D.local_day_end);
        END IF
      END FOR
      -- ALSO: (device, site) pairs that SHOULD have a row for a day in the
      -- window but have NONE, while environment_measurements now has buckets:
      FOR each (device, D) with source buckets in [v_ws, v_cp) and NO
              environment_daily row -> refresh_environment_daily(D range).
      log to pipeline_reconciliation_log.
    plausibility_frac: [DESIGN] start at NULL (i.e. only repair on the
    "v_source_now > sample_count" condition -- a strict, false-positive-free
    signal). Add the thin-row fraction check only if staging evidence (§O #11)
    shows genuine thin-day under-reporting; a fraction like 0.5 would then flag
    days with < 50% of expected buckets that also have more source available.
    Do NOT auto-"repair" a genuinely thin day (device really was offline) --
    re-running refresh over it just rewrites the same thin row (0 rows_changed);
    that is harmless but noisy, hence gate on "v_source_now > sample_count".

H5. DOES 212/213 NEED A COMPLETENESS RULE FOR environment_daily?  [DESIGN] YES,
    the STRICT form only: "environment_measurements now has more buckets for
    (device, local-day) than the row's sample_count" -> re-run. This catches
    late-arriving environment buckets for an already-finalised day, which is
    the real, common case. The thin-day plausibility fraction is OPTIONAL and
    gated on staging evidence. NEITHER changes refresh_environment_daily.

H6. reconcile_window for environment_daily: KEEP 35 DAYS.
    environment_measurements retention is 1 YEAR, so ground truth is available
    far past 35d. 35d covers any realistic late-arrival + operator-backfill
    horizon for a historian with no live consumer. Cadence: every 24h.

I. DEMAND RECONCILIATION SEMANTICS

I1. WHAT RECONCILIATION MUST DO, PER TRANSITION.  [DESIGN, consistent with 210]
    The reconciler for demand_intervals calls, over its trailing window
    [cp - reconcile_window, cp)  (cp = pipeline_state('demand_intervals')
    .last_received_at, NEVER advanced):

      CALL analytics.refresh_demand_analytics(
             p_now          => clock_timestamp(),      -- keeps live demand_state current
             p_lookback     => <the job's lookback>,   -- irrelevant to the finalize loop here
             p_finalize_from => cp - reconcile_window,
             p_finalize_to   => cp);

    This is EXACTLY the migration-210 re-finalisation path (test T-Refin-E
    proved it repairs a hole WITHOUT moving the watermark). Per transition:

      NO_DATA  -> INCOMPLETE : allowed. refresh recomputes; the 210 status-guard
                               (quality_status <> 'VALID' AND (... IS DISTINCT
                               FROM ...)) fires because quality_status changes.
      NO_DATA  -> VALID      : allowed. same guard.
      INCOMPLETE -> VALID    : allowed. same guard.
      existing VALID         : FROZEN. The guard's  quality_status <> 'VALID'
                               predicate makes the DO UPDATE a no-op. VALID
                               never regresses. [VERIFIED 210 guard]
      stale / non-finalised  : a row that is non-VALID and whose recomputed
                               values now differ -> DO UPDATE (finalized_at
                               moves). A row whose recompute is identical ->
                               0 rows (IS DISTINCT FROM all-false) -> no churn.
      late-arriving source    : the reason the recompute now differs; handled by
                               the above.
      SITE scope              : refresh_demand_analytics branches on
                               v_scope.scope_type='SITE' and targets
                               ON CONFLICT (site_id, interval_start,
                               demand_policy_id) WHERE scope_type='SITE'.
      ASSET scope             : the ELSE branch targets ON CONFLICT (asset_id,
                               interval_start, demand_policy_id) WHERE
                               scope_type='ASSET'.
    The reconciler does NOT write its own INSERT/ON CONFLICT -- it calls
    refresh_demand_analytics, which already contains the two correct
    scope-branched partial-index upserts. The task's warning ("do NOT introduce
    a generic ON CONFLICT that cannot target the two partial indexes") is
    satisfied by NOT writing one at all.

I2. VALID-NON-REGRESSION PROOF.  [VERIFIED via 210 code + test]
    The DO UPDATE WHERE clause is
      analytics.demand_intervals.quality_status <> 'VALID'
      AND ( 5x IS DISTINCT FROM guards ).
    For an existing VALID row the first conjunct is FALSE => the row is not
    updated, regardless of what the recompute produced. Reconciliation cannot
    downgrade a VALID row. (Test assert_demand_watermark_refinalization T-Refin-A
    and T-K already assert this for the forward path; the reconcile path uses
    the identical function.)

I3. demand_state IS NOT TOUCHED by reconciliation.  [DESIGN]
    refresh_demand_analytics's live demand_state block is keyed to p_now =
    clock_timestamp(); with p_finalize_from/to bounding ONLY the historical
    loop, a reconcile call over an old window updates demand_state for the
    CURRENT interval only (same as any normal call) -- it does not replay
    historical demand_state. [VERIFIED 210 design; test T-DS].

I4. reconcile_window for demand: 12h (see §G6). Cadence: every 1h.

J. PROPOSED 212->213 RECONCILIATION ARCHITECTURE
===============================================================================

J1. SHAPE. ONE new schema object family, NO new pipeline:
      analytics.pipeline_reconciliation_log   -- table (§K)
      analytics.reconcile_energy_consumption_1min(config jsonb)   -- proc
      analytics.reconcile_energy_consumption_5min(config jsonb)
      analytics.reconcile_energy_consumption_15min(config jsonb)
      analytics.reconcile_energy_consumption_hourly(config jsonb)
      analytics.reconcile_energy_consumption_daily(config jsonb)
      analytics.reconcile_demand_intervals(config jsonb)
      analytics.reconcile_environment_daily(config jsonb)
    Each is a THIN wrapper: read the tier's checkpoint (never write it), compute
    a bounded trailing window, run a cheap per-coarse-bucket deficit detector,
    call the tier's EXISTING refresh_* over only the mismatching sub-windows,
    write ONE pipeline_reconciliation_log row. Registered as TimescaleDB jobs.

J2. ONE JOB OR MANY?  [DESIGN] MANY -- one reconcile job per tier.
    Rationale:
      - A single job calling every tier in sequence means one bad/slow tier
        (e.g. a large demand reconcile) starves the others and blows one
        max_runtime budget for the whole cascade. The task explicitly requires
        "one bad tier does not prevent other tiers from reconciling".
      - Per-tier jobs let each have its own cadence (1min:1h, 5min:1h, 15min:6h,
        hourly:12h, daily:24h, demand:1h, environment_daily:24h) and its own
        max_runtime.
      - Per-tier jobs each take THAT TIER's advisory lock (the same key the
        normal job uses) so a reconcile can never run concurrently with the
        normal forward job for the same tier -- it gets SKIPPED_LOCKED and
        retries next cadence. Different tiers are independent.
    Cost: 7 more scheduler slots. At a 1h-24h cadence that is negligible.
    A single "dispatcher" job that PERFORMs each reconcile_* in turn is an
    acceptable ALTERNATIVE only if wrapped so that one tier's EXCEPTION is
    caught, logged, and the loop continues -- but that reintroduces the
    "second pipeline / CALL chain" smell the task warns against. Prefer 7 jobs.

J3. BOUNDED WORK PER RUN.  [DESIGN]
      - reconcile window = [cp - reconcile_window(tier), cp). cp is the tier's
        OWN checkpoint; the window is ENTIRELY at or below the HWM. It never
        looks forward. (The old design's [cp - rw, cp) IS retained for the
        window bounds -- what changes is that a blind refresh over it is
        replaced by a detector + targeted sub-window repair, and for CAGG-fed
        tiers a bounded refresh_continuous_aggregate precedes it.)
      - coarse detector bucket = 1 hour (energy tiers), 1 day (daily / env),
        15/30 min (demand). MAX coarse buckets per run =
        reconcile_window / coarse_bucket: 1min = 8d? no -- 1min rw = 2d /1h = 48;
        5min = 7d/1h = 168; 15min = 8d/1h = 192; hourly = 10d/1h = 240;
        daily = 21d/1d = 21; demand = 12h / 15min = 48; env = 35d/1d = 35.
        Each coarse-bucket check = 2-3 indexed COUNT() range scans. Even 240
        of them is sub-second. [INFERENCE; staging cost check §O #6]
      - MAX refresh_* sub-window invocations per run = number of MISMATCHING
        coarse buckets. In steady state = 0. After an incident = a handful.
        Hard cap [DESIGN]: if > <N_max> (e.g. 24) coarse buckets mismatch,
        repair the first N_max, log outcome='PARTIAL', and let the next cadence
        continue -- so a massive backlog cannot make one reconcile run exceed
        max_runtime. The normal forward job + successive reconcile runs drain
        the rest.
      - reconcile jobs do NOT recompute healthy rows: the detector's
        src==chi comparison skips them at count-read cost only.

J4. TRANSACTION BOUNDARIES / FAILURE.  [DESIGN]
      - Each reconcile_* proc body is ONE transaction (like the refresh_* it
        calls). No intermediate COMMIT.
      - It owns NO watermark. It never UPDATEs pipeline_state.last_received_at.
        (It MAY write pipeline_state.last_reconcile_at / last_reconcile_rows --
        see §I/§K -- but those are advisory metadata, not a processing
        checkpoint, and a failure that rolls them back is harmless.)
      - EXCEPTION WHEN OTHERS -> write a pipeline_reconciliation_log row with
        outcome='FAILED' and SQLSTATE/SQLERRM, then RAISE (so the job runner
        records the failure and consecutive_failures climbs -> §J alert).
        Because the whole txn rolls back, the FAILED log row is also rolled
        back UNLESS written via a subtransaction; DESIGN: wrap the refresh_*
        calls in a BEGIN ... EXCEPTION block that captures the error into a
        variable, then write the log row OUTSIDE that block and re-RAISE.
        (This mirrors migration 203's per-candidate pattern -- proven.)
      - advisory lock: pg_try_advisory_xact_lock(hashtextextended(
        '<the tier's normal job proc name>', 0)). On miss: log outcome=
        'SKIPPED_LOCKED', rows_repaired=0, RETURN. NO analytical work is done
        on the skip path.

J5. ORDERING.  [DESIGN] Bottom-up, but via CADENCE not a CALL chain:
      1min/5min reconcile every 1h  (fastest; feeds 15min)
      15min reconcile every 6h
      hourly reconcile every 12h
      daily reconcile every 24h
      demand reconcile every 1h  (independent parent -- energy_measurements)
      environment_daily reconcile every 24h  (independent parent)
    A 1min repair at 02:00 is picked up by the 15min reconcile at its next
    06:00 slot, then hourly at 12:00, then daily at 24:00. Eventual, bounded,
    self-consistent. No tier waits on another within a single run.

J6. IDEMPOTENCY.  [INFERENCE] Every refresh_* is an idempotent ON CONFLICT DO
    UPDATE; every reconcile_* only calls refresh_* on sub-windows that FAIL the
    src==chi check, and a repaired sub-window passes the check on the next run.
    Two reconcile runs back-to-back: the second finds everything healthy and
    does 0 writes, logs rows_repaired=0.

J7. TENANT ISOLATION.  [INFERENCE] reconcile_* passes only (from, to) to
    refresh_*, which writes org_id/site_id from the source rows exactly as the
    forward path does. The detector's COUNT()s are not org-filtered (they are
    tier-global time-range counts) but they only DECIDE whether to re-drive a
    time sub-window; the re-drive itself is org-correct. No cross-org write is
    possible that the forward path does not already make.

J8. OBSERVABILITY: pipeline_reconciliation_log (§K) + v_pipeline_health (§L) +
    the existing timescaledb_information.job_stats.consecutive_failures on the
    reconcile jobs. Alert conditions (from the old design, retained):
      - rows_repaired > noise_floor on the SAME tier for >= 3 consecutive
        reconcile runs  => persistent upstream problem, not a one-off.
      - a detected deficit for a coarse bucket OLDER than reconcile_window
        (surfaced by v_pipeline_health) => self-repair impossible; manual
        widened refresh_* needed.
      - reconcile job consecutive_failures >= 3.

J9. WHAT 213 EXPLICITLY DOES NOT DO.
      - no message broker, no queue table, no external supervisor, no CALL
        chain between tiers, no replacement of any refresh_* function, no
        Grafana change, no calculation-semantics change.
      - no advancement of any pipeline_state.last_received_at.
      - no reconciliation of the routing/normalization tiers.
      - no retention changes (§K stays separate).
      - no change to CAGG refresh policies (the bounded manual
        refresh_continuous_aggregate call in F4 step 1 is an INVOCATION of an
        existing function over an explicit range, not a policy change).

M. FAILURE / FALSE-ADVANCE PROOF
===============================================================================

M1. WATERMARK-DRIVEN TIERS (209/210/211) -- the invariant, re-proven per kill point.
    Common structure (all 7): advisory lock -> [SKIPPED_LOCKED + RETURN on miss]
    -> read cp FOR UPDATE -> RUNNING -> derive [v_from, v_to) -> [NO_SOURCE_DATA
    + RETURN if v_to <= v_start] -> CALL refresh_*(...) -> UPDATE pipeline_state
    SET last_received_at = v_to (LAST write) -> [EXCEPTION -> FAILED -> RAISE].
    The whole body is ONE job transaction.

      killed BEFORE refresh          : txn aborts. RUNNING write rolled back.
                                       last_received_at unchanged. [INFERENCE from
                                       structure; VERIFIED by 209/210/211 tests
                                       T-*-fail]
      killed DURING refresh          : partial target-table writes are in the
                                       same txn -> rolled back. last_received_at
                                       unchanged.
      killed immediately BEFORE the  : the checkpoint UPDATE never ran; txn
        checkpoint UPDATE            : aborts; every target write in the run
                                       rolls back. Retry reprocesses [v_from,v_to).
      timed out (max_runtime)        : TimescaleDB cancels the backend =>
                                       statement error => txn abort => as above.
      fails after partial target rows: EXCEPTION handler sets FAILED (still in
                                       the txn) then RAISE => txn abort => the
                                       FAILED write AND the partial rows AND the
                                       checkpoint all roll back. Net: nothing
                                       moved. (last_status may briefly show FAILED
                                       only if the job runner commits the handler
                                       write before re-raising -- it does not;
                                       RAISE propagates and aborts.)
      concurrent invocation          : second caller's pg_try_advisory_xact_lock
                                       fails -> SKIPPED_LOCKED -> RETURN. No read
                                       of cp FOR UPDATE, no refresh, no write.
      rerun same window              : refresh_* is ON CONFLICT DO UPDATE with
                                       "IS DISTINCT FROM" guards (energy/demand)
                                       or unconditional idempotent recompute
                                       (env) -> same output; checkpoint set to
                                       the same v_to. No drift.

M2. RECONCILIATION (213) -- the required proofs.
      never advances pipeline_state.last_received_at : the reconcile_* procs
        contain NO  UPDATE telemetry.pipeline_state SET last_received_at  --
        by construction. (An assertion in the test suite greps the deployed
        bodies for this and fails if present -- §N.)
      failure cannot corrupt the checkpoint : reconcile owns no checkpoint. Its
        only pipeline_state write (optional) is last_reconcile_at/rows, advisory
        metadata; a rollback of it loses only a log annotation, and the
        pipeline_reconciliation_log row (written in a subtransaction-guarded
        step, §J4) records the FAILED outcome.
      repeated reconciliation is idempotent : proven in J6 -- detector finds
        src==chi on the second pass, 0 refresh_* calls, rows_repaired=0.
      a repair does not create a false "healthy" state : a repair only writes
        via refresh_*, which sets the child's source-count fingerprint to the
        CURRENT source value; the NEXT detector pass re-reads source and child
        and confirms src==chi. If source changes again, the next pass repairs
        again. "healthy" is always re-derived from live counts, never asserted.
      SKIPPED_LOCKED does no analytical work : the reconcile proc's first action
        after computing the window is pg_try_advisory_xact_lock; on miss it
        writes one log row (outcome='SKIPPED_LOCKED', rows_*=0) and RETURNs
        before any COUNT() detector or refresh_* call.
      concurrent with the normal forward job : same advisory-lock key => exactly
        one of {forward job, reconcile job} runs at a time for a given tier;
        the other SKIPPED_LOCKED and retries next cadence. Neither corrupts the
        other. A reconcile that loses the race simply runs next cadence over a
        window that now includes the forward job's fresh work -- still correct.

M3. CAGG bounded refresh_continuous_aggregate (F4 step 1) failure : it is its
    own statement inside the reconcile txn; if it errors, the whole reconcile
    txn aborts, nothing is written except (subtxn-guarded) the FAILED log row.
    It cannot leave the CAGG in a partial state (TimescaleDB refresh is
    transactional per invocation).

P. RETENTION / STORAGE IMPLICATIONS  (do NOT implement here)

CORRECTNESS / RECOVERY (relevant to N1/213 -- state, do not fix):
  P1. raw_messages retention 48h [VERIFIED]. This is the HARD floor on how far
      back a FAILED raw message can be recovered (job 1077). It does NOT limit
      213's reconcile windows because 213 reconciles ANALYTICAL tiers against
      energy_measurements/ca_energy_* (retention 90d/180d) and
      environment_measurements (1y), not against raw. But it DOES mean a
      demand/energy hole caused by a raw message lost > 48h ago is
      IRRECOVERABLE by any mechanism -- v_pipeline_health should surface such a
      deficit as an ALERT (older than reconcile_window), not a silent repair
      attempt. The standing recommendation (48h -> 7d) would widen the
      recoverable horizon; it is a SEPARATE migration and a broker/disk
      trade-off, not required for 213 correctness.
  P2. energy_measurements retention 90d, ca_energy_1min 180d, ca_energy_5min 2y.
      213's energy reconcile_windows (2d/7d/8d/10d/21d) are all far inside 90d
      => ground truth always present. No change needed for correctness.
  P3. environment_measurements retention 1y; env_daily reconcile_window 35d.
      Fine.

STORAGE HYGIENE (out of scope for N1/213; own future migrations):
  P4. normalized_points compression AFTER 1 DAY [VERIFIED]. Recompute/recovery
      reads on the recent window hit compressed chunks -> slower. Standing rec:
      compress after 7d. Separate migration.
  P5. demand_intervals -- PLAIN table, no retention/compression [VERIFIED].
      Grows one row per (site, 15/30-min bucket, scope, policy) forever.
      Standing rec: ~3y retention. Because it is a plain table (not a
      hypertable), this needs either conversion to a hypertable + drop policy,
      or a scheduled DELETE job. Separate migration; NOT 213.
  P6. capture_bucket_samples -- PLAIN table, no policy [VERIFIED]. One row per
      (site, bucket, device) selected for normalization, forever. This is the
      largest latent unbounded-plain-table risk. Standing rec: application-level
      pruning (e.g. delete rows whose bucket_start < now() - 30d and status IN
      ('NORMALIZED','FAILED')). Separate migration.
  P7. energy_consumption_daily / environment_daily -- no retention (compression
      only). Standing rec: ~5y retention each. Separate migration.
  P8. pipeline_reconciliation_log (NEW in 213) -- retention IS included in 213
      (hypertable, drop_after 400d) per §K3, because an unbounded new log table
      would be self-defeating.

RULE: 212 and 213 change NO retention or compression policy on any EXISTING
