Part B — Detailed lineage for the important metrics

1. Energy Consumption (kWh) — the most-implemented metric in the platform

Business meaning: interval energy delivered (import) or exported, in kWh, derived from a cumulative meter register.

Three parallel, non-identical implementations were traced, all ultimately calling the same primitive classifier but assembled differently:

(A) Path A — "general classifier" view, analytics.v_energy_consumption_15min
- Source: telemetry.ca_energy_15min (raw MAX/MIN register CAGG) → CROSS JOIN LATERAL analytics.classify_energy_register_delta(...), gap threshold resolved live via config.resolve_interval_quality_rule(device_id, bucket_start).
- Timestamp: bucket_start (UTC-aligned, received_at-keyed CAGG).
- Tenant scope: metadata.grafana_organization_map join → grafana_org_id.
- Quality: full vocabulary (GOOD/GAP/RESET/RESET_FROM_ZERO/ROLLOVER/ROLLOVER_UNRESOLVED/DIRECTION_ERROR/IMPLAUSIBLE_DELTA/CONFIG_MISSING/CONFIG_INVALID/MISSING_REGISTER/INITIAL) attached per import/export.
- Feeds: v_energy_consumption_daily's pre-036 implementation (superseded), v_site_energy_balance_daily, v_energy_demand_15min-adjacent KPI family. Granted to grafana_reader but no panel in the 7 read dashboards queries it directly.

(B) Path B — "semantic reporting" pipeline
- Source: persisted analytics.energy_consumption_1min/5min (already-classified, populated by scheduled jobs, classify_energy_register_delta called once at native resolution) → v_energy_consumption_native → v_energy_semantic_rollup_5min/15min → v_energy_reporting_5min/15min/hourly/daily.
- Never reclassifies; every rollup only sums WHERE is_valid, counts gap/reset/rollover/invalid intervals separately, derives a quality_status by priority (INVALID_INTERVALS > RESET_DETECTED > GAPS_DETECTED > ROLLOVER_DETECTED > GOOD).
- Timezone: hourly/daily tiers use site-local time (bucket_start AT TIME ZONE s.timezone), explicitly fixed for DST-naive fixed-offset zones only (documented limitation).
- Access: ems_admin-only except v_energy_consumption_daily (migration 036 cutover, Grafana-granted).
- Exposed externally only via analytics.get_canonical_energy_read() — tenant/asset resolved, capture-policy-boundary-guarded (twice patched for false positives, migrations 191/192), dispatches by actual duration to native/5m/15m/hourly/daily. The auto-router (resolve_grafana_energy_routing_resolution, migration 045) never selects '1d' — the daily tier is reachable only by an explicit direct call, and none was found in the app or dashboard layer.

(C) Path C — asset-overview's own function, analytics.get_grafana_asset_energy_intervals
- Reads telemetry.energy_measurements directly (not through any CAGG), resolves one prior sample before p_from plus all in-range samples, computes LAG()-based deltas, classifies via the same classify_energy_register_delta() function, restricted to the asset's PRIMARY_METER device only.
- This is the actual source of the Asset Dashboard's "Total Energy vs previous period" and "Energy Consumption Trend" panels (confirmed by migration 191/192 incident narratives naming these panels explicitly).
- This is a third, independently-written implementation of the identical calculation (register delta + classifier), not a call into either Path A or Path B. It duplicates the LAG/classify logic rather than reading a shared view.

(D) A fourth, much simpler thing that is not consumption but is easily mistaken for it: v_grafana_energy_samples.import_energy_register_kwh / export_energy_register_kwh and v_grafana_asset_electrical_samples's identically-named columns are the raw cumulative register value ÷1000, with no delta and no classification — a different metric wearing a similar name.

(E) A fifth, ad hoc implementation: the Analytics Explorer dashboard computes GREATEST(0, MAX(value) − LAG(MAX(value))) directly in its panel SQL for any point matching %ENERGY%, over analytics.generic_telemetry_15m/1h (a generic, non-energy-specific point CAGG) — no register-semantics lookup, no reset/rollover handling, no quality code. This is the one place where "energy consumption" is computed with materially weaker guarantees than everywhere else in the platform.

Classification: metric calculated in (at least) five places, with materially different quality guarantees; A/B/C are functionally equivalent in intent but structurally independent implementations — a change to the classifier's calling convention would need to be replicated in three places, not one.

2. Instantaneous Power (kW / kvar / kVA)

- Single source of truth: telemetry.energy_measurements.active/reactive/apparent_power_total_w (+ per-phase).
- Aggregated identically (AVG/MIN/MAX) across all raw CAGGs (ca_energy_1min/5min/15min/hourly/daily) — one calculation, five resolutions, no divergence found.
- Converted to kW at the Grafana view layer only (÷1000.0), in v_grafana_asset_electrical_samples and v_grafana_energy_samples — conversion factor consistent across both.
- Not flagged as multiply-implemented — the divergence problem starts one layer up, in what gets labeled demand (§3).
