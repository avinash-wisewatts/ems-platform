A. EXECUTIVE VERDICT
===============================================================================

The Phase 2 investigation's diagnosis holds under repository proof. The
recommended architecture (child watermark + bounded catch-up + bounded
reconciliation, Option D) is correct and should proceed. This document adds the
implementation-grade detail the investigation deferred, and surfaces four
findings not called out sharply enough there:

  1. [FACT] NONE of the seven analytics-tier procedures
     (run_/refresh_ × energy_consumption_{1min,5min,15min,hourly,daily} +
     demand + environment_daily) take an advisory lock or touch pipeline_state.
     The three telemetry loaders all do
     (pg_try_advisory_xact_lock + pipeline_state RUNNING/SUCCESS/FAILED).
     Combined with max_runtime = 00:00:00 (unlimited) and max_retries = -1
     (infinite) on every analytics job, a single slow run silently overruns
     its 1-minute schedule and a second worker begins processing the SAME
     window concurrently — wasted work at best, row-lock deadlock or
     double-counted provisional demand at worst. Self-overlap protection is a
     prerequisite for everything else in Phase 2, not an afterthought.

  2. [FACT] Jobs 1001 (run_energy_routing_job → load_energy_measurements_
     incremental) and 1012 (run_environment_routing_job →
     load_environment_measurements_incremental) retain the exact
     unbounded-forward shape that stalled job 1000 before migration 205.
     PROOF below (§D). This is a latent repeat of the original incident one
     hop downstream and must be fixed in the FIRST implementation phase,
     before any analytics-tier work.

  3. [FACT] telemetry.capture_bucket_samples — written on every normalization
     run, one row per (site,bucket,device) with status lifecycle
     SELECTED/NORMALIZED/FAILED — is a PLAIN TABLE (not a hypertable), has NO
     retention/compression policy, and nothing in the application prunes it
     (only test scripts DELETE from it). Unbounded growth on the hot
     normalization path. Not in the Phase 2 retention matrix; added here.

  4. [FACT/INFERENCE] The energy CAGGs are NOT redundant with the persisted
     analytics.energy_consumption_* tables — Phase 1E already proved they are
     distinct lineages (raw time-bucket aggregation vs register-delta
     classification with quality). But ca_energy_15min/hourly/daily are read
     DIRECTLY by Grafana tenant-analytics views (postgres/ddl/55) as well as
     by the semantic layer, so their materialized_only=true + start_offset
     (2d/7d/30d) freshness cliff is a Grafana-facing risk, not only an
     internal one.

FIRST PHASE TO IMPLEMENT: Phase 0 (telemetry-routing hardening — p_max_window on
1001/1012 + self-overlap-safe bounded scheduled behaviour) + Phase 0b (job
hardening: real max_runtime / finite max_retries / advisory lock on the analytics
tier). These are small, low-risk, independently valuable, and are preconditions
for the watermark work. Full phase plan in §Q.

E. PROPOSED CANONICAL WATERMARK MODEL
===============================================================================

STORE: reuse telemetry.pipeline_state, unchanged schema, one new row per
analytical pipeline. [RECOMMENDATION] Rationale: (a) postgres/ddl/41's own
header comment declares it for "future pipelines"; (b) it already holds 5
non-normalization rows; (c) a second store (analytics.pipeline_state mirror)
duplicates a table + its tests for zero functional gain. Decision to confirm
with a reviewer, not assume — but the default is reuse. [UNKNOWN] whether any
analytics-schema isolation convention forbids an analytics proc writing
telemetry.pipeline_state (grep found no such rule; §"staging queries").

New rows (pipeline_name):
  energy_consumption_1min, energy_consumption_5min, energy_consumption_15min,
  energy_consumption_hourly, energy_consumption_daily,
  demand_intervals, environment_daily

TWO DISTINCT TIMESTAMPS per pipeline P with immediate source(s) S:

  parent_available_through(P)
    = the point up to which every S has DURABLY finished producing rows that P
      consumes. It is READ live each run, NEVER stored on P. Sources:
        S is a telemetry pipeline  → pipeline_state(S).last_received_at
        S is a native CAGG         → to_timestamp(continuous_aggs_watermark(S))
        S is a persisted analytics tier → pipeline_state(S).last_received_at
                                          (that tier's own child watermark)
      For a tier with several sources, parent_available_through =
        LEAST(over all S).
    Meaning of the timestamp: it is a BUCKET-TIME boundary (event_time /
      bucket_start), NOT an ingest time. (The telemetry tier stores an ingest
      time in last_received_at; the analytics tier must store a bucket-time.
      They share a column name and a table, not a semantic — documented
      explicitly to prevent a future reader assuming uniformity.)

  child_processed_through(P)  [stored in pipeline_state(P).last_received_at]
    = the exclusive upper bound of the CONTIGUOUS bucket-time range P has
      durably written. P has processed every bucket in
      [<floor>, child_processed_through(P)); it has processed NOTHING at or
      after it. Advanced ONLY by P's own successful run, ONLY in the same
      transaction as the writes it accounts for, ONLY to the end of the slice
      actually committed (§F rule R2/R3).

  last_status / last_error / last_started_at / last_completed_at /
  last_inserted_rows — used exactly as the telemetry tier uses them
  (RUNNING on entry; SUCCESS/FAILED/SKIPPED_LOCKED/NO_SOURCE_DATA on exit).

INITIALISATION: on first run (row absent or last_received_at NULL),
  child_processed_through := date_bin(<tier resolution>, now()) - <tier floor>
  where <tier floor> = the current lookback constant (30m / 2h / 2d / 8d / 3h).
  I.e. the wall-clock lookback becomes the ONE-TIME cold-start floor and is
  never used again.

INVARIANT (the whole point): parent_available_through is an input; a parent
value is never assigned to child_processed_through. A parent racing ahead
(09:00→12:00) while the child is stuck at 10:00 simply widens
outstanding(P) = (10:00, min(parent_available_through, now_binned)]; the child
drains it over bounded runs (§F). No data is lost because the child's own
checkpoint is durable and only moves for committed work.

F. PROPOSED BOUNDED CATCH-UP MODEL
===============================================================================

Per run of pipeline P (inside the advisory lock, §J):

  v_res      := <tier bucket width>            -- 1m,5m,15m,1h,1d, or demand interval
  v_overlap  := <tier overlap>                 -- boundary-race guard (see table)
  v_maxwin   := <tier max_catchup_window>      -- NEW config key, per tier
  v_ckpt     := pipeline_state(P).last_received_at        -- child_processed_through
  v_parent   := <LEAST over sources, §E>                  -- parent_available_through
  v_to       := LEAST(date_bin(v_res, clock_timestamp()), v_parent)
  v_to       := LEAST(v_to, v_ckpt + v_maxwin)            -- BOUND per-run work
  IF v_to <= v_ckpt THEN mark NO_SOURCE_DATA / SUCCESS(no-op); RETURN; END IF
  v_from     := v_ckpt - v_overlap                        -- small re-scan
  PERFORM <tier>.refresh_*(v_from, v_to)                  -- existing math, unchanged
  UPDATE pipeline_state(P) SET last_received_at = v_to,   -- advance == last write
    last_status='SUCCESS', last_inserted_rows=<n>, ... ;  -- SAME transaction
  -- EXCEPTION WHEN OTHERS: SET last_status='FAILED', last_error=...; RAISE;
  --   ⇒ refresh writes AND the watermark advance roll back together.

RULES:
  R1  parent value read, never written to the child.
  R2  advance is monotonic and CONTIGUOUS from v_ckpt forward; a run never
      advances past a sub-range it did not commit; never "newest-first then max()".
  R3  the advance UPDATE is the final write in the slice's transaction.
  R4  overlap covers just-closed buckets + boundary races only; v_maxwin bounds
      cost; the lookback constant survives only as the cold-start floor.
  R5  a run that is cancelled (max_runtime) or crashes loses at most one slice
      (≤ v_maxwin of work); the watermark did not move; next run retries the
      same slice.

PER-TIER PARAMETERS  [RECOMMENDATION; [UNKNOWN] production scale — see caveat]

  Assumed scale for sizing: [UNKNOWN, from Phase 0/1] ~10-50 energy meters at
  60s capture on staging today; design headroom to ~1,000 devices. Cost driver
  per tier is NOT row count (small) but the per-bucket LATERAL previous-eligible-
  bucket lookup + classifier calls (1min), the view recompute (15min), and the

  SIZING RATIONALE:
   - 1min tiers @ 2h: 120 device-buckets/device/run. At 1,000 devices = 120k
     rows + 120k LATERAL lookups; well inside 5 min even pessimistically. 2h
     drains a full-day outage in 12 one-minute ticks. Going to 6h would drain
     faster but risks brushing 5 min at scale — 2h is the safe knee.
   - 15min @ 6h: 24 buckets/device; the cost is the semantic-rollup view
     recompute over the window, which is O(window). 6h keeps that bounded;
     drains a day in 4 runs.
   - hourly @ 2d, daily @ 8d: these tiers read the small persisted 15min table
     and sum additively; 2d = 48 rows/device, 8d = 8 rows/device — trivial;
     the generous window means a week-long hourly outage self-heals in ~4 runs
     and daily in 1. Keep the current constants as the window.
   - demand @ 3h initially (= today's lookback, so behaviour is unchanged until
     an outage), then raise to 6-12h once staging run-duration is measured
     (§"staging queries" #5). The inner loop cost is ceil(window/15m) ×
     (#sites + #assets) × calculate_demand_window(); at 3h that is 12 ×
     scope-count iterations — measure before widening.
   - energy/environment routing: the SCHEDULED job should pass a bounded
     p_max_window (2h), NOT NULL. [DISAGREEMENT with Phase 2 — see §"disagreements".]

     over successive 1-min ticks (15h → ~8 ticks → ~8 min) with no operator.
     NULL / a wider manual value (30m chunks, as used in the incident) remains
     available for deliberate operator-driven catch-up.

STEADY STATE: v_ckpt tracks now_binned, so [v_from, v_to) is one bucket wide
every run — identical cost to today. The bound only engages after a gap.

G. PROPOSED CASCADE DEPENDENCY MODEL

Each tier's parent_available_through is the LEAST of its IMMEDIATE sources'
durable-through marks — never wall clock, never a grand-parent:

  energy_consumption_1min.parent_available_through
     = to_timestamp(continuous_aggs_watermark(ca_energy_1min))
  energy_consumption_5min.parent_available_through
     = to_timestamp(continuous_aggs_watermark(ca_energy_5min))
  energy_consumption_15min.parent_available_through
     = LEAST( pipeline_state('energy_consumption_1min').last_received_at,
              pipeline_state('energy_consumption_5min').last_received_at )
       -- 5min is empty for this fleet; its checkpoint still advances (no-op
       -- runs mark SUCCESS and set last_received_at = v_to), so the LEAST is
       -- driven by 1min in practice but remains correct if 300s sites appear.
  energy_consumption_hourly.parent_available_through
     = pipeline_state('energy_consumption_15min').last_received_at
  energy_consumption_daily.parent_available_through
     = pipeline_state('energy_consumption_15min').last_received_at
       -- plus: clamp v_to to the last COMPLETE site-local day boundary
       -- (a day is only finalised once 15min data through local-midnight+grace
       -- exists) — daily already computes local_day_end; intersect it with
       -- this parent mark.
  demand_intervals.parent_available_through
     = LEAST( pipeline_state('energy_measurements').last_received_at,
              pipeline_state('normalized_points').last_received_at )
       -- demand reads both directly; both must have reached the bucket time.
  environment_daily.parent_available_through
     = LEAST( to_timestamp(continuous_aggs_watermark(ca_environment_15min)),
              to_timestamp(continuous_aggs_watermark(ca_environment_hourly)) )
       -- (pending §"env daily source" confirmation)

CONSEQUENCE: a child can never claim to have processed a range its own input
has not durably reached. The "1min repaired, 15min still stale" class (Phase 2
finding #5) is closed structurally: 15min's v_to cannot exceed 1min's
checkpoint, so when 1min catches up, 15min's outstanding interval automatically
widens and drains on its next runs.

EMPTY-SOURCE HANDLING: a no-op run (v_to <= v_ckpt, or refresh returns 0 rows
because the source genuinely has no data for the slice) still advances
child_processed_through to v_to and marks last_status = 'NO_SOURCE_DATA' (not
FAILED). This is required so downstream LEAST() marks keep moving and so
"empty" is distinguishable from "failed" (§O, §P-pitfall "empty vs failed").

       WHERE analytics.demand_intervals.quality_status <> 'VALID';

   because the table has two PARTIAL unique indexes, not one. [FACT — verified
   the index definitions.]

   Semantics: a row already finalised VALID is immutable. A row finalised
   NO_DATA / INCOMPLETE / INVALID_SOURCE / INSUFFICIENT_SOURCE_RESOLUTION is
   recomputed every pass and UPGRADED the moment real source data exists.

   impossible (guard). A worse→VALID or worse→worse transition is allowed.

   [INFERENCE] safe against the "flapping" risk (a marginal-coverage bucket
   oscillating INCOMPLETE↔VALID across runs): once it reaches VALID it is
   frozen by the guard; before that, each pass can only reflect more data, not
   less, because calculate_demand_window(..., p_final=TRUE) is monotone in
   observed_observations for a fixed interval.

     v_parent := LEAST(pipeline_state('energy_measurements').last_received_at,

   unchanged (it is already mutable and correct). Advance
   child_processed_through to v_to only after the loop commits, same

   The 3h lookback constant becomes v_maxwin_demand's initial value (behaviour
   identical until a gap); reconsideration is then watermark-bounded, not
   pinned to 3h.

I. RECONCILIATION ARCHITECTURE  (critical evaluation of the Phase 2 proposal)
===============================================================================

Phase 2 proposes "a bounded trailing reconciliation pass". Evaluated critically:

WHY A HWM IS INSUFFICIENT ALONE: R2 (contiguous advance) prevents a hole
FORMING below child_processed_through during NORMAL operation. But three cases
still create sub-watermark holes:
  (a) source data arrives LATE, with a bucket_time BELOW child_processed_through,
      after the overlap window has already passed it (energy/environment
      correction_deadline, or a very-late raw replay via job 1077);
  (b) an effective-dated CONFIG change (capture policy, quality rule, register
      semantics) retroactively changes the correct value of already-processed
      buckets;
  (c) a BUG (in a refresh function, or a bad manual intervention) that wrote
      wrong/partial rows that the guard-free DO UPDATE would fix on reprocess
      but that nothing currently reprocesses.
None of these are "trailing backlog"; a HWM cannot see them.

RECOMMENDED MECHANISM — "re-drive the same refresh over a bounded trailing
window, on a slow cadence" — NOT a new comparison engine, NOT a second
pipeline:

  reconcile(P):
    v_win_end   := pipeline_state(P).last_received_at            -- never ahead of the HWM
    v_win_start := v_win_end - <reconcile_window(P)>
    PERFORM <tier>.refresh_*(v_win_start, v_win_end)             -- SAME function, wider bounds
    GET DIAGNOSTICS v_changed = ROW_COUNT
    INSERT INTO analytics.pipeline_reconciliation_log
      (pipeline_name, ran_at, win_start, win_end, rows_changed) VALUES (...)
    IF v_changed > <noise_floor(P)> THEN  RAISE WARNING / emit metric  END IF

  This is defensible because EVERY tier writer is idempotent DO UPDATE (demand
  becomes so via §H). Re-running a clean window changes 0 rows (cost = an
  indexed range scan on bucket_start, which the refresh functions already do).
  Re-running a window with a stale/late/mis-config'd bucket corrects exactly
  those rows and reports the count.

WHICH TABLES NEED IT:
  energy_consumption_1min ...... YES (late corrections + config changes)
  energy_consumption_5min ...... NO (empty)
  energy_consumption_15min ..... YES (inherits 1min corrections; view recompute)
  energy_consumption_hourly .... YES (inherits 15min)
  energy_consumption_daily ..... YES (inherits 15min; DST/local-midnight edge)
  demand_intervals ............. YES (late raw replay is the exact incident class)
  environment_daily ............ YES (low risk but cheap)
  telemetry routing (1000/1001/1012) ... NO — they already re-scan an overlap
    every run and their watermark rolls back atomically on failure, so R2 holds
    and (a)/(c) are handled by the existing overlap; (b) config changes at that
    tier are already covered by the effective-policy lookback logic
    (migration 129). Adding reconciliation there would be the "second pipeline"
    the task warns against.

CADENCE / LOOKBACK  [RECOMMENDATION]:
  tier                 reconcile cadence   reconcile_window   rationale
  -------------------- ------------------- ----------------- -----------------------------
  energy_consump_1min  every 1h            24h               covers a full day of late
                                                             corrections; 24 indexed
                                                             range-scans/day is trivial
  energy_consump_15min every 6h            3d                inherits 1min; 3d > 1min's 24h
  energy_consump_hrly  every 12h           10d              > energy_measurements
                                                             correction horizon
  energy_consump_daily every 24h           14d              DST + month-boundary safety
  demand_intervals     every 1h            6h                = raw replay backoff ceiling
                                                             (job 1077: 1h+2h+6h)
  environment_daily    every 24h           14d
  These are the OUTER bound on "how old a hole can be and still self-repair".
  A discrepancy older than reconcile_window ⇒ alert, not silent repair.

CONCURRENCY: reconciliation acquires the SAME advisory lock as the tier's
normal job (§J). It therefore cannot run concurrently with the normal job for
the same pipeline — it waits (pg_try_advisory_xact_lock → SKIPPED_LOCKED, retry
next cadence) or is scheduled in a non-overlapping slot. It never advances
child_processed_through (it has no business doing so — it re-drives a window
already below the HWM). Two reconciliation runs for different tiers are
independent.

RECONCILIATION FAILS: it is idempotent and stateless; the next cadence retries.
It owns no watermark, so a failure risks nothing. Alert after N consecutive
reconciliation failures for a pipeline (same detector as normal jobs, §O).

WHEN A DISCREPANCY BECOMES AN ALERT (not silently repaired):
  - rows_changed > 0 on the SAME pipeline for >= 3 consecutive reconciliation
    runs ⇒ an upstream bug or a persistent late-data source, not a one-off ⇒ alert.
  - a gap detected OLDER than reconcile_window(P) (found by the freshness view
    §O, e.g. a bucket-count deficit vs source beyond the window) ⇒ alert;
    self-repair impossible without a manual widened refresh.
  - reconciliation run itself FAILED N times ⇒ alert.
A single reconciliation run that quietly fixes a handful of late-arriving rows
and reports rows_changed in the log is NORMAL and does not alert.

OPTIONAL cheap detector to DECIDE whether to even run a repair (keeps steady
state at zero write cost): a per-coarse-bucket COUNT comparison
(target rows vs source rows per hour, over the trailing window) using existing
bucket_start indexes; only invoke refresh_*() for coarse buckets that fail the
count check. Adds code; defer unless the blind re-drive proves too costly at
scale (it will not, at this fleet size). [RECOMMENDATION: start with blind
re-drive; add the detector only if §"staging queries" #5 shows a refresh over
reconcile_window costs > ~30s.]

    worker exceeding max_runtime; the statement rolls back like any cancel.]
  - _timescaledb_internal.bgw_job_stat exposes consecutive_failures,
    consecutive_crashes, total_crashes, last_run_success, next_start —
    zero new state needed for detection.

    pipeline_state RUNNING write and the terminal write leaves last_status
    stuck at 'RUNNING'. Handle two ways, both cheap:
      (i) each proc's normal entry, after taking the advisory lock,
          unconditionally overwrites its own stale RUNNING (it holds the lock,
          so no live run exists) — self-healing;

          last_status='RUNNING' AND age(last_started_at) > 3 × max_runtime.

with backoff. With R2/R3 no watermark advanced past uncommitted work.
[FACT — standard TSDB behaviour; nothing EMS-side required beyond the alert.]

DOES TIMESCALEDB RETRY CORRECTLY: yes for the "job raised an error" case
(retry after retry_period up to max_retries). It does NOT re-run a job that
SUCCEEDED but did incomplete work — that is what bounded catch-up (re-runs next
tick) and reconciliation (re-drives the window) cover. No external supervisor
is warranted. [INFERENCE]

  compress_after(T)  >=  MAX( T's refresh/start_offset window,
                              the operational-recovery window (REC 7d),
                              the routine bounded-catch-up / reconcile window
                              that writes into T ).

Audit against the rule ([FACT] current; [RECOMMENDATION] change):
  normalized_points        1d  → 7d   VIOLATES rule. Upsert-updated by the
    normalization catch-up path AND read directly by demand finalisation AND
    the deepest rebuild source. At 7-day chunks it compresses ~1d after a
    chunk's 7-day span closes, so real exposure is smaller than "1 day"
    suggests — but still tighter than energy_measurements (7d) for no benefit.
    Align to 7d. [UNKNOWN] whether current staging backfills already touch
    compressed chunks (§q #6) — if they do and it is fine, this drops to LOW.
  raw_messages             1d  → keep 1d. Retention is only 48h→7d; raw is
    write-once, never reprocessed in place (job 1077 reads, never updates).
    Compressing at 1d is fine and saves the most space on the biggest table.
  energy_measurements      7d  → keep. Meets the rule (catch-up drains < 7d).
  environment_measurements 7d  → keep.
  capture_bucket_samples   n/a (plain table) → no compression; prune instead (§K).
  energy_consumption_1min  7d  → keep (reconcile_window 24h < 7d).
  energy_consumption_5min  14d → keep.
  energy_consumption_15min 7d  → keep (reconcile_window 3d < 7d).
  energy_consumption_hourly 30d → keep (reconcile 10d < 30d).
  energy_consumption_daily 90d → keep (reconcile 14d < 90d).
  demand_intervals         7d  → keep, BUT v_maxwin_demand tuning must stay
    < 7d, and reconcile_window (6h) is well within. If demand recovery windows
    are ever widened past 7d, raise this in lockstep.
  environment_daily        90d → keep.
  CAGG compression (7d–90d) → all exceed their own start_offsets (2d–30d);
    refresh never fights compression. KEEP ALL.

Do NOT compress anything MORE aggressively for space: the decompress-for-write
cost on a reprocessed table dwarfs the storage saving.

M. CAGG STRATEGY — IS ANY LAYER REDUNDANT?
===============================================================================

[FACT via Phase 1E + grep this pass] NO CAGG is redundant with a persisted
analytics table. They are distinct lineages:

    ca_energy_5min / the semantic 15min view.
  The CAGG is the substrate; the persisted table is the customer "consumption"
  fact. Removing either breaks a real consumer.

MATERIALIZED_ONLY:
  [FACT] the entire energy CAGG family is materialized_only = TRUE ⇒ a read
  returns nothing past the refresh watermark. This is the direct cause of "job
  1079 produced nothing" during the incident AND is a GRAFANA-FACING risk
  (ddl/55 tenant views read ca_energy_15min/hourly/daily directly).
  [FACT] ca_environment_15min/hourly are materialized_only = FALSE ⇒ reads
  union live rows ⇒ a missed refresh degrades latency, not correctness.

RECOMMENDATION:
  1. Do NOT remove any CAGG. Do NOT convert the persisted tables to read CAGGs
     directly (they need the classifier).
  2. [RECOMMENDATION, evaluate — do not implement] consider setting
     materialized_only = FALSE on ca_energy_15min / ca_energy_hourly /
     ca_energy_daily. Trade-off: realtime union adds a query-time aggregation
     over recent uncompressed energy_measurements chunks (cost grows with the
     gap between now and the refresh watermark, normally minutes). Benefit:
     Grafana tenant views and the semantic layer stop going blank when a
     refresh lags, and Tier-5 jobs see fresher source. This is the single
     highest-value CAGG change and should be tested for query cost on staging
     (§q #11) before adoption. Leaving ca_energy_1min materialized_only=TRUE is
     fine (job 1079 gets its freshness from bounded catch-up + reconciliation).
  3. Keep every CAGG refresh cadence. Do NOT widen start_offsets until
     raw_messages retention is raised (the 48h ceiling makes a >2d start_offset
     moot today).
  4. Native CAGGs supporting the semantic layer directly (ddl/55) is
     acceptable AS LONG AS (2) is adopted or the refresh policies are healthy;
     the watermark model does not extend to CAGGs (TSDB owns them) — but the
     freshness view (§O) must surface CAGG refresh lag so a lagging refresh is
     visible before it blanks a panel.

N. FAILURE-SCENARIO WALKTHROUGH (proposed architecture)
===============================================================================

Assumes: Phase 0 + all watermark/catch-up/reconcile/demand phases implemented;
raw_messages retention 7d; per-tier params from §F/§I.

  #  scenario                     outcome / data loss / blank / recovery / max time / alert / manual?
  -- ---------------------------- ------------------------------------------------------------------
  1  1-min network interruption   1 bucket late; overlap re-scan picks it up next tick. No loss,
                                  no blank. Recovery: 1 tick. No alert. No manual.
  2  30-min interruption          each tier's outstanding interval = 30m; drained in the next 1–2
                                  bounded runs (30m << every v_maxwin). No loss/blank beyond
                                  transient. Recovery: minutes. No alert (below backlog threshold).
  3  2-hour interruption          telemetry routing: 1 run if job passes 2h p_max_window, else 2
                                  ticks. 1min tier: outstanding 2h, v_maxwin 2h → 1 run. 15min:
                                  1 run. No loss/blank. Recovery: < 5 min. Warn if backlog age
                                  crossed 4 cycles briefly; clears itself.
  4  12-hour interruption         telemetry routing drains in ~6 ticks (2h window) ≈ 6 min. Then
                                  ca_energy_1min refresh (start_offset 2d) covers it automatically.
                                  1min tier drains 12h in 6 runs (2h window) ≈ 6 min; 15min in 2
                                  runs; hourly/daily 1 run each. No permanent blank. Total pipeline
                                  caught up < ~20 min. Alert: source-watermark-not-advancing fired
                                  during the outage (correct — an operator should know); auto-clears.
  5  24-hour interruption         as #4 at 2× — routing ~12 ticks, 1min tier 12 runs, still all
                                  automatic because 24h < ca_energy_1min start_offset (2d) and <
                                  every table retention. Recovery < ~40 min after ingest resumes.
                                  Alert fired and auto-cleared. No manual.
  6  MQTT reconnect burst         burst lands in raw_messages with new received_at; normalization
                                  watermark advances over it in bounded p_max_window steps;
                                  energy/env routing keyed on platform_received_at picks it up the
                                  same way. Bounded ⇒ no giant transaction. No loss. Recovery
                                  proportional to burst size / v_maxwin.
  7  job 1000 fails 20 min        3 retries then waits for schedule; each 1-min tick retries the
                                  SAME slice (watermark did not move). When it recovers, outstanding
                                  = 20m, drained in 1 run. Downstream tiers were starved (their
                                  parent_available_through did not advance) so they idled — no false
                                  advance, no blank finalisation. Recovery: 1–2 ticks after 1000
                                  recovers. Alert: consecutive_failures >= 3 → warn.
  8  job 1001 fails 20 min        same as #7 one tier down. energy_measurements watermark frozen ⇒
                                  ca_energy_* refresh has no new source ⇒ 1min tier's
                                  parent_available_through frozen ⇒ it idles (NO_SOURCE_DATA), does
                                  NOT advance. On recovery: 1001 drains 20m in 1 run; cascade
                                  follows. No loss/blank. Alert: warn on 1001 consecutive_failures.
  9  job 1079 fails 2 h           watermark frozen at T-2h. 15min/hourly/daily see
                                  parent_available_through frozen and idle (no false advance). On
                                  recovery: outstanding 2h, v_maxwin 2h → 1 run; 15min then drains.
                                  Reconciliation would also have caught it within 1h. No permanent
                                  gap (vs TODAY = permanent). Alert: warn.
  10 hourly job fails 24 h        watermark frozen. daily (also sourced from 15min, not hourly) is
                                  unaffected. On recovery: outstanding 24h, v_maxwin 2d → 1 run.
                                  Reconciliation (12h cadence, 10d window) is a second safety net.
                                  No blank. Alert: warn → page if backlog age > 26h.
  11 child permanently down hours as #9/#10 generalised: parent keeps advancing, child watermark
                                  frozen, outstanding interval grows, NOTHING downstream of the
                                  child falsely advances (cascade LEAST). Zero data loss as long as
                                  source retention (7d raw / 90d normalized / CAGG start_offset)
                                  is not exceeded. Page after backlog age > tier threshold.
  12 child resumes, parent ahead  exactly the agreed example: child at 10:00, parent at 12:00+.
                                  Child processes 10:00→10:00+v_maxwin, commits, advances; repeats.
                                  Independent catch-up. No loss.
  13 child crashes mid-slice      slice transaction (refresh writes + watermark advance) rolls back
                                  atomically (R3). Watermark unmoved. Next run retries the identical
                                  slice. At most v_maxwin of work redone. No hole, no false advance.
  14 DB restart mid-slice         WAL recovery rolls back the in-flight slice. Same as #13.
                                  bgw_job_stat.consecutive_crashes++ ; job rescheduled. No manual.
  15 job exceeds max_runtime      launcher cancels the worker; statement (incl. watermark advance)
                                  rolls back; retried after retry_period. Because v_maxwin bounds
                                  the slice, a correctly-sized window completes well inside
                                  max_runtime; a run that still times out indicates v_maxwin is too
                                  large for current scale → tune down (config, no code). No loss.
  16 job repeatedly fails         3 retries, then waits for next scheduled slot, retrying the same
                                  slice each slot. consecutive_failures climbs → warn at 3, page at
                                  10. No progress but NO corruption and NO false advance. Manual:
                                  investigate root cause; the slice is preserved for when it is fixed.
  17 internal hole below HWM      cannot form during normal op (R2 contiguous advance). If created
                                  by late data / config change / bug: the tier's reconciliation
                                  pass re-drives its trailing window (24h/3d/10d/14d) and the
                                  idempotent DO UPDATE corrects the hole; rows_changed logged.
                                  Alert only if the hole is older than reconcile_window, or
                                  rows_changed>0 for >=3 consecutive reconcile runs.
  18 source row arrives late      if within the tier overlap: normal run corrects it. If below HWM
                                  but within reconcile_window: reconciliation corrects it. If older
                                  than reconcile_window: alert; manual widened refresh_*(from,to).
                                  Bounded by energy_measurements correction_deadline / job-1077
                                  backoff anyway.
  19 source genuinely absent      tier run finds 0 rows for the slice, advances watermark to v_to,
                                  marks NO_SOURCE_DATA (NOT FAILED). demand writes quality_status
                                  NO_DATA (now UPGRADEABLE via §H if data later appears). Semantic
                                  layer returns NULL, not 0 (§P/§O). No false blank-as-zero.
  20 raw retention expires first  outage longer than raw_messages retention (7d): the un-normalised
                                  window is physically gone. normalization watermark can never
                                  advance across it; downstream stays honestly empty (NO_SOURCE_DATA
                                  / NO_DATA), never zero. Page (recovery-runway alert fired long
                                  before). Manual: none possible — data is gone; this is the
                                  documented hard limit.
  21 CAGG refresh delayed         mat_only energy CAGGs read empty for the un-refreshed tail ⇒ Tier
                                  5 parent_available_through (from continuous_aggs_watermark) is
                                  frozen ⇒ tiers idle, no false advance. If (M)(2) adopted
                                  (mat_only=FALSE on 15m/1h/1d) the semantic/Grafana reads stay
                                  correct via realtime union. Alert: CAGG-refresh-lag.
  22 CAGG hits start_offset       outage > start_offset (2d for 1min/15min): the refresh policy
                                  will not revisit that range. Tier-5 parent mark stops there.
                                  Manual: refresh_continuous_aggregate(ca, old_start, end) then the
                                  bounded catch-up drains Tier 5 automatically. Alert:
                                  gap-older-than-recoverable. (Raising raw retention to 7d does NOT
                                  by itself fix this — start_offset must be widened too, and only
                                  then is it worth it.)
  23 reconciliation finds stale   re-drives the window, idempotent DO UPDATE fixes it, logs
                                  rows_changed. Silent if one-off and within window. Alert if
                                  persistent (>=3 runs) or older than window.
  24 reconciliation itself fails  no watermark owned ⇒ nothing advances, nothing corrupts. Retried
                                  next cadence. Alert after N consecutive reconciliation failures.
                                  Normal tier jobs are unaffected (separate advisory-lock holders,
                                  separate schedule).

SUMMARY: with the proposed architecture, scenarios 1–19 and 21–24 involve NO
permanent data loss and NO blank-as-zero; recovery is automatic and bounded;
alerts fire for anything an operator should see and auto-clear when resolved.
Only #20 (outage > raw retention) is unrecoverable — and that is a
retention-policy limit, made explicit and alertable, not a pipeline defect.

O. MONITORING / ALERTING ARCHITECTURE
===============================================================================

NEW STATE (minimal): the 7 pipeline_state rows (§E) + one small table
analytics.pipeline_reconciliation_log(pipeline_name, ran_at, win_start,
win_end, rows_changed, status). Nothing else.

READ-ONLY VIEW analytics.v_pipeline_health — one row per pipeline:
  pipeline_name,
  child_processed_through            (pipeline_state.last_received_at),
  parent_available_through           (computed per §E/§G),
  freshness_lag = now() - child_processed_through,
  backlog = parent_available_through - child_processed_through,
  last_status, last_error, last_started_at, last_completed_at,
  consecutive_failures              (bgw_job_stat),
  consecutive_crashes               (bgw_job_stat),
  last_run_duration                 (job_stats),
  cagg_refresh_lag                  (now() - continuous_aggs_watermark, where applicable),
  last_reconcile_at, last_reconcile_rows_changed  (reconciliation_log),
  stuck_seconds = CASE WHEN last_status='RUNNING'
                       THEN extract(epoch FROM now()-last_started_at) END.

This view drives BOTH a Grafana ops panel (not built in this phase) and the
alert rules. Grafana panels for customer data are NOT changed.

ALERT RULES — thresholds are starting points; tune against staging baselines
(§q #5). Warn = ticket; Page = wake someone.

  condition                                              warn         page
  ----------------------------------------------------- ------------ ------------
  bgw_job_stat.consecutive_failures                     >= 3         >= 10
  stuck RUNNING: stuck_seconds / max_runtime            > 2×         > 3×
  bgw_job_stat.consecutive_crashes                      >= 2         >= 5
  freshness_lag vs per-tier SLA (below)                 at SLA       2× SLA
  backlog age (backlog / schedule_interval)             > 4 cycles   1m/demand>1h;
                                                                     daily>26h
  source watermark not advancing while ingest healthy   > 10 min     > 15 min
    (age(pipeline_state('normalized_points').last_received_at) with
     raw_messages still receiving) — THE incident signature
  cagg_refresh_lag / refresh_interval                   > 3×         > 6×
  recovery runway: oldest backlog vs MIN(upstream       > 25%        > 50%
    retention on path)
  reconciliation rows_changed on same pipeline          -            >= 3 consec runs
  reconciliation discrepancy older than reconcile_window -           any
  reconciliation run failed                             -            >= N consec

  PER-TIER FRESHNESS SLA (proposed):
    energy_consumption_1min, demand_intervals   <= 10 min
    energy_consumption_15min                    <= 30 min
    energy_consumption_hourly                   <= 90 min
    energy_consumption_daily, environment_daily <= 26 h
    energy_measurements, environment_measurements <= 5 min
    normalized_points                           <= 5 min

  EMPTY-vs-FAILED: never alert on last_status='NO_SOURCE_DATA' by itself
  (energy_consumption_5min sits here permanently for this fleet). Alert on
  FAILED, on freshness_lag, and on backlog — not on "no source".

All signals except the 7 new pipeline_state rows and the reconciliation_log
come from existing TimescaleDB catalogs — no metrics infrastructure added.

  P-C2  Jobs 1001/1012 unbounded-forward transaction (proof §D). [FACT] Latent

  P-C3  demand_intervals ON CONFLICT DO NOTHING write-once. [FACT] Permanent

HIGH

  P-H2  Native energy CAGGs materialized_only=TRUE feed Grafana tenant views

CROSS-CUTTING (add to every phase's suite):

  - tenant isolation: a repair/reconcile scoped to one org/site never touches

S. RISKS / TRADE-OFFS
===============================================================================

  - Bounded catch-up trades recovery SPEED for bounded per-run cost (N small
    runs vs 1 big one). Same trade migration 205 accepted; tunable via
    v_max_catchup_window per tier. Mitigation: generous windows on cheap tiers
    (hourly/daily), tight on expensive (1min/demand).
  - Reusing telemetry.pipeline_state from analytics procs crosses a schema
    boundary and overloads the last_received_at semantic (ingest-time at the
    telemetry tier, bucket-time at the analytics tier). Mitigation: document
    loudly; the alternative (analytics.pipeline_state mirror) duplicates a
    table + tests for no functional gain. Confirm no isolation rule (§q).
  - Setting max_runtime on analytics jobs means a legitimately-large backfill
    run is cancelled mid-way. SAFE only because of R2/R3 (advance only the
    committed contiguous slice). If any proc later gains an inner COMMIT, each
    committed slice must advance the watermark atomically (job-1077 rule) —
    call this out in code review.
  - Bounded scheduled p_max_window on 1001/1012 (Phase 0.3) changes steady-
    state behaviour slightly: if the platform is ever legitimately >2h behind
    at steady state (it should never be), the routing tier would now take
    multiple ticks to close that. Acceptable and self-correcting; the alert on
    backlog age surfaces it.
  - Reconciliation "blind re-drive" spends an indexed range scan per cadence
    even when clean. At this fleet size negligible; at 10× scale, add the
    cheap per-coarse-bucket count detector (§I) — designed for but not built.
  - materialized_only=FALSE on the 15m/1h/1d CAGGs (Phase 9) adds query-time
    aggregation cost to every semantic/Grafana read of those CAGGs. Gated on a
    staging EXPLAIN test; reversible.
  - Raising raw_messages retention to 7d increases storage on the largest
    table. Must be sized first (§q #6); 96h is the fallback if the delta is
    unacceptable.
  - Canonicalising the analytics job registration (P-H6) touches deploy
    ordering. Do it in isolation, verify against a fresh-deploy test.
  - normalized_points compress_after 1d→7d increases uncompressed footprint for
    ~6 extra days of the highest-cardinality telemetry table. Quantify (§q #6).
  - More jobs (reconciliation) = more scheduler slots + more advisory-lock
    contention on the 1-min tiers. Mitigation: reconciliation on 1h+ cadences,
    off-phase from the normal jobs.

T. FINAL RECOMMENDED ARCHITECTURE
===============================================================================

  1. STORE: telemetry.pipeline_state, reused, +7 rows. child_processed_through
     lives in last_received_at (bucket-time for analytics rows).
     parent_available_through is always READ (parent pipeline_state row or CAGG
     watermark), never stored on the child.

  2. EVERY analytical stage per run, inside its own advisory xact lock:
       v_to   = LEAST( date_bin(res, now()), parent_available_through,
                       child_checkpoint + max_catchup_window )
       v_from = child_checkpoint - overlap
       refresh_*(v_from, v_to)                 -- existing math, untouched
       advance child_checkpoint := v_to        -- last write, same txn
       on error: FAILED + RAISE ⇒ full rollback incl. the advance
     Contiguous, monotonic, bounded, idempotent, false-advance-proof.

  3. CASCADE: each tier's parent mark = LEAST over its IMMEDIATE sources'
     durable marks. 15min ≤ min(1min,5min); hourly ≤ 15min; daily ≤ 15min (and
     ≤ last complete local day); demand ≤ min(energy_measurements,
     normalized_points). A child never processes past its input.

  4. DEMAND: status-guarded ON CONFLICT DO UPDATE (VALID frozen; everything
     else reconsidered and upgradeable) + a demand watermark. Same
     calculate_demand_window() math.

  5. RECONCILIATION: per tier, a low-cadence job that re-drives the existing
     refresh_*() over a bounded trailing window [checkpoint - reconcile_window,
     checkpoint), logs rows_changed, alerts on persistent or out-of-window
     discrepancy. Not a second pipeline — the same function, wider bounds,
     slower clock.

  6. TELEMETRY ROUTING: p_max_window added to 1001/1012 (mirror 205); the
     scheduled wrappers pass a bounded 2h so an unattended stall self-drains.

  7. JOB POLICY: keep all cadences. Analytics tier gets advisory lock,
     max_runtime (5m/10m), finite max_retries (3), pipeline_state status,
     config validators. No external supervisor — TimescaleDB's max_runtime +
     bgw_job_stat are sufficient; add only a stale-RUNNING alert and
     self-overwrite.

  8. RETENTION: raw_messages 48h→7d (the one high-leverage change; size first);
     normalized_points compress 1d→7d; explicit policies on demand_intervals /
     daily tables; prune capture_bucket_samples. Publish a recovery-ceiling
     matrix so "how far back can this self-heal / when is data gone" is a
     lookup.

  9. CAGG: nothing removed. Evaluate materialized_only=FALSE on
     ca_energy_15min/hourly/daily (biggest freshness win, gated on a cost
     test). Surface CAGG refresh lag in monitoring.

 10. OBSERVABILITY: analytics.v_pipeline_health (child/parent through, backlog,
     freshness, failures, crashes, stuck, cagg lag, reconcile state) from
     existing catalogs + the 7 new rows + a small reconcile log. Alert rules
     per §O with empty-vs-failed discrimination.

 11. NOT DONE (correctly): no message broker, no backfill/work-queue table, no
     parent→child synchronous CALL chain, no external process supervisor, no
     new metrics stack. NOTIFY is a later latency-only optimisation.

This eliminates the CLASS: any stage, at any depth, after any outage length up
to source retention, converges to correct data automatically and boundedly,
cannot falsely advance, cannot silently blank-as-zero, cannot hide an internal
hole beyond its reconciliation window, and is observable and alertable
throughout.

7. RECOMMENDATIONS IN THE PHASE 2 REPORT I DISAGREE WITH (with reasons):

   D1. Phase 2 §N.5 / §U Phase 0 says the telemetry routing WRAPPERS "keep
       passing NULL" for p_max_window. DISAGREE. NULL means the scheduled job
       still attempts unbounded forward progress; recovery then depends on an
       operator running manual bounded calls (as in the incident). For genuine
       hands-off self-healing the SCHEDULED wrapper should pass a bounded value
       (recommend 2h). NULL stays available for deliberate operator catch-up.
       This is objective #2 ("self-healing after outages ... without manual
       intervention") applied consistently.

   D2. Phase 2 treats job hardening (max_runtime / finite retries / advisory
       lock) as a LATE phase (its Phase 6). DISAGREE on ordering. The missing
       advisory lock + unlimited runtime is a CRITICAL correctness bug in its
       own right (P-C1: concurrent self-overlap on the demand provisional
       accumulator) and is a PRECONDITION for safely deploying the watermark
       logic (a watermark advanced by two overlapping workers is exactly the
       false-advance we are trying to prevent). Move it to Phase 0b, before any
       watermark work.

   D3. Phase 2's retention/compression section does not mention
       telemetry.capture_bucket_samples. DISAGREE by omission — it is an
       unbounded-growth plain table on the hot normalization path and belongs
       in the retention scope (added here as P-H1 / §K / Phase 8.4).

   D4. Phase 2 §H (CAgg arch) notes materialized_only=true as an internal
       freshness risk but does not flag that ca_energy_15min/hourly/daily are
       read DIRECTLY by Grafana tenant views (postgres/ddl/55). DISAGREE on
       severity — this makes a lagging CAGG refresh a CUSTOMER-VISIBLE blank,
       not just an internal one, and motivates evaluating materialized_only=
       FALSE (new §M.2 / Phase 9).

   D5. Phase 2 implies fixing the persisted energy_consumption_15min/hourly/
       daily tables improves the Grafana "Energy Consumption Trend" panel.
       PARTIALLY DISAGREE — per Phase 1E, get_canonical_energy_read reads the
       LIVE v_energy_reporting_* view chain, not those persisted rollup tables.
       The watermark on those tables is still worth doing (Path A, export,
       future canonicalisation, and the 1min tier it depends on IS on the live
       path) but the causal claim "fix the table → fix the panel" is not
       accurate for the primary read path. Verify per-panel binding (§q #11).

   D6. Phase 2 leaves per-tier max_catchup_window as "seed = current lookback".
       AGREE as a safe default but INSUFFICIENT — §F here gives calculated
       target values (2h/2h/6h/2d/8d/3h→6-12h) with rationale, to be confirmed
       against staging run-duration (§q #5). "Seed = old lookback" for the 1min
       tier (30m) would still leave a 30-min-per-run drain rate, i.e. a 24h
       outage takes 48 runs instead of 12 — technically self-healing but
       needlessly slow.
