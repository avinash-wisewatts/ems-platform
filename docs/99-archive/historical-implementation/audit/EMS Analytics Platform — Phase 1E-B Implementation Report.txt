per_flow_quality(p_from TIMESTAMPTZ, p_to TIMESTAMPTZ, p_batch_interval
INTERVAL DEFAULT INTERVAL '7 days') RETURNS TABLE(batch_start, batch_end,
rows_15min, rows_hourly, rows_daily, batch_error). SECURITY DEFINER, owned
by ems_admin, EXECUTE granted to ems_admin only (matching the refresh
functions' own internal-only posture — never exposed to grafana_reader or
ems_app). It contains no calculation logic of its own: for each batch it
calls, in order, analytics.refresh_energy_consumption_15min(), then
_hourly(), then _daily() — all three completely unmodified since Phase
1E-A (commit 523ac5b) — inside a nested exception block so a single
batch's failure is caught, logged via RAISE WARNING, and does not abort
the remaining range. No existing function, view, table, index, grant, or
retention policy was modified.

unmodified refresh functions:
    1. First backfill run over the full fixture range (2025-12-31 to
       2026-04-01, 7-day batches): at least one batch executed, zero
       batch errors.
    2. Device A 15-minute per-flow reconstruction: exact per-flow arrays
       across all seven buckets (import/export gap, reset, rollover
       counts) and exact consumption_kwh arrays (GAP/ROLLOVER contribute,
       RESET excluded), matching Phase 1E-A's own proven values exactly.
    3. Device A hourly propagation: two hourly buckets, exact per-flow
       sums and exact kwh sums.
    4. Device A daily propagation and Device T tenant isolation: daily
       per-flow sums correct; Device T's row shows the correct
       organization_id and zero per-flow counters (no cross-tenant
       contamination via the backfill's own write path).
    5. Device TZ site-local-midnight boundary: two correctly-split daily
       rows (2025-12-31 and 2026-01-01) with correct bucket_start values,
       proving timezone bucketing survives when exercised through the new
       backfill procedure specifically, not just the raw refresh functions.
    6. Device D ("durability"): 15-minute per-flow values UNCHANGED after
       the backfill runs (no native exists, so the 15-minute call is a
       safe no-op); pre-existing consumption_kwh values unchanged; hourly
       and daily rows correctly derived FROM Device D's surviving 15-
       minute per-flow data, proving forward durability — a lower tier's
       absent native source does not prevent a higher tier from correctly
       inheriting already-materialized per-flow semantics.
    7. Device E ("unreconstructable"): per-flow columns remain NULL (not
       zeroed) after the backfill runs; pre-existing consumption_kwh
       values unchanged; hourly and daily rows are created (correctly
       deriving consumption_kwh from Device E's existing 15-minute data)
       with per-flow columns propagating as NULL (SUM of NULL = NULL,
       falling out of standard SQL semantics with no special-case code),
       proving the system never infers GOOD/zero from absent source data.
    8. Idempotent rerun: the identical backfill call issued a second time
       over the identical range; Device A, D, and E's 15-minute rows are
       asserted byte-for-byte identical to their first-run values.
