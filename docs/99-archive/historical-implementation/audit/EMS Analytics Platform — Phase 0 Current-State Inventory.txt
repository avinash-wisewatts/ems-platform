4. Persisted aggregate tables — "validated energy-consumption" lineage

This is architecturally distinct from §3: it never re-derives energy from raw power/register MAX-MIN; it classifies register deltas once at native resolution, then every coarser tier sums already-classified intervals.

Native tier (mutually exclusive per site by capture policy, not a resolution hierarchy)

Object: analytics.energy_consumption_1min
Source: telemetry.ca_energy_1min
Eligibility: sites with capture interval ≤60s
Refresh: job every 1 min, 30-min lookback
Retention: none — explicitly deferred ("prevents data loss until higher-resolution rollups exist and are verified")
Access: internal only — REVOKE ALL FROM PUBLIC, no grant to grafana_reader/ems_app
────────────────────────────────────────
Object: analytics.energy_consumption_5min
Source: telemetry.ca_energy_5min
Eligibility: sites with capture interval exactly 300s
Refresh: job every 1 min, 30-min lookback, date_bin epoch-anchored
Retention: none (same rationale)
Access: internal only

Each row carries: register value + previous register, consumption (Wh and kWh), quality_code, is_valid, reset_detected, rollover_detected, plus which effective-dated quality rule applied. Calculation delegates entirely to analytics.classify_energy_register_delta() (§5).

Persisted rollup hierarchy (one-directional, never reclassifies registers)

Object: analytics.energy_consumption_15min
Source: analytics.v_energy_semantic_rollup_15min (i.e. native 1min/5min tables, one hop)
Refresh: job every 5 min
Compress: 7d
Retention: 2y
────────────────────────────────────────
Object: analytics.energy_consumption_hourly
Source: analytics.energy_consumption_15min only (never hourly-from-raw)
Refresh: job every 15 min
Compress: 30d
Retention: 5y
────────────────────────────────────────
Object: analytics.energy_consumption_daily
Source: analytics.energy_consumption_15min only (explicitly not hourly, to avoid UTC-hour crossing site-local midnight)
Refresh: job every 1 hour
Compress: 90d
Retention: none ("durable long-term accounting layer")

Chain: ca_energy_1min/5min (raw CAGG) → energy_consumption_1min/5min (validated/classified) → energy_consumption_15min (rollup) → hourly/daily (further rollup) → exposed via analytics.get_canonical_energy_read() (§5).

Canonical read function (not a table, but the contract everything feeds)

analytics.get_canonical_energy_read(grafana_org_id, asset_id, from, to, resolution, fallback_policy) — resolves tenant→asset→PRIMARY_METER→device→site, rejects ranges crossing a genuine capture-policy change, dispatches to exactly one of v_energy_consumption_native / v_energy_reporting_5min/15min/hourly/daily by actual duration comparison. Explicitly documented: never reads the raw MAX/MIN CAGGs, never reclassifies registers. Grants extend to grafana_reader (migration 043) but no direct dashboard call site was found in the 7 Grafana dashboards read — it's reached only indirectly via get_grafana_asset_energy_intervals (asset-overview's actual entry point).

Confidence: VERIFIED FROM SOURCE for all object definitions and comments quoted; the "why this table has no retention yet" rationale is a direct quote, not inference.

5. Views, functions, procedures, triggers

5.1 The single authoritative quality classifier

analytics.classify_energy_register_delta(current, previous, elapsed_minutes, counter_direction, rollover_behavior, rollover_value, reset_behavior, expected_max_interval_delta, gap_threshold_minutes) — pure, IMMUTABLE, PARALLEL SAFE function.

Full quality-code vocabulary, in decision order (verified from source): INITIAL → MISSING_REGISTER → CONFIG_MISSING/CONFIG_INVALID → ROLLOVER_UNRESOLVED → ROLLOVER → RESET_FROM_ZERO → RESET → DIRECTION_ERROR → IMPLAUSIBLE_DELTA → GAP → GOOD.

Every downstream consumption object (native tables, v_energy_consumption_15min, get_grafana_asset_energy_intervals) calls this same function rather than re-implementing classification — confirmed by tracing v_energy_consumption_15min through 4 generations (ddl/56→80→82→84), where generation 3 (82_refactor_energy_consumption_to_classifier.sql) is literally the migration that replaced inline classification logic with a call to this function.

Config driving it: config.energy_register_semantics (per-profile counter direction/rollover/reset rules, seeded only for ENERGY_METER_ENISCOPE_V1) + config.interval_quality_rules/resolve_interval_quality_rule() (effective-dated gap threshold, precedence DEVICE→PROFILE→SITE→ORGANIZATION→PLATFORM, default 30 min).

5.2 Two coexisting "validated" reporting paths (important nuance)

The audit traced two parallel paths, both ultimately built on the same classifier, that the task's framing ("general CAGGs vs. validated lineage") doesn't fully capture as a single split:

- Path A — direct classifier view: analytics.v_energy_consumption_15min (Gen 4, ddl/84) reads the raw ca_energy_15min CAGG and classifies live via CROSS JOIN LATERAL classify_energy_register_delta. Grafana-granted; feeds v_energy_demand_15min, peak-demand daily/monthly, load-profile views, v_site_energy_balance_daily (§5.4).
- Path B — semantic reporting pipeline: v_energy_consumption_native → v_energy_semantic_rollup_5min/15min → v_energy_reporting_5min/15min/hourly/daily, built entirely on the persisted energy_consumption_1min/5min tables (§4), which were already classified once and never reclassified. Internal-only (ems_admin) except v_energy_consumption_daily, which migration 036 (036_energy_daily_semantic_compatibility_cutover.sql) explicitly re-pointed from Path A to Path B while preserving its public 15-column contract — quoted: "Energy comes from already-classified semantic native intervals… No cumulative-register classification occurs here."

Fact, stated plainly: Path A's demand/load-profile/site-balance family still hardcodes 'Asia/Kolkata'; Path B was migrated to per-site timezone (migrations 037/041/034/036). This divergence was not resolved by any migration found — flagged as UNCERTAIN whether intentional (may be masked by all current sites sharing one timezone).

5.3 Grafana resolution routing

- analytics.resolve_grafana_energy_routing_resolution — two generations: migration 044 (≤24h→15m, ≤14d→1h, >14d→1d, superseded) → migration 045, current: ≤24h→native, ≤14d→15m, >14d→1h. The router's ELSE branch never returns '1d' — the daily reporting tier is reachable only via an explicit direct caller, and none was found in the files read (UNKNOWN whether one exists in the app layer).
- analytics.get_grafana_asset_energy_intervals — the actual Grafana Asset Dashboard entry point (confirmed by migration 191/192 incident narratives naming it explicitly), max-10-asset multi-asset sibling, calls the router then get_canonical_energy_read(..., 'native').
- analytics.get_grafana_short_history — three generations (171→173→175 superseded, 176 current), rewritten from SQL-language SECURITY DEFINER to plpgsql with dynamic EXECUTE…USING specifically to fix an observed slow cached query plan (migration 176 comment).

5.4 Demand engine (independent of energy CAGGs)

- config.demand_register_semantics — per-profile "true native demand register" certification (basis kW/kVA, native interval 900 or 1800 seconds only — the one resolution outside the 1m/5m/15m/1h/1d ladder).
- config.resolve_device_demand_method / analytics.resolve_demand_capability — 3-tier method priority METER_NATIVE > ENERGY_COUNTER_DELTA > TIME_WEIGHTED_POWER. Two generations: migration 012 (unified SITE/ASSET resolver, superseded) → migration 017, current (splits SITE, user-opt-in, from ASSET, platform-managed/always-on/15-min/kW, explicitly decoupled: "ASSET source... does not depend on SITE demand enablement").
- analytics.calculate_demand_window / analytics.refresh_demand_analytics (procedure) — writes analytics.demand_intervals (finalized, 10-min processing grace beyond late_arrival_tolerance_seconds) and analytics.demand_state (provisional/current).
- analytics.v_site_energy_balance_daily — balance equation (verified): derived_site_consumption_kwh = grid_import + onsite_generation − grid_export − battery_charge + battery_discharge, precedence DIRECT_METER > DERIVED_BALANCE > UNAVAILABLE, excludes LOAD_SUBMETER role explicitly to avoid double-counting.

5.6 Environment analytics — no equivalent classifier

No environment-specific quality/validation function analogous to classify_energy_register_delta was found anywhere in the read files. quality_code/is_estimated exist as columns on the domain table but are hardcoded NULL/FALSE at the routing view. analytics.v_environment_sensor_kpis uses hardcoded freshness thresholds (180s/600s), not the configurable config.telemetry_availability_policy mechanism used for asset connectivity. UNCERTAIN whether this is a genuine gap or intentional (environment isn't a cumulative counter, so register-delta classification doesn't apply the same way) — stated as fact, not judged.

Every Grafana-facing analytics.* object joins metadata.grafana_organization_map ON organization_id = ... AND is_active = TRUE, exposing grafana_org_id; all declared security_barrier. grafana_reader has REVOKE ALL on metadata/config/telemetry schemas directly — zero table access outside explicitly granted analytics.* objects (structural, not conventional).
