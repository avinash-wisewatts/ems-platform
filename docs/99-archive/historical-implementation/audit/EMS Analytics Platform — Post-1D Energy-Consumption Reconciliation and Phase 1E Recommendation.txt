B. REMAINING GAPS
===============================================================================

    - Two live, correct, real implementations (A.1 persisted, A.2 live-
      aggregated) compute the identical metric from the identical native
      source, and only one of them (A.2, the less efficient, query-time
      one) is ever read. A.1 is fully built, proven, populated, and idle.
      This is the concrete remaining architectural inconsistency Phase 1D
      surfaced and explicitly deferred.
    - A.3 (Path A / v_energy_consumption_15min / v_site_energy_balance_
      daily) has zero real consumer of either object, exactly as found in
      the original Reconciliation. The Reconciliation document itself
      named "Decision-1A (Energy Balance's fate)" as the one true
      precondition before touching Path A — that product decision has
      still not been made. Retiring or migrating Path A is therefore NOT
      safe to bundle into the smallest next phase without first deciding
      whether Energy Balance is kept, retired, or migrated.
    - Stale documentation risk (already flagged, still unresolved, still
      advisory-only): postgres/ddl/141_asset_energy_persisted_read_path.sql
      contains a pre-migration-044 function body for get_grafana_asset_
      energy_intervals that no longer matches live behavior. No live-
      behavior impact on any checked environment (every real deploy path
      applies forward migrations after it), but it will mislead the next
      reader exactly as it misled this investigation twice before being
      caught by direct live-DB verification.
    - No tenant-isolation risk identified for a same-shape consolidation:
      A.1's tables are internal-only (ems_admin); A.2's reporting views
      already carry the gom/tenant join that would need to be preserved
      when retargeted.

C. PROPOSED NEXT PHASE
===============================================================================

PHASE 1E — ENERGY-CONSUMPTION REPORTING-LAYER CONSOLIDATION

Objective: retarget the live Grafana-facing reporting views (A.2) to read
from Phase 1B's already-proven, already-populated persisted tables (A.1)
instead of live-re-aggregating from native data on every query — closing
the gap Phase 1D discovered and explicitly deferred (Phase 1D Plan §19),
without touching anything above the view layer.

What gets consolidated: the SOURCE of analytics.v_energy_reporting_5min,
v_energy_reporting_15min, v_energy_reporting_hourly, v_energy_reporting_
daily — from v_energy_semantic_rollup_5min/15min (live GROUP BY) to
analytics.energy_consumption_5min/15min/hourly/daily (persisted, Phase
1B-proven) respectively, keeping each view's existing name, column list,
tenant (gom) join, and device-name join structure identical.

What gets migrated: nothing above the view layer needs migration — analytics
.get_canonical_energy_read, analytics.get_grafana_asset_energy_intervals,
analytics.get_grafana_assets_energy_intervals, analytics.resolve_grafana_
energy_routing_resolution, and asset-overview.json all call/query these
views by the same name and get the same column shape back; none require a
code change.

What gets retired: analytics.v_energy_semantic_rollup_5min/15min (the live
GROUP BY views) once nothing reads them — retire only after confirming no
other consumer exists (grep confirms none this session; re-verify at
implementation time as a final check, not assumed).

What must NOT be changed this phase: analytics.v_energy_consumption_15min
/ v_site_energy_balance_daily (Path A — deferred pending the Energy
Balance product decision, per §B); analytics.get_grafana_explorer_intervals
/ v_grafana_energy_samples (confirmed different metrics, A.4); analytics.
classify_energy_register_delta() and the native tier itself (already
correct, Phase 1B-proven, unchanged); analytics.resolve_grafana_energy_
routing_resolution and every Phase 1D object; any Grafana dashboard file;
any Phase 1A connectivity object; the job schedules corrected in Phase 1C.

Exact database objects/files expected to change:
    New migration(s): CREATE OR REPLACE VIEW for v_energy_reporting_5min,
    _15min, _hourly, _daily (repointing FROM clause only; same output
    columns) — a small number of new migration files (one per view, or
    combined, per implementation-time judgment), plus a manifest entry.
    Retire (DROP) migration for v_energy_semantic_rollup_5min/15min, issued
    only after the reporting views no longer reference them.
    New test: a disposable-DB contract proving the retargeted views return
    identical shape/values to what the native tier + real refresh functions
    (A.1's own refresh_energy_consumption_15min/hourly/daily, already
    proven in Phase 1B) produce, plus a re-run of Phase 1D's existing
    routing contract to confirm end-to-end behavior is unchanged from the
    Grafana caller's perspective.
    No application code file, no Grafana dashboard file, no change to any
    function signature or grant.

Dependency/order of operations:
    1. Confirm (at implementation time, not assumed) that v_energy_
       semantic_rollup_5min/15min still have no consumer beyond the
       reporting views being retargeted.
    2. Retarget v_energy_reporting_15min first (it is what hourly/daily
       are themselves built on within the SAME lineage today — but after
       this phase, hourly/daily will read A.1's own persisted hourly/daily
       tables directly, not through the 15min view, so this ordering risk
       is limited to the transition window of a single migration file
       applied atomically).
    3. Retarget v_energy_reporting_5min, _hourly, _daily.
    4. Confirm output equivalence via the new contract test before
       retiring anything.
    5. Retire v_energy_semantic_rollup_5min/15min only after step 4 passes.

Tenant/security implications: none, provided each retargeted view
preserves its existing JOIN to metadata.grafana_organization_map (and
metadata.devices for the device-name column) exactly as today — this is a
straightforward, verifiable structural requirement, not a design change.
analytics.energy_consumption_* tables remain internal-only (ems_admin);
the reporting views remain the only tenant-scoped boundary, unchanged.

Grafana impact: none. asset-overview.json's panel call is unaffected —
same function, same signature, same columns; only the data now comes from
a persisted table instead of a live aggregation.

Rollback considerations: each CREATE OR REPLACE VIEW is trivially
reversible by a follow-up migration restoring the prior FROM clause; the
DROP of v_energy_semantic_rollup_5min/15min should be deferred to a
separate, later migration (not bundled with the retarget) specifically so
a rollback of the retarget does not also require recreating a dropped view
under time pressure.
