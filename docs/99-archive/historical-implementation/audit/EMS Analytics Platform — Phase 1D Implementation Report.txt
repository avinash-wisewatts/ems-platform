2. DISCREPANCY DISCOVERED AND CORRECTED DURING TEST-FIXTURE DESIGN
===============================================================================

While designing the contract test, direct inspection (pg_get_viewdef
against the live local database, not assumption from a possibly-stale file)
established that analytics.v_energy_reporting_hourly and analytics.v_
energy_reporting_daily — what get_canonical_energy_read's 1h/1d branches
actually query — are NOT reads of Phase 1B's persisted analytics.energy_
consumption_hourly/daily tables. Both are live, query-time GROUP BY
aggregations over analytics.v_energy_reporting_15min -> analytics.v_energy_
semantic_rollup_15min -> analytics.v_energy_consumption_native (the native
energy_consumption_1min/5min tables) — an older reporting-view lineage
(postgres/ddl/147, predating Phase 1B) never repointed at the newer
persisted tables. This explains Phase 1B's own finding that its persisted
rollup chain has zero real consumers.

Consequence: routing a >90-day range to '1d' does not reduce the native-data
scan (the same rows are aggregated either way, just grouped coarser) — the
real benefit is fewer, more compact result rows returned to the client for
very long ranges, not a scan-cost reduction. This was corrected in the
Implementation Plan document (Section 15) before writing the test, and the
test fixture was designed accordingly: it seeds the NATIVE tier (analytics.
energy_consumption_1min, via a real call to analytics.classify_energy_
register_delta — Phase 1B's own discipline, not a faked calculation), since
that is what the live view chain actually aggregates from; it does not seed
the (uninvolved, for this call path) persisted hourly/daily tables. Also
logged as a candidate for the later energy-consumption consolidation phase:
repointing the reporting-view lineage at Phase 1B's persisted tables would
be the change that actually delivers the scan-cost reduction originally
assumed.

No other discrepancy found. The migration content matches the approved
plan exactly.

5. TEST COVERAGE ADDED
===============================================================================

scripts/test/assert_grafana_energy_routing_daily_tier.sql — four scenarios:
    1. Pure router assertions (no fixture — IMMUTABLE, no table dependency):
       12h->native, 7d->15m, 30d->1h, exactly-90d->1h, 91d->1d.
    2. Hourly regression guard: a 30-day range (<=90d) still returns exactly
       one row with elapsed_minutes=60 and the correct kWh, through the
       real, unmodified get_grafana_asset_energy_intervals -> get_
       canonical_energy_read -> v_energy_reporting_hourly chain, seeded
       from one real native-tier interval.
    3. Daily end-to-end: a 91-day range (>90d) returns exactly one row with
       elapsed_minutes=1440 and the correct kWh, through the same real
       chain reaching v_energy_reporting_daily for the first time via
       automatic routing.
    4. Tenant isolation: the same 91-day query issued under an unrelated
       organization's grafana_org_id returns zero rows.

Fixture: one organization/site (Asia/Kolkata)/gateway, two devices (each
with its own asset + PRIMARY_METER relationship, since one asset may have
only one PRIMARY_METER device), one site-specific config.telemetry_capture_
policies row fixed 2000 days before the test's reference instant (avoiding
the platform-default policy's non-deterministic wall-clock effective_from),
a second unrelated organization for the tenant-isolation control. All
native rows are real classifier outputs (GOOD classification), not
hand-asserted values.
