Three real fixture bugs were found and fixed while getting this test green (all in the new test file only, not in any production object):
1. Devices were inserted with lifecycle_status='ACTIVE' directly, which trg_reject_uncommissioned_active_device (postgres/ddl/91_device_lifecycle_management.sql) correctly rejects outside the controlled commissioning action. Fixed: omit the column (defaults to 'REGISTERED', which the connectivity function is correctly blind to regardless).
2. PRIMARY_METER/SECONDARY_METER asset_devices assignments require the device to reference a metadata.device_models row in the "Energy Meter" config.device_categories category (metadata.assert_asset_device_relationship). Fixed: the test now inserts its own self-contained device_models row referencing the existing 'Energy Meter' category by name.
3. A device cannot receive a *new* asset_devices assignment while already DECOMMISSIONED, and a device can have at most one PRIMARY_METER relationship (uq_asset_devices_primary_meter) -- the decommissioned-device fixture and the multi-device-asset fixture each initially violated one of these. Fixed: assign the decommissioned device before decommissioning it (UPDATE afterward, not INSERT already-decommissioned), and use a dedicated device for the multi-device asset's PRIMARY_METER instead of reusing another test case's device.
None of these were bugs in analytics.get_grafana_asset_connectivity_context() or any other production object -- all three were fixture-construction mistakes in the new test, now corrected.

3. TESTS ADDED
================================================================
scripts/test/assert_connectivity_semantic_contract.sql / .sh — a new entry in the scripts/test/assert_*.sql + .sh convention (the same pattern used by assert_tenant_telemetry_isolation.sql, assert_energy_register_semantics.sql, etc.: BEGIN; fixture INSERTs; DO $$ ... RAISE EXCEPTION ... $$ assertions; ROLLBACK;), run against the disposable ems_test database via compose.test.yaml's timescaledb-test service.

Deviation from the original plan's wording, made deliberately and reported per instruction: the plan named the target file "app/tests/test_connectivity_semantic_contract.py". Investigation during implementation confirmed app/tests/*_contract.py files in this repo assert against migration SQL *text* and explicitly never open a live database connection (confirmed pattern from test_telemetry_pipeline_performance_state_contract.py and CI/CD documentation). Since the plan required tests that "verify semantic behavior, not merely SQL object existence" — i.e. actually invoke the function against real fixture data — the correct venue per existing repo convention is the scripts/test/assert_*.sql+.sh pattern, which does execute against a real (disposable) Postgres/TimescaleDB instance. This substitution preserves the plan's intent exactly; only the file location/format changed to match how this repository actually implements DB-executing contract tests.

Cases covered (12 assertions in one script):
1. Recently reporting device -> RECEIVING
2. Stale device (400s old, between 300s/3600s) -> STALE
3. Silent device (4000s old, past 3600s) -> SILENT
4. Delayed device (fresh receipt, source 1000s old, past 900s) -> DELAYED
5. Never-seen device (no device_raw_receipt_state row) -> NEVER_SEEN
6. NULL source timestamp with fresh receipt -> RECEIVING, not DELAYED
7. No assigned device -> NO_ASSIGNED_DEVICE, source_device_id NULL
8. Decommissioned device with old telemetry -> SILENT (documents the confirmed gap: lifecycle_status is not a state input today, not a bug)
9. Deterministic precedence: a device satisfying both SILENT and DELAYED conditions simultaneously -> SILENT wins
10. Multi-device asset: PRIMARY_METER device selected regardless of assignment insertion order
11. Correct site_id returned alongside state
12. Tenant isolation: org A's grafana_org_id against org B's asset_id -> 0 rows; org B's own org_id against its own asset -> 1 RECEIVING row

Wired into scripts/test/run_integration_environment.sh as a new step ("[connectivity-semantics]"), placed after the existing demand-capability/asset-demand regression steps and before the final migration-ledger verification — this script is exactly what .github/workflows/ci.yml's `database-integration-tests` job invokes, so the new test becomes part of the real CI gate once committed and pushed (not done in this task).
