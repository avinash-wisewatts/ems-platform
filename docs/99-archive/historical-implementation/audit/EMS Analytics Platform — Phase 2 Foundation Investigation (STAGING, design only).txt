===============================================================================
A. EXECUTIVE SUMMARY
===============================================================================

1. The incident that triggered this work (job-1000 normalization stall →
   downstream stale demand_intervals + energy_consumption_1min gap) was NOT a
   1079/1080 problem. It is one instance of a single architectural class:
   "a processing stage derives its work window from wall-clock time instead of
   from how far its own input has actually been incorporated." The class is
   present at THREE distinct layers, only one of which has been fixed:

     a. telemetry.run_normalization_job (job 1000)  — FIXED (migration 205
        added a bounded catch-up window; the watermark itself always existed).
     b. telemetry.run_energy_routing_job (1001) and
        telemetry.run_environment_routing_job (1012) — NOT FIXED. [INF] These
        have the SAME "advance to max(source ingest time) in one transaction"
        shape job 1000 had before migration 205. A large normalized_points
        burst will make them attempt one unbounded transaction, exceed the
        5-minute max_runtime, roll back, and retry against an equal-or-wider
        window every minute — the exact stall mechanism, one hop downstream.
        This is the single most important newly-surfaced finding.
     c. Every analytics-tier job (1078 demand, 1079/1080 energy 1min/5min,
        1099 15min, 1102 hourly, 1105 daily, 1107 environment daily) — NOT
        FIXED, and worse than (b): they have NO persisted watermark at all,
        their max_runtime is 00:00:00 (unlimited) and max_retries is -1
        (infinite). [VR]

2. analytics.demand_intervals has a second, independent defect: finalisation
   writes INSERT ... ON CONFLICT DO NOTHING against a write-once row. A bucket
   finalised NO_DATA / INCOMPLETE while upstream was stalled is never
   reconsidered, even after real data arrives and even inside the 3-hour
   lookback. [VR]

3. The native continuous aggregates in the energy path
   (ca_energy_1min/5min/15min/hourly/daily, and the phase-power / electrical
   families) are all materialized_only = true. [VR] Querying them returns
   NOTHING for any time range past their refresh watermark — there is no
   real-time union with telemetry.energy_measurements. So a stalled or
   too-narrow CAGG refresh directly produces an empty read for job 1079,
   independent of job 1079's own lookback.

4. Recovery is ultimately capped by telemetry.raw_messages retention = 48h
   [VR, matches VS]. No watermark or backfill design can recover past that;
   it is the binding constraint on "how long can this platform self-heal."

5. Recommended architecture (design only, not approved): Option D (hybrid) —
   each analytical child owns an independent processing watermark
   (parent_available_through vs child_processed_through kept strictly
   separate), each run does BOUNDED catch-up work (the migration-205 pattern),
   every child write is idempotent (already true except demand_intervals,
   which becomes a status-guarded DO UPDATE), plus a cheap bounded trailing
   RECONCILIATION pass per tier as the safety net for the one thing a single
   high-water mark cannot represent (an internal hole). NOTIFY is optional
   latency sugar layered on top later, never the correctness mechanism. No
   message broker, no external queue, no new work-queue table — reuse
   telemetry.pipeline_state's shape and TimescaleDB's own job primitives.

6. Independent of the self-healing work: normalized_points compress_after = 1
   day [VR] is too aggressive for a table that is a backfill/reprocessing
   source; and several analytical tables (demand_intervals, environment_daily,
   energy_consumption_daily, ca_energy_daily, electrical_ext_*) have NO
   retention policy at all [VR] — fine for low-cardinality daily tables, a
   real unbounded-growth risk for demand_intervals (15-min resolution ×
   per-asset + per-site scope).

C. CURRENT FAILURE / SELF-HEALING MATRIX
===============================================================================

Legend for "Recoverable outage ceiling" = the longest upstream gap after which
the stage still returns to correct data WITHOUT a manual repair.

STAGE: telemetry.normalized_points  (job run_normalization_job)          [VR]
  Watermark: pipeline_state.last_received_at, keyed on raw_messages.received_at
  Source-avail vs child-processed: SAME COLUMN (single HWM) — acceptable here
    because this is the first stage and its source (raw_messages) has no
    upstream watermark to diverge from.
  Write: capture_bucket_samples + normalized_points ON CONFLICT DO UPDATE
    (guarded: only fill NULL lineage / newer receipt). Idempotent.
  Transaction: single; EXCEPTION → set FAILED + RAISE ⇒ watermark ALSO rolls
    back ⇒ no partial progress, no false advance.
  Bounded catch-up: YES since migration 205 (p_max_window; NULL = old behaviour;
    run_normalization_job still passes NULL, so steady state unchanged).
  1h / 6h / 12h / 24h / 48h outage: self-heals; >~5min of backlog per run
    needs a bounded p_max_window sequence (as executed manually in the incident:
    32 × 30-min calls).
  Burst after disconnect: self-heals (watermark advances further next run).
  Child job down then resumes: self-heals (durable watermark).
  Crash / DB restart mid-run: full rollback; watermark unmoved; retries.
  Recoverable outage ceiling: 48h (raw_messages retention). Beyond → permanent.

STAGE: telemetry.energy_measurements (job run_energy_routing_job)         [VR/INF]
  Watermark: pipeline_state.last_received_at on normalized_points.platform_received_at
  Write: ON CONFLICT (bucket_start,device_id) DO UPDATE WHERE newer AND
    now()<=correction_deadline; MISSING rows INSERT regardless of age.
    ⇒ gap buckets (no row) DO backfill; already-written rows past their
    correction deadline do NOT get corrected.
  Transaction: single; forward bound = max(platform_received_at) — UNBOUNDED.
  NO p_max_window.
  1h–2h outage: self-heals in one run.
  6h+ outage / burst: [INF] one giant transaction, likely > 5-min max_runtime,
    killed, rolled back, retried next minute against equal-or-wider window ⇒
    STALL (same failure mode as job 1000 pre-205). Not observed on staging
    this pass [UNK], but structurally identical.
  Crash / DB restart: full rollback; watermark unmoved.
  Recoverable outage ceiling (once bounded catch-up added): 90d (normalized_points
    retention), but effectively 48h because raw→normalized is itself capped at 48h.

STAGE: telemetry.environment_measurements (job run_environment_routing_job) [VR/INF]
  Same shape as energy_measurements. Write = UPDATE-within-deadline then INSERT
  ON CONFLICT DO NOTHING. Same UNBOUNDED forward bound, same 6h+ stall risk [INF].

STAGE: native CAggs ca_energy_* / ca_energy_phase_power_* / electrical_ext_*  [VR]
  materialized_only = TRUE ⇒ reads are EMPTY past the refresh watermark.
  Refresh is TimescaleDB-managed; start_offset 2d (1min/15min), 7d (5min/hourly),
  30d (daily).
  Outage <= start_offset: self-heals when energy_measurements is repaired AND
    the next scheduled refresh runs.
  Outage > start_offset: refresh will NOT revisit that range ⇒ permanent empty
    unless a manual refresh_continuous_aggregate(name, older_start, end) is run.
  ca_environment_15min/hourly: materialized_only = FALSE ⇒ reads union live data
    ⇒ much lower gap risk.

STAGE: analytics.energy_consumption_1min (job run_energy_consumption_1min_job) [VR]
  Watermark: NONE. Wrapper window = [date_trunc('min',now())-30min, now()).
  Source: ca_energy_1min (materialized_only).
  Write: ON CONFLICT (device_id,bucket_start) DO UPDATE — full recompute,
    idempotent. (So the ONLY defects are the 30-min window and the missing
    watermark — the writer itself is sound.)
  1h+ outage: PERMANENT GAP (window never covers it again). Confirmed by the
    incident [VS].
  Even within 30 min: if ca_energy_1min refresh hasn't materialised the range,
    reads empty ⇒ produces nothing.
  max_runtime = 0 (unlimited), max_retries = -1 (infinite) [VR].

STAGE: analytics.energy_consumption_5min (job 1080) [VR]
  As above (30-min window, no watermark, DO UPDATE). Structurally empty for
  this fleet [VS] — no traffic to gap.

STAGE: analytics.energy_consumption_15min (job run_energy_consumption_15min_job) [VR]
  Watermark: NONE. Window = [date_bin(15m,now())-2h, date_bin(15m,now())).
  Source: v_energy_consumption_native → v_energy_semantic_rollup_15min, i.e.
    the 1min ∪ 5min PERSISTED tables (not raw). ⇒ inherits any gap in 1min/5min.
  Write: DO UPDATE (idempotent).
  Parent-catches-up-child-stays-stale: a 1min repair does NOT propagate here
    automatically; 15min must be independently re-driven for the same range,
    AND its own 2h window must still cover it.
  2h+ outage: PERMANENT GAP.

STAGE: analytics.energy_consumption_hourly (job 1102) / _daily (job 1105) [VR]
  Watermark: NONE. Windows now()-2d / now()-8d. Source = energy_consumption_15min.
  Write: DO UPDATE (idempotent).
  Outage <= 2d (hourly) / 8d (daily): self-heals IF 15min underneath is correct.
  Outage > that: PERMANENT GAP. Also inherits 15min gaps regardless of own window.

STAGE: analytics.demand_intervals (job run_demand_calculation_job) [VR]
  Watermark: NONE. Wrapper lookback 3h; inner loop bound
    v_max_n = ceil(3h / demand_interval_seconds) + 2; EXIT when interval_end
    < now()-3h.
  Write: analytics.demand_intervals INSERT ... ON CONFLICT DO NOTHING —
    WRITE-ONCE. analytics.demand_state (provisional) is mutable.
  Any outage: buckets finalised NO_DATA/INCOMPLETE during the stall stay that
    way FOREVER — worse than a lookback bug; even a re-run inside 3h cannot
    fix an already-finalised row. Confirmed by the incident [VS] (1,320 rows
    manually corrected).
  Transaction: single (no inner COMMIT). site × scope × interval triple loop.
  max_runtime = 0, max_retries = -1 [VR] ⇒ a big run is never force-stopped;
    it just holds locks.

STAGE: telemetry.environment_daily (job run_environment_daily_job) [VR]
  Watermark: NONE. Window now()-8d. Write DO UPDATE (idempotent).
  Source unions live data (env CAggs materialized_only=FALSE) ⇒ lower gap risk,
  but the fixed 8d window still caps recovery and there is no watermark.

STAGE: telemetry.raw_message_failures per-row recovery (job run_failed_message_recovery_job) [VR]
  THE ONE ALREADY-CORRECT PATTERN. Per-row state: resolution_status
  (OPEN/RETRY_PENDING/RETRY.../RECOVERED/PERMANENT_FAILURE),
  replay_attempt_count (<5), next_replay_at (escalating backoff 1h/2h/6h/...),
  FOR UPDATE SKIP LOCKED, per-candidate COMMIT (migration 203), dynamic
  retention cutoff read from timescaledb_information.jobs (migration 206).
  Self-heals at every outage length up to the raw_messages retention cutoff,
  past which it correctly marks PERMANENT_FAILURE. Leave untouched.

E. CURRENT JOB SCHEDULING / FREQUENCY ANALYSIS
===============================================================================

[VR] Cadence today is coherent with source cadence and downstream freshness
need — the frequencies themselves are NOT the bug:
  - 1-minute source capture ⇒ 1-minute normalization/energy/environment
    routing and 1-minute energy_consumption_1min + demand. Reasonable.
  - 15-min tier every 5m, hourly every 15m, daily every 1h — each well
    below its own resolution; gives near-real-time rollups. Reasonable.
  - CAgg refresh cadence tracks resolution (1m/5m/15m/1h). Reasonable.

[VR] The scheduling DEFECTS are not frequency, they are:
  1. Window derivation (now()-lookback instead of watermark-based) — §G, §N.
  2. max_runtime = 00:00:00 on all 7 analytics jobs ⇒ a run that falls
     behind is never force-bounded; combined with max_retries = -1 it can
     spin or hold locks indefinitely. The telemetry jobs correctly use
     5m / 3 retries.
  3. No config-validation hook: _timescaledb_config.bgw_job has
     check_schema/check_name columns; NO EMS job populates them [VR], so a
     bad alter_job config (e.g. lookback='0') is only caught at run time by
     an in-body RAISE.
  4. Canonicalisation gap [VS, known-issues §9]: the analytics rollup jobs
     are registered only inside migrations (121/132/140/143/179–184), not in
     postgres/jobs/*.sql, unlike the telemetry jobs. Schedule-drift assertion
     (scripts/test/assert_job_schedule_canonical.sql) covers only the three
     telemetry routing jobs.
  [UNK] whether staging job CONFIG has drifted from canonical (migration 194
  was a drift-correction; needs re-check — §W).

Chain-timing observation [INF]: hourly reads 15min, daily reads 15min, 15min
reads 1min∪5min, 1min reads ca_energy_1min, ca_energy_1min refreshes from
energy_measurements. Nothing enforces that a downstream run happens AFTER its
upstream run for the same wall-clock minute — each simply trusts its lookback
window already contains complete upstream data. Usually true at steady state;
false during and after any stall.

F. CURRENT CRASH / TIMEOUT / RETRY BEHAVIOUR  (TimescaleDB 2.29.2) [VR]
===============================================================================

What TimescaleDB already provides:
  - _timescaledb_internal.bgw_job_stat: total_runs, total_successes,
    total_failures, total_crashes, consecutive_failures, consecutive_crashes,
    last_run_success, last_start/last_finish/last_successful_finish, next_start.
  - timescaledb_information.job_stats (view): last_run_status, job_status,
    last_run_duration, next_start, totals. (No consecutive_failures in the
    view — use bgw_job_stat.)
  - timescaledb_information.job_history: per-run history (start, finish,
    status, config snapshot, error data).
  - timescaledb_information.job_errors: error log.
  - Retry: on failure the job is retried after retry_period, backing off up to
    max_retries; max_retries = -1 = retry every retry_period forever; after
    the retry budget the job simply waits for its next fixed-schedule slot.
  - max_runtime exceeded ⇒ the launcher sends the worker a cancel; the running
    statement is rolled back like any cancelled statement.
  - Process crash / DB restart ⇒ consecutive_crashes/total_crashes increment;
    job is rescheduled with backoff. In-flight transaction is rolled back by
    normal WAL recovery.
  - fixed_schedule = true for policy jobs; UDA jobs created via add_job default
    to drift-free fixed scheduling as configured.

What TimescaleDB does NOT provide, and EMS must own:
  - It NEVER touches an application watermark. Whether a killed/crashed run
    leaves a false-advanced checkpoint is entirely determined by the proc.
    Current state:
      * run_normalization_job / run_energy_routing_job /
        run_environment_routing_job / run_raw_receipt_state_job: watermark
        UPDATE is the last statement in the single transaction ⇒ a kill/crash
        rolls it back with everything else ⇒ SAFE (invariant holds today) [VR].
      * run_failed_message_recovery_job: per-candidate COMMIT; each committed
        candidate's state change is atomic with its own work ⇒ SAFE [VR].
      * demand / energy_consumption_* jobs: single transaction, no watermark
        at all ⇒ a kill rolls back the whole run; nothing false-advances, but
        nothing durably progresses either — a run that can't finish inside
        (unlimited, so: inside a lock-contention or statement-timeout event)
        makes zero progress, exactly like job 1000 pre-205 [INF].
  - No "stuck RUNNING" detector. pipeline_state.last_status can sit at
    'RUNNING' indefinitely if a worker is killed between the RUNNING update
    and the terminal update. (The local test DB currently shows exactly this
    for the raw_message_failures pipeline: last_status='RUNNING',
    last_started_at today, last_completed_at yesterday — a faithful
    illustration of the pattern.) [VR]
  - No consecutive-failure alerting surface (the data exists; nothing reads it).

Critical invariant to carry into any new design:
  A watermark (or per-range completion mark) is advanced in the SAME
  transaction as the writes it accounts for, and only after them. A run that
  is killed/crashes loses at most one bounded slice, never marks unprocessed
  time as processed.

G. CURRENT WATERMARK ARCHITECTURE  [VR]
===============================================================================

telemetry.pipeline_state (created in postgres/ddl/41; header comment explicitly
anticipates "future pipelines such as environmental telemetry, alarms and
asset-health normalization" — i.e. it is intended as a generic per-pipeline
checkpoint, despite living in the telemetry schema):

  pipeline_name       text  PRIMARY KEY
  last_received_at     timestamptz          -- the SINGLE high-water mark
  last_started_at      timestamptz

  - downstream processing failed ..... pipeline_state last_status=FAILED
    (telemetry tier only); NOTHING at analytics tier.
  - downstream stale ................ NOT represented anywhere — there is no

  - partial coverage / incomplete finalised interval ..
    demand_intervals.coverage_percent + quality_status INCOMPLETE;
    energy_consumption_* per-interval valid/invalid/gap counters.

Blank-risk conclusions:
  - get_canonical_energy_read maps import_quality_status != GOOD → NULL

    it also plots quality/coverage, which no panel does. UX caveat, not a
    Phase 2 fix.
  - The demand_intervals write-once bug is a QUALITY bug: a NO_DATA row is
    indistinguishable from a legitimately-empty interval, and it is permanent.
    The fix (status-guarded DO UPDATE) restores the distinction.

===============================================================================
M. CANDIDATE SELF-HEALING ARCHITECTURES
===============================================================================

Shared requirement (the authoritative principle): the parent may only ever
publish parent_available_through; each child owns child_processed_through; a
parent value is NEVER assigned into a child's processed watermark. Outstanding
work = (child_processed_through, LEAST(parent_available_through, safe_bound)].
Each run processes a BOUNDED slice of that interval and advances
child_processed_through only for the slice actually committed.

OPTION A — Parent directly invokes child (synchronous chain)
  Mechanism: run_normalization_job CALLs the energy routing loader, which CALLs
    the 1min refresh, etc., in one call tree.
  Reliability: LOW. A slow/failing/locked child now stalls the parent —
    re-creates the exact cascade we are trying to remove, and widens the
    blast radius (one failure stops the whole chain).
  Failure/retry: parent and child share a transaction and a retry budget;
    partial completion is all-or-nothing across the chain.
  Transaction boundaries: one giant transaction per tick, or messy nested
    subtransactions.
  Coupling: maximal. Deployment: any child signature change breaks the parent.
  TimescaleDB fit: UDA jobs are not designed to invoke each other; no clean
    isolation. Concurrency: chain cannot overlap itself; a long catch-up
    blocks all fresh data.
  Crash/restart recovery: whole chain rolls back; zero durable progress.
  VERDICT: reject.

OPTION B — Durable work/range events (a queue / range table)
  Mechanism: parent, on advancing, INSERTs a row like
    (pipeline, range_start, range_end, status) into analytics.backfill_queue;
    child consumes rows FOR UPDATE SKIP LOCKED, processes, marks done.
  Reliability: HIGH if built carefully.
  Failure/retry: per-row, like job 1077 — good.
  Duplicate events: needs dedup (unique on range, or merge-on-insert).
  Missed events: if the parent crashes between advancing and enqueuing, a
    range is silently lost unless a reconciliation sweep also exists — so you
    end up needing Option C's watermark anyway.
  Ordering: must process ranges in order for cascade tiers, or track
    dependencies — extra logic.
  Operational complexity: a new schema surface, its own retention/vacuum,
    monitoring, and back-pressure semantics.
  DB overhead: an extra write per parent advance per child (x7), plus queue
    bloat management.
  TimescaleDB fit: fine (plain table).
  Precedent: job 1077's per-ROW table — but that unit of work is naturally
    per-item (a failed message). Aggregation work is naturally a contiguous
    time range, for which a moving watermark is the simpler exact fit.
  VERDICT: reject as the primary mechanism — it is more moving parts than the
    problem needs and still requires a watermark/reconciliation backstop. Keep
    in reserve only for a tier that is simultaneously expensive, non-idempotent
    and hole-prone (none currently qualify).

OPTION C — Child dependency watermark (pure)
  Mechanism: each child stores child_processed_through in a pipeline_state-shaped
    row. Each run: read child_processed_through; read parent_available_through
    (= the parent pipeline's own watermark, NOT wall clock); v_to =
    LEAST(parent_available_through, ...); v_from = child_processed_through -
    small_overlap; cap forward progress at v_from + max_catchup_window
    (migration-205 pattern); process [v_from, v_to_capped); on success advance
    child_processed_through to v_to_capped in the same transaction.
  Reliability: HIGH. Durable, survives any outage length up to source
    retention, resumes exactly where it left off.
  Failure/retry: run fails ⇒ transaction (incl. the watermark advance) rolls
    back ⇒ same slice retried next tick. No false advance.
  Transaction boundaries: one bounded slice per run (or an inner COMMIT per
    slice if a single run drains several, à la job 1077).
  Coupling: minimal — child reads parent's published watermark value only.
  DB overhead: steady state identical to today (one small window per run).
  TimescaleDB fit: perfect — pure SQL, reuses pipeline_state.
  Duplicate/missed events: N/A — there are no events; the watermark IS the
    truth. A parent advancing while the child is down just means a bigger
    outstanding interval, drained over multiple bounded runs.
  Crash/DB restart: watermark is durable table state; recovers automatically.
  GAP: a single max() watermark cannot represent an internal hole
    (09:00 OK, 10:00 FAILED, 11:00 OK). With strict "advance only the
    contiguous committed prefix" semantics this is safe (the watermark simply
    stops at 10:00 and 11:00's success is re-done later) — but only if each
    run processes a contiguous slice from the watermark forward and never
    "skips ahead". A run that processes newest-first, or a partial failure
    inside a slice, can still leave a hole below the watermark.
  VERDICT: strong core; needs a small backstop for the hole case.

OPTION D — Hybrid: child watermark + bounded trailing reconciliation
            (+ optional NOTIFY early-wake)   <<< RECOMMENDED
  Mechanism: Option C as the steady-state driver, PLUS a low-frequency,
    read-mostly reconciliation pass per tier that re-derives a bounded
    trailing window (e.g. "last 24h" for the minute tiers, "last 8d" for
    daily) straight from source and re-UPSERTs it. Because every child writer
    is idempotent (energy_consumption_* already DO UPDATE; demand_intervals
    becomes status-guarded DO UPDATE), re-processing a trailing window has no
    side effects beyond correcting whatever was wrong. The reconciliation
    window size is the explicit bound on "how large a hole can hide" — a hole
    older than the window triggers an alert rather than silent correction.
  Optional: parent emits pg_notify('pipeline_advanced', child) after advancing
    its watermark; a listening child wakes immediately instead of waiting for
    its next tick. Pure latency optimisation; if the NOTIFY is lost, the next
    scheduled tick still does the work. NOTIFY is NEVER consulted for
    correctness.
  Reliability: HIGH + defence in depth. The watermark handles outages of any
    length; reconciliation handles checkpoint bugs, partial-slice holes, and
    late-arriving source data that landed behind an already-advanced window.
  Cost: reconciliation is a bounded periodic scan (cheap, tunable, off the hot
    path). No new schema beyond the watermark rows (+ optionally a tiny
    reconciliation-run log for observability).
  TimescaleDB fit: perfect. Operational complexity: low — one more scheduled
    job pattern, same shape as everything else.
  VERDICT: recommended.

N. RECOMMENDED ARCHITECTURE

Adopt Option D. Concretely, and reusing only mechanisms already in the
codebase:

1. WATERMARK STORE. Reuse the telemetry.pipeline_state SHAPE for the analytics
   tier. Decision to make explicitly (do not assume): either
   (a) add rows to telemetry.pipeline_state (its own header comment invites
       "future pipelines"; simplest; one cross-schema read from analytics
       procs), or
   (b) create analytics.pipeline_state with the identical column contract if
       schema ownership is considered load-bearing.
   Recommendation: (a), unless a reviewer identifies an analytics-schema
   isolation rule. Add one row per analytics pipeline:
     energy_consumption_1min, energy_consumption_5min, energy_consumption_15min,
     energy_consumption_hourly, energy_consumption_daily, demand_intervals,
     environment_daily.
   The single last_received_at column is repurposed as
   child_processed_through. parent_available_through is NOT stored on the
   child — it is read live from the parent pipeline's own row
   (or, for tiers whose parent is a native CAgg, from
   _timescaledb_catalog.continuous_aggs_watermark). This keeps the two values
   structurally distinct and makes it impossible to accidentally persist a
   parent value as a child's processed mark.

2. WINDOW DERIVATION. In each analytics job wrapper replace
     v_to   := clock_timestamp();  v_from := v_to - v_lookback;
   with
     v_parent_through := <parent watermark / CAgg watermark for this tier>;
     v_to   := LEAST(date_bin(<res>, clock_timestamp()), v_parent_through);
     v_from := GREATEST(v_checkpoint - v_overlap,
                        v_to - v_max_catchup_window);
     ... process [v_from, v_to) ...
     -- on success, in the same txn:
     v_checkpoint := v_to;
   v_max_catchup_window is a NEW config key, separate from the existing
   lookback/overlap (exactly as migration 205 kept p_max_window separate from
   p_overlap). Steady state: v_checkpoint is at "now", so [v_from, v_to) is
   one tick wide — identical cost to today. After an outage: the interval is
   drained over ceil(outage / v_max_catchup_window) bounded runs.

3. CASCADE TIERS derive v_parent_through from their IMMEDIATE parent's
   checkpoint, never wall clock:
     energy_consumption_15min.v_to =
        LEAST(now_binned, checkpoint(energy_consumption_1min),
                          checkpoint(energy_consumption_5min))
     energy_consumption_hourly.v_to = LEAST(now_binned, checkpoint(15min))
     energy_consumption_daily.v_to  = LEAST(now_binned, checkpoint(15min))
   This closes "parent catches up, child stays stale" — a tier can never claim
   to have processed a range its own input has not reached.

4. demand_intervals FINALISATION becomes:
     INSERT ... ON CONFLICT (<the two partial unique keys>) DO UPDATE
       SET <all computed columns>, finalized_at = clock_timestamp()
       WHERE demand_intervals.quality_status <> 'VALID';
   i.e. a previously-uncertain finalised row (NO_DATA / INCOMPLETE /
   INVALID_SOURCE / INSUFFICIENT_SOURCE_RESOLUTION) is reconsidered on every
   pass; a VALID row is never overwritten. Same logic the manual incident
   repair used, made automatic and bounded inside the job's normal run. Plus a
   demand child watermark so the reconsideration window is watermark-bounded,
   not the fixed 3h.

5. TELEMETRY-TIER PARITY (do this FIRST — it is the smallest, safest, and
   closes the "incident recurs one hop down" gap): add the migration-205
   p_max_window parameter to telemetry.load_energy_measurements_incremental
   and telemetry.load_environment_measurements_incremental. NULL default =
   byte-for-byte current behaviour; run_energy_routing_job /
   run_environment_routing_job keep passing NULL. This gives an operator the
   same bounded manual catch-up tool that saved job 1000, for jobs 1001/1012.

6. BOUNDED RECONCILIATION. One scheduled pass per tier (or one pass iterating
   all tiers), low frequency (e.g. every 1h for minute tiers, every 6h for
   daily), that recomputes a bounded trailing window straight from the tier's
   source and re-UPSERTs. Emits a metric/log line; raises visibility (not an
   exception) if it finds and corrects anything, and alerts if it finds a
   discrepancy older than its own window.

7. JOB HARDENING. On every analytics job: set max_runtime to a real value
   (5m for the 1-minute tiers, 10m for demand/daily), set max_retries to a

   malformed v_max_catchup_window / lookback at alter_job time.

8. NOTIFY (optional, later phase). Parent SELECTs pg_notify after its
   in-transaction watermark advance; child LISTENs and wakes early. Removes

===============================================================================
O. CANONICAL PROCESSING / WATERMARK SEMANTICS
===============================================================================

Definitions (per analytical pipeline P with immediate source S):

  available_through(S)  = the point up to which S's own processing has
                          durably succeeded. For a telemetry pipeline: its
                          pipeline_state.last_received_at. For a native CAgg:
                          its continuous_aggs_watermark. For a persisted
                          analytical tier: that tier's own processed_through.
  processed_through(P)  = the point up to which P has durably incorporated S,
                          stored in P's own watermark row. Initialised to a
                          floor (e.g. now() - lookback) on first run.

  outstanding(P) = ( processed_through(P),
                     LEAST( available_through(S1..Sn), now_binned ) ]

  Each run:
    slice_end   = MIN( upper bound of outstanding(P),
                       processed_through(P) + max_catchup_window )
    slice_start = processed_through(P) - overlap
    process [slice_start, slice_end)         -- contiguous, oldest-first
    IF success: processed_through(P) := slice_end     -- same transaction
    ELSE:       roll back everything, including the watermark advance

Rules:
  R1. A parent value is read, never written, by the child. processed_through is
      written only by that pipeline's own successful run.
  R2. Advance is monotonic and contiguous from the current watermark forward.
      A run never advances past a sub-range it did not commit. No "process
      newest first then set max()".
  R3. The advance statement is the last write in the slice's transaction.
  R4. overlap covers boundary races and just-closed buckets; max_catchup_window
      bounds per-run cost; lookback (if retained at all) becomes just the
      first-run floor.

HOLE HANDLING — is a bare watermark enough, or is explicit range tracking
required? Recommendation: watermark + bounded trailing reconciliation, NOT a
per-range completion table, because:
  - every child writer is idempotent (or made so), so re-running a trailing
    window is free of side effects;
  - contiguous oldest-first advance (R2) means a failed slice simply halts the
    watermark — later successes are re-done, not skipped, so no hole forms
    below the watermark in the first place;
  - the reconciliation window is an explicit, per-tier bound on residual risk
    (a hole can only hide if it is BOTH below the watermark AND older than the
    reconciliation window — and that condition is alertable).
  A per-range table (analytics.*_processed_ranges) is only justified for a tier
  that is expensive AND non-idempotent AND hole-prone simultaneously. None of
  the eight tiers meet all three today; revisit if one ever does.

===============================================================================
P. JOB SCHEDULING / FREQUENCY RECOMMENDATION
===============================================================================

A. Upstream watermark jobs (run_normalization_job, run_energy_routing_job,
   run_environment_routing_job): keep continuous @1m, max_runtime 5m,
   retries 3. ADD p_max_window to the energy + environment loaders (parity
   with normalization). No cadence change.

B. Domain routing jobs = the same three jobs as A. No separate action.

C. Native CAggs: keep TimescaleDB-managed refresh at current cadence. Do NOT
   widen start_offsets by default — the raw_messages 48h retention already
   caps recoverable outage below the 2d minimum start_offset. IF raw retention
   is raised (see R), revisit ca_energy_1min/15min start_offset to match.
   Keep as a documented manual step: refresh_continuous_aggregate() for any
   recovery beyond start_offset.

D. Persisted analytical rollups (energy_consumption_1min/5min/15min/hourly/
   daily): keep current cadence (1m / 1m / 5m / 15m / 1h — each well inside
   its resolution). Change ONLY window derivation (watermark, §N/§O). Set
   max_runtime (5m for 1m/5m/15m tiers, 10m for hourly/daily), retries 3.
   Add per-tier max_catchup_window config (start it equal to the current
   lookback, so behaviour is unchanged until an outage).

E. Demand finalisation (run_demand_calculation_job): keep @1m. Add demand
   watermark; status-guarded DO UPDATE; max_runtime 10m; retries 3. The 3h
   lookback becomes the first-run floor only.

F. Environment daily (run_environment_daily_job): keep @1h. Same treatment as
   D, AFTER confirming its source chain (§U phase 5). Because ca_environment_*
   are materialized_only=FALSE, gap risk is lower, but the watermark still
   removes the fixed-8d ceiling.

G. Failure recovery (run_failed_message_recovery_job): NO CHANGE to mechanism.
   Reconcile the canonical registration to limit=1000 to match staging [D].
   Consider raising cadence from 1h only if backlog-drain latency is a concern
   (out of scope here).

New reconciliation jobs (from §N.6): one @1h covering the minute/demand tiers
(trailing 24h), one @6h covering hourly/daily/environment-daily (trailing
8–14d). max_runtime 10m, retries 1, read-mostly.

===============================================================================
Q. CRASH / STUCK JOB RECOVERY RECOMMENDATION
===============================================================================

Use what TimescaleDB 2.29.2 already gives, add the minimum on top:

  1. TERMINATION: give every analytics job a real max_runtime (§P). That alone
     converts "unbounded run holds locks forever" into "run is cancelled,
     rolled back, retried" — and with the §O watermark semantics a cancel
     loses at most one bounded slice.

  2. FALSE-ADVANCE PREVENTION: enforce R2/R3 (§O) — watermark advance is the
     last write in the slice transaction, contiguous from current position.
     Add a regression test per pipeline that kills a run mid-slice and asserts
     the watermark did not move (the pattern already used for job 1077's
     per-candidate commit test).

  3. DETECTION (all from existing state, zero new tables):
       - repeated failure: _timescaledb_internal.bgw_job_stat.consecutive_failures
       - crash loop: bgw_job_stat.consecutive_crashes / total_crashes
       - stuck RUNNING: pipeline_state.last_status='RUNNING' AND
         age(last_started_at) > 3 * max_runtime
       - watermark not advancing: age(processed_through) beyond SLA while the
         parent watermark IS advancing
       - per-run detail: timescaledb_information.job_history / job_errors

  4. RETRY/BACKOFF: finite max_retries (3) + retry_period 5m on analytics jobs,
     so a persistently failing job stops hammering and surfaces via
     consecutive_failures instead of retrying forever silently (current
     max_retries = -1).

  5. CONFIG SAFETY: populate check_schema/check_name on each job with a small
     validator function so a bad alter_job (negative/zero window, absurd
     catch-up) is rejected at configuration time, not discovered at 02:00.

  6. RECONCILIATION (§N.6) is itself the recovery mechanism for any watermark
     that DID get corrupted by a bug outside these guarantees: it re-derives a
     bounded trailing window from source regardless of watermark state.

Do NOT build a bespoke "watchdog that kills RUNNING jobs" — max_runtime is
that watchdog. The only EMS-side addition is the stuck-RUNNING ALERT (a job
worker killed between the RUNNING and terminal pipeline_state writes leaves a
stale RUNNING row; alert on it, and have each proc's normal start path
overwrite a stale RUNNING for its own pipeline).

===============================================================================
R. RETENTION RECOMMENDATIONS
===============================================================================

Decide these PURPOSEFULLY; each line has a rationale, not "keep longer".

  1. telemetry.raw_messages 48h → raise to 7d (or an explicit operational
     number). RATIONALE: this is the single cap on automatic recovery for the
     ENTIRE analytical pipeline. 48h did not cover the ~15h incident with much
     margin; a longer undetected stall over a weekend would exceed it and make
     recovery physically impossible. 7d covers "Friday-evening stall noticed
     Monday". COST: highest-volume table — quantify the storage delta on
     staging before committing (§W). This is the highest-leverage retention
     change in the whole exercise.

  2. telemetry.normalized_points 90d, telemetry.energy_measurements 90d:
     KEEP. Already far exceed any plausible outage + drain time. They are the
     reprocessing floor above raw.

  3. analytics.demand_intervals (none) → set an explicit policy, e.g. 5y
     (customer-analytics history) or 2y if peak-demand history need is
     shorter. RATIONALE: 15-min resolution × (every PRIMARY_METER asset +
     every site) with no retention = unbounded growth on a compressed but
     ever-larger hypertable. [UNK] current row count / growth rate — §W.

  4. ca_energy_electrical_ext_15min / _hourly (none): set retention consistent
     with their sibling CAggs (2y / 5y) unless a consumer needs otherwise.
     [VS] not directly dashboard-consumed; low urgency but tidy.

  5. analytics.energy_consumption_daily (none), ca_energy_daily (none),
     telemetry.environment_daily (none), phase_power_daily (none): daily
     resolution, low cardinality — leaving unbounded is defensible; if a
     policy is wanted for uniformity, 10y. Low priority.

  6. Publish a RECOVERY-CEILING MATRIX in the platform manual:
     for each customer-facing tier, max_auto_recovery = MIN(all upstream
     retentions on its path, all native-CAgg start_offsets on its path),
     so "how far back can this self-heal" and "past what point is data
     physically gone" are answerable at a glance.

  7. Classify retention by PURPOSE in the manual:
     operational-recovery (raw_messages, normalized_points, energy_measurements)
     vs customer-analytics-history (energy_consumption_*, demand_intervals)
     vs audit (raw_message_failures) vs source-of-truth (normalized_points).

===============================================================================
S. COMPRESSION RECOMMENDATIONS
===============================================================================

  1. telemetry.normalized_points compress_after 1d → align to >= 7d (the
     operational-recovery window). RATIONALE: it is upsert-updated by the
     normalization catch-up path and read directly by demand finalisation;
     compressing at 1d makes routine catch-up and demand backfill fight
     decompression. [UNK] confirm on staging whether current backfills touch
     compressed chunks (§W) — if they already do and it is fine, this drops in
     priority.

  2. telemetry.energy_measurements compress_after 7d: KEEP, but document that
     any correction/backfill older than 7d incurs chunk decompression. With
     the §N design, backfills of that age should be rare (bounded catch-up
     drains within hours of an outage).

  3. CAgg compression (7d–90d): KEEP. All ages exceed their refresh
     start_offsets, so refresh never fights compression.

  4. Adopt and document the rule:
       compress_after(table) >= MAX( its refresh/start_offset window,
                                     the operational-recovery window,
                                     the routine-backfill window ).
     Audit every hypertable against this rule once; today only
     normalized_points violates it.

  5. No table should be compressed MORE aggressively to "save space" without
     checking this rule — the columnstore conversion cost on
     decompress-for-write dwarfs the storage saving on a
     frequently-reprocessed table.

METRICS — nearly all available from existing state; new state = only the

                                continuous_aggs_watermark (CAggs)

  backlog duration              now() - child_processed_through

                                bgw_job_stat.total_duration / total_runs

===============================================================================
V. RISKS AND TRADEOFFS
===============================================================================

  - Bounded catch-up = slower recovery (N small runs vs 1 big one). Tunable
    via max_catchup_window; identical tradeoff migration 205 already accepted
    for job 1000 (32 runs ≈ 96 min to drain 15h there).
  - Reusing telemetry.pipeline_state from analytics procs crosses a schema
    boundary. Mild; the alternative duplicates a table + its maintenance.
  - Adding max_runtime to demand/analytics jobs: a run legitimately needing
    more than max_runtime for a large backfill is cancelled mid-way — SAFE
    only because of the §O invariant (advance only the committed contiguous
    slice). If any proc later adds an inner COMMIT, each committed slice must
    advance the watermark atomically with its own writes (the job-1077 rule).
  - Widening CAgg start_offsets raises every-cycle refresh cost — only do it
    where a real recovery need exceeds the current window AND raw retention
    supports it.
  - Raising raw_messages retention increases storage on the largest table —
    size it on staging first.
  - Reconciliation window sizing: too short lets a hole hide; too long wastes
    scans. Per-tier tuning + the "hole older than window" alert as backstop.
  - NOTIFY (Phase 8) is not durable; must remain a pure optimisation with the
    scheduled tick as the guaranteed path. Risk only if someone later treats
    it as the mechanism.
  - Canonicalisation churn: moving the persisted-rollup job registration into
    postgres/jobs/ touches deploy ordering — do it in isolation, verify
    against a fresh-deploy test.
