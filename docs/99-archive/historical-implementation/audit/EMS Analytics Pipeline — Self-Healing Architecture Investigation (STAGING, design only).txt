5. Additional concrete finding (not in your list, discovered this pass)

analytics.energy_consumption_5min is not just theoretically fragile — it is verified structurally empty for the entire current device fleet, because refresh_energy_consumption_5min only processes capture_interval_seconds=300 devices and every device here is configured at 60. This isn't a bug to fix; it means any self-healing design for the "5min tier" should not assume it ever has real traffic on this deployment — worth keeping in mind so a future engineer doesn't "fix" an empty table that was never supposed to have data.

7. Recommended Architecture

Extend the exact telemetry.pipeline_state shape and the exact migration-205 p_max_window bounded-catch-up pattern to every analytics-tier job that currently lacks a watermark (1078, 1079, 1080, 1099, 1102, 1105, 1107). Concretely:

- Add rows to telemetry.pipeline_state (reuse the table as-is — it's schema-generic, not telemetry-specific despite its schema location) for each of these seven pipelines, or a lightweight analytics.pipeline_state mirror if schema ownership matters more than reuse (verify which before implementing — this is exactly the kind of decision that should be confirmed against repo convention, not assumed).
- Each job wrapper changes from v_from := clock_timestamp() - v_lookback to v_from := GREATEST(v_checkpoint, v_to - v_max_catchup_window), where v_checkpoint comes from the pipeline's own pipeline_state.last_received_at and v_max_catchup_window is a new, separate config value bounding per-run work (distinct from the lookback/overlap value, exactly as migration 205 separates p_overlap from p_max_window). After a successful call, advance the checkpoint to v_to (or the actual max processed, if less).
- For analytics.demand_intervals specifically: also change the finalization INSERT ... ON CONFLICT DO NOTHING to ON CONFLICT (...) DO UPDATE ... WHERE demand_intervals.quality_status IN ('NO_DATA','INCOMPLETE','INVALID_SOURCE','INSUFFICIENT_SOURCE_RESOLUTION') — i.e., only ever overwrite a previously-uncertain row, never a resolved VALID one. This is the exact same logic the manual repair used, made permanent and automatic within the job's own normal bounded run, not a separate reconciliation pass.
- For the cascade (15min ← 1min/5min; hourly/daily ← 15min): give each tier its own watermark against its own immediate source's watermark, not wall-clock time — so 15min's effective v_to is LEAST(now(), source_1min_checkpoint, source_5min_checkpoint), guaranteeing it never claims to have processed a range its own inputs haven't actually reached yet. This directly closes the parent-catches-up-child-stays-stale gap (finding #5).
- Add the lightweight periodic audit (option 5's safety net) as a read-only, low-frequency (e.g., once/day, or manually invocable) diagnostic query per pipeline — SELECT max(source.ts) vs pipeline_state.last_received_at — that raises visibility (log/metric/pipeline_state.last_error) if divergence exceeds a threshold, without ever driving the hot path.

Why sufficient: every failure mode in §3/§4 that's currently a "CURRENT BUG" is closed by (a) a durable watermark surviving any outage length, (b) bounded per-run catch-up preventing the "one giant scan" the user explicitly ruled out, and (c) DO UPDATE-with-status-guard replacing DO NOTHING, closing the one bug a watermark alone can't fix.

What existing components are reused, unmodified: telemetry.pipeline_state's exact shape; migration 205's exact p_max_window/LEAST(...) pattern; analytics.calculate_demand_window()/analytics.refresh_energy_consumption_*() — none of the actual calculation logic changes, only how each job derives its [p_from, p_to) window and how demand_intervals writes.

Minimal schema/function/job changes: one new/reused watermark table (or table extension) + one migration per job wrapper (7 wrappers) changing window-derivation logic + one migration changing demand_intervals's ON CONFLICT clause. No new job, no new schema concept, no new table beyond the watermark rows.

Expected runtime cost: unchanged in the steady state (each run still processes a small bounded window); during an outage recovery, cost is proportional to outage length / v_max_catchup_window runs, each individually cheap — same shape as the job-1000 recovery we already executed and measured (32 chunks × ~2-40s each).

Worst-case recovery behavior: a 2-day outage on the 1min tier (worst case in the matrix) would need roughly 2 days / v_max_catchup_window runs to fully drain — at a 30-minute v_max_catchup_window per run (matching the current lookback value, repurposed), that's ~96 runs at 1/minute cadence ≈ 96 minutes to fully catch up, each run bounded and cheap. This is a deliberate, tunable trade-off (larger v_max_catchup_window = faster catch-up, more per-run cost) — exactly the same trade-off migration 205 already exposed for job 1000.

Avoids rescanning healthy history: yes — once v_checkpoint = v_to (caught up), every subsequent run's window is trivially small (one lookback-worth), identical in cost to today's steady-state behavior.

Prevents permanent blanks: yes, for both root causes found (missing watermark, and demand_intervals' finalize-once-forever write).

11. What Remains Unsafe After This Change

- An outage longer than raw_messages'/normalized_points'/energy_measurements' own retention windows (48h/90d/90d respectively) is still permanently unrecoverable at the root — no watermark design can recover data that's been physically deleted. This is a retention-policy risk, not an aggregation-job risk, and out of this design's scope.
- The native TimescaleDB continuous aggregates (ca_*) still rely on their own start_offset windows (2d-30d) — an outage exceeding those (implausible but not impossible) would need a manual refresh_continuous_aggregate() call, same as any TimescaleDB deployment; this design doesn't change that.
- analytics.energy_consumption_5min remains permanently empty by design (capture-interval routing) — not a defect, but also not "fixed" by this architecture, since there's nothing to fix.
- environment_daily's exact dependency chain was not independently re-verified this pass (assumed parallel to the energy cascade) — should be confirmed before migration 211 is written.
