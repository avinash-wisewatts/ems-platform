| [ADR-018](decisions/ADR-018-asset-point-assignment-and-commissioning.md) | Decided (product/architecture); not implemented | 2026-09-20 | Analytics must derive an asset's available data points from `metadata.asset_points` (confirmed assignments) only, never from device/meter capability, device profile, source-technology grouping, or the current Grafana asset-point selector. Commissioning model: automatic initial candidate assignment from the wired device's configured points + required Admin confirmation/adjustment. Pre-commissioning telemetry stays device-level, never auto-promoted to asset history. Initial commissioning backfills only confirmed points; points added later do not backfill. Moving a point between assets is an explicit Admin "Move Sensor / Data Point" operation (close old binding, open new one at the move time); historical attribution is immutable — assignment changes affect future attribution only. Verified current gap: telemetry attribution (`telemetry.resolve_primary_asset_id()`) uses `asset_devices`/`PRIMARY_METER` only, with no `lifecycle_status`/`asset_points` check (confirmed on staging via a `DRAFT`-status asset already accumulating real energy history); a real commissioning-readiness/gate mechanism (`lifecycle_status`, `metering_requirement`, `analytics.v_commissioning_readiness`, audited `admin.commission_asset()`) already exists and is Admin-Portal-visible but never touches `asset_points`. Which architectural seam enforces the gate (raw-persistence vs. Analytics-read-layer) is explicitly left undecided. **Amended same day**: split into Device Commissioning (automatic; verified as a real, deployed, audited `admin.commission_device()` action, not merely conceptual — but its own readiness check requires normalization to already be working, and is asset-assignment-independent only for `STANDALONE`-policy devices, 4 of 59 on staging) vs. Asset Commissioning (explicit, Admin-confirmed); see ADR-018's Amendment section for the full verification. **Amendment 2, same day**: confirmed Asset↔Device is already many-to-many in the schema for every `relationship_type` except `PRIMARY_METER` (deliberately `ASSET_AND_DEVICE_UNIQUE` via a named `exclusivity_policy` column; all 8 others are `NON_EXCLUSIVE`) — the target many-to-many model needs no schema change; `ASSET_ASSIGNED` operational policy identified as the sole, isolated coupling to remove for decoupled device commissioning; candidate-point derivation's read-side join already exists (`v_grafana_asset_point_selector`, unfiltered by relationship_type) but no Admin write path exists; documented (not resolved) the same-semantic-point-from-two-devices ambiguity. **Amendment 3, same day**: decided to remove `PRIMARY_METER`'s special `ASSET_AND_DEVICE_UNIQUE` status entirely, with a full 34-object impact trace. **Superseded same day by Amendment 4**: the removal decision is reversed — `PRIMARY_METER` is retained exactly as-is (schema unchanged), meaning specifically "the device designated as the primary electrical measurement source for an asset," not a claim over which of its points belong to the asset. Every traced object reclassified under the corrected rule ("Analytics must not infer asset data-point ownership from `PRIMARY_METER`"): schema constraints, live-state device-preference ordering, meter-coverage/commissioning-readiness, and device-relationship Admin actions (replace/remove/assign) are all legitimate as-is (Class A); telemetry attribution (`resolve_primary_asset_id`) and every asset-level Analytics/Grafana rollup/function (consumption, demand, energy, load-profile, peak-demand, the shipped Asset Power Trend endpoint, demand-capability resolution, canonical energy read) must stop inferring asset history from `PRIMARY_METER` and instead read confirmed `metadata.asset_points` (Class B) — flagged as a real, unresolved product tension for inherently single-device metrics like Demand. No Class C (nothing requiring a primary meter needs to stop requiring one). No implementation performed. **Amendment 5, same day**: decided the Admin Portal UX for managing `asset_points` — a landing table of currently assigned points (Data Point/Friendly Name/Device Name/Status/Edit) that *is* the authoritative configuration, an "Assign Data Points" empty state, and an edit flow (pick device → grouped candidate points, pre-checked/labeled for already-assigned ones → check/uncheck + editable friendly names → explicit save only). No implementation performed. **Amendment 6, same day**: removed the separate "Commission Asset" admin action — commissioning is now triggered by an asset's first successful point-assignment Save, which moves it to `COMMISSIONING` and starts an async background backfill job (confirmed points only, per decision 5) shown as "Historical Backfill: In Progress"; the asset reaches `ACTIVE` only once that backfill succeeds. Requires new, not-yet-built durable backfill state (`Pending`/`Running`/`Completed`/`Failed`) for safe retry. Later point changes never trigger backfill (decision 6) and never rewrite existing history (decision 8), both restated unchanged. No implementation performed. **Amendment 7, same day**: chose Option A — point-level telemetry (`telemetry.normalized_points` and the already-live, already-populated `analytics.generic_telemetry_15m`/`1h` continuous aggregates) becomes the canonical foundation for asset attribution, resolved through `asset_points`, never through `PRIMARY_METER` implying full-device ownership; no second copy of telemetry is created.
